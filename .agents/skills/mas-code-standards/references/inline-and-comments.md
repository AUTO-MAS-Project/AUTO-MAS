# 内联、嵌套、命名与注释（全仓通用）

任何代码编写前先读本节；与 `mas-skills` Global Constraints、`mas-function-design` 一致。

## 内联（强制）

1. 仅使用一次的逻辑禁止抽成模块级 / 类级函数或方法。
2. 禁止为一两行逻辑或「单次调用再包一层」的薄 helper（如 `_update_x` 只转调 `_apply_x`）。
3. 调用点直接写清楚；允许为可读性做轻量重复。
4. 函数过长时用**功能块注释**分段，不要为分段再抽一层。
5. 仅当同一非平凡逻辑在**多处**复用、且抽出后显著降低维护成本时才抽函数。

## 函数嵌套风格

1. 需要闭包、递归访问、或交给 `to_thread` / `gather` 的回调时，把局部函数**嵌在调用方内部**，不要为此再建模块级 `_helper`。
2. 嵌套函数同样禁止「只调用一次的薄包装」；能内联进循环 / 调用点就内联。
3. 嵌套函数名保持极短（如 `visit`、`fetch_one`），说明写在外层函数的注释或紧邻的功能块注释里。

## 函数名

1. 名字短、动词优先、不堆描述性长句（如 `scan`、`sync`、`precheck`，不要 `scan_all_plugins_and_merge_local_over_installed`）。
2. 「做什么、边界、失败语义」放进 docstring / 紧邻注释，不要靠拉长函数名承载。
3. 避免模糊名单独使用：`handle` / `process` 须带作用域词，或改用更具体短名。

## 注释

1. 实现须有足够注释：业务意图、操作步骤、兼容性、非显然不变量、失败策略。
2. 长流程用功能块注释分段（如 `# ── 云端 Requires-Dist ──`）。
3. 公开函数用简短 docstring（Google 风格：摘要 + 必要时 Args/Returns/Raises）。
4. 不要写复述下一行代码的废话注释；不要借 cleanup 删掉仍有用的意图注释。

## 反模式

- 模块级单次使用的 `_parse_*` / `_from_*` / `_mark_*` 仅被一个调用方使用
- `_do_x` 只 `return await self._x(...)` 且无额外语义
- 为「看起来分层」而拆 `builder` / `loader` / `apply` 链
- 用超长函数名代替 docstring
