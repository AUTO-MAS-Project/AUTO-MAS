# 请求状态与即时保存

用于共享查询、即时保存或重复请求状态的重构。先核对当前实现与调用者，再提取共同机制；不要把所有读写都改造成同一种请求模型。

## 按语义选择入口

| 场景 | 复用方式 | 保留的边界 |
| --- | --- | --- |
| 多页面共享的后端列表、选项和类型信息 | Vue Query；参考 `frontend/src/composables/useEmulatorOptions.ts` 与 `frontend/src/services/queryClient.ts` | 页面是否启用、表单草稿和设备级选择仍归页面或已有模块 |
| 脚本编辑页的普通字段即时保存 | `frontend/src/composables/useScriptSaveMutation.ts` 的 `saveField` / `save` | 字段映射、初始化和专项联动由页面决定 |
| 保存后的路径回读、能力刷新 | `afterFieldSave`；复杂操作用同一入口导出的 `enqueue` | 回读范围、回滚和提示仍由页面决定 |
| 归档、恢复、导入等有副作用的操作 | 现有 API composable，例如 `useConfigBackupApi` | 不套用普通字段的缓存、合并或自动重试策略 |
| 用户编辑页另有失败记账、离开拦截或每笔保存要求 | 保留原有保存契约，先比较行为再决定能否复用 | 例如 `useMaaFWUserSaveStatus` 不合并同字段保存，不能直接替换成脚本保存入口 |

API 请求仍通过生成客户端和业务 composable。Vue Query 负责缓存与请求状态，不取代后端契约，也不为页面增加新的直接 `axios` / `fetch` 通道。

## 共享读取

- Query key 包含决定返回结果的业务上下文。会变化的脚本或用户 ID 从 ref/getter 在调用时解析；不要在新建用户时捕获一个永久为空的 ID。
- 沿用项目 QueryClient 对本地后端的设置：`networkMode: 'always'`，不因外网离线暂停请求，不自动重试或因窗口聚焦、重连而额外读取。新增查询的有效期按数据语义选择，不照抄其他查询的时长。
- 业务失败也必须进入失败状态：HTTP 成功但 `response.code !== 200` 时按契约处理，不能缓存为成功结果。公共 QueryCache 已提示的错误，页面不再重复弹出同一提示。
- 保存后需要使共享查询失效时，先取消对应的旧查询，再失效或重新读取，避免旧响应把新列表覆盖。核对实际传输层的取消能力；取消缓存更新不等于后端操作已停止。
- 页面清空自己的选项显示时，不应删除其他页面正在使用的共享缓存；保留已有设备缓存与真实设备类型规则。

## 脚本字段保存契约

使用 `useScriptSaveMutation` 时，维持以下行为：

1. **只写补丁。** 单字段走 `saveField(category, key, value)`。相互依赖的字段一次走 `save(patch)`，例如更换模拟器时把 ID 与实例索引重置放在同一个补丁里。
2. **不丢输入。** 初始化期间不落盘；初始化结束后的改动进入队列。不要用 `if (isSaving) return` 丢弃保存中的后续修改。
3. **串行与合并分开处理。** 同一脚本的写入由 mutation scope 串行执行；合并仅针对尚未开始的同字段更新。已开始的请求不替换，多个合并调用者共享最终结果。无 key 的多字段操作或等待队列完成的操作是顺序边界，不能跨越它合并。
4. **回读属于该笔保存。** `afterFieldSave` 只在保存成功后执行，并在下一笔写入开始前完成。路径规范化、能力及档案刷新按原字段集合触发；不要为普通字段新增全表回读，覆盖用户尚在编辑的值。
5. **特殊流程共用队列。** 页面特有的批量更新、回滚或等待保存完成，使用同一实例导出的 `enqueue`。不要另起 Promise 队列，或在队列之外补一笔 `updateScript`。需要保持与后续写入顺序的回读、回滚也放在该任务内。
6. **保留结果与失败行为。** 接口返回 `false` 或抛错都算失败；普通保存返回 `false`，不阻塞后续任务。页面依赖结果做回滚时继续等待该结果，保留失败输入与既有提示归属，不重复提示。
7. **保留草稿语义。** MaaFW 脚本草稿在初始化期间仍可同步本地名称，只抑制网络写入；引导切页前通过同一队列等待已排入的保存完成。不要把初始化守卫上移到本地草稿更新之前。
8. **统计整条队列。** 保存状态要覆盖该脚本正在执行与等待执行的任务；`useMutation().isPending` 只反映当前 observer 对应的 mutation，不能直接替代整条队列的状态。沿用公共入口的聚合状态。

公共层不维护按专项类型分支的回读表。MAA / SRC / General 的指定路径回读、HSR 的能力与档案刷新、MaaEnd 的特殊回滚，以及 MaaFW 的初始化和引导步骤都留在所属模块；接入前现场确认触发字段和回读范围，不照抄另一专项。

## Mutation 生命周期与超时

- 不要为尽快清缓存设置 `gcTime: 0`。已验证的 `@tanstack/query-core` 5.104.4 会在 observer 切换或卸载后对仍 pending 的 mutation 再次安排 GC；零延迟会造成反复调度。沿用客户端默认 GC，若确需更改，核对当前依赖版本并验证仍在保存时的行为。
- 页面卸载不代表已经排队的写入应被丢弃。保持既有保存完成语义，同时允许 observer 清理；不要把缓存 GC 当作取消请求。
- 不要仅用 `Promise.race` 超时来释放写队列：底层请求可能仍在写入，与下一笔交错。若任务要求超时或取消，先确定客户端取消、后端是否继续执行及配置最终状态，再设计恢复行为；不因普通重构自动增加超时。

## 最小行为验证

根据改动面选择行为验证，不为每个页面复制一套永久测试：

- 用受控 Promise 验证先后顺序、待执行同字段合并、多字段操作边界、失败后继续、成功后回读完成才放行，以及卸载时的在途保存。
- 调整 mutation 生命周期时，验证保存未结束且 observer 切换或卸载的场景；只确认已安装插件或页面可打开不能证明 GC 行为正确。
- 页面验证覆盖初始化不误写、连续改不同字段、失败保留输入、重载后持久化结果，并补被改页面特有的路径回读、能力刷新或引导等待。
- 使用模拟接口的浏览器验证只证明页面与请求编排；真实脚本、账号或游戏执行另按 [mas-e2e](../../mas-e2e/SKILL.md) 取证，不混报结果。
- 一次性验证与永久测试的取舍沿用 [前端测试规范](../../../../frontend/TESTING.md)；本地探针可归档到被忽略的 `frontend/debug/`，不随功能改动默认提交。
