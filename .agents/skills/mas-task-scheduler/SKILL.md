# MAS 任务调度

## 适用与依据

本 Skill 保存已确认的调度框架目标设计，不是当前工作区的完成情况报告。来源框架的分层与生命周期是主干；既有实现中更强的能力应归入对应层或复用基础库，不能成为保留冗余框架的理由。修改前现场检查实际入口、模型、调用方和迁移差异，不用现有兼容代码反推规范。

涉及参数、运行树、分发、锁、中止、推送或触发时机时，读取 [框架设计](references/scheduler-framework.md) 中对应章节。跨层修改读取全文。

配置机制遵守 [mas-data-model](../mas-data-model/SKILL.md) 及其配置框架参考；HTTP/WS 边界结合 [mas-api-contract](../mas-api-contract/SKILL.md)；专项能力归属结合 [mas-script-specialized-adapter](../mas-script-specialized-adapter/SKILL.md)。仅新增计划表类型时使用 [mas-plan-schedule](../mas-plan-schedule/SKILL.md)，不要把计划表注册与运行任务框架混为一体。

## 核心约束

1. **任务根直接包含托管。** 运行树为 `TaskItem → TaskScriptItem → TaskUserItem → LogRecord`。不增加 `TaskQueueItem`，直接运行和配置会话也不创建空队列节点。调度管理器用映射保存多个独立任务根，不建立总根，也不以 `TaskQueueSource` 或来源区间另行分组派发。四级执行不要求四层任务信息节点：L1 是创建流程。
2. **要求树与运行树分开。** 请求仍按队列／队列项／用户选择；真实队列下队列项解析成实际托管 UID，再进入任务根的托管列表。运行节点 UUID 独立生成，原配置 ID 仅为属性，重复托管各次执行独立记录。
3. **创建输入集中。** 公开业务模式为 `TaskMode.AUTO_PROXY`、`SCRIPT_CONFIG`、`SCRIPT_VIEW`；输入为模式、要求树和明确的触发原因枚举；运行树仅保存 `info.trigger`，不再增加来源文本或循环布尔投影。要求树顶层必须且只能有索引 `0` 一个入口：自动代理为一个队列或 `-`，会话为一个托管；不合并多个队列或混合队列／直接来源。节点统一使用 `uid`、`params`、`children`，下级索引从 0 连续递增；不恢复平铺目标、用户范围数组、`view_only` 或独立 `instance_idx` 参数。
4. **L1 完整受理并记录触发。** 短事务内校验、解析队列项、展开选择、建完整信息树；成功受理时只提交触发原因对应的启动／定时／循环时间，手动触发不更新这些时间，不保留通用上次运行时间。失败不发布部分树、不提前记时；timer 不再提交这些字段。
5. **上层持有下一层的锁。** L2 在托管循环中先解析并确认托管存在，再等待非级联 X 锁；凭证由 L2 保留，将已锁配置和上下文交 L3，等其完整收尾后解锁。L3 对每个真实用户执行相同流程，持有用户级联 X 锁并将已锁用户交 L4。L4 不重复取锁或释放上层凭证。
6. **存在性检查在取锁之前。** 每次等待重试都重新解析当前对象；找不到就记录异常、跳过或结束对应分支，不能对失效对象永久等待。取得锁后核对对象身份及最新准入条件，是竞态防护，不是将首次存在性检查后移。
7. **锁保护完整下层生命周期。** 正常派发结束释放，异常和取消由所属层 `final_task` 兜底释放仍持有的凭证，避免重复解锁。先完成下层收尾再解上层锁。共享 `default` 没有真实用户配置，仅由 L2 的托管锁保护。
8. **清单固定、字段热读。** L1 保留禁用和天数不足的用户节点；L3 在用户锁内判断自动代理准入。建树后增删重排队列不改变本轮清单。配置删除或替换保留运行节点并记录异常，不重建、不改跑别的对象。
9. **来源 TaskBase 只负责生命周期。** 下层通过 `await self.spawn(child)` 同 Task 执行；顶层 `stop()` 请求取消并等待唯一收尾，`ended` 清理登记后才完成。超时、维护检查、报告及背景任务不塞入基类。
10. **提交归产生暂存的执行协程。** 主流程在自身 Task 提交，收尾协程仅提交自己的暂存；不要指望 `final_task` 代交主流程修改。只提交实际字段，不能整份回写旧快照。必要恢复与提交完成后解锁，再发布终态；提交失败也要释放锁。
11. **运行树是唯一状态来源。** 复用 Config 的字段、集合、信号和虚拟结果，不登记为持久化根，不再手写第二套状态／结果／发布队列。查询和重连保留完整日志；WS 信息树省略正文，日志独立使用序号、追加／替换和首行号协议。任务模型定义完成后直接声明配置类订阅，随模型导入生效，按运行登记筛选事件；模型接收者生成元数据、日志增量并调用既有 WS 发送能力，不在管理器模块订阅或逐任务绑定回调；必要游标由任务根私有属性维护，不进入公开字段或配置回滚，不另建管理器影子表与推送锁。保留事务内直接推送、接受过程态的约定。
12. **timer 只补充触发时机。** 启动、定时、循环由 timer 独立判定并提交普通任务，每项任务只有一个触发原因，不设计交叉枚举或合并派发；到期不判断空闲、不等待任务结束。时间记录归 L1，结束不维护循环会话；停止当前任务不关闭排期，删除排期不再派发或回写恢复。
13. **兼容在 L2 分叉。** 插件继续 L3/L4；旧 task 直接调用原 manager，由其自行完成下层业务，不大规模改写旧专项。接入时明确唯一锁所有者，不能叠加相互阻塞的上层锁与旧 manager 取锁。旧平铺属性、用户重建和粗粒度锁只属于兼容例外。

## 实施与审查

- 按“要求节点 → 业务配置标识 → 运行节点标识 → 锁持有层 → 执行层 → 收尾与推送”追踪一次实际派发；重点核对传参、删除、等待与取消发生在哪一步。
- 游戏订阅／释放、插件声明及配置访问仅在真实调用位置留职责注释；未迁入的模块不做假注册表、占位 API 或返回成功的空实现。不能把预留位置报告为已接入。
- 卫星等配置展示从 Config 查询配置关系与持久化历史，不通过 TaskManager 快照或任务事件维护排期／最近失败的影子状态；运行快照只包含实际任务。具体边界见参考文档的“推送、日志与可写性”。
- 每项历史、通知、恢复、资源释放及统计明确唯一所有者。简单脚本操作复用现有基础能力；文件目录访问沿对应配置持锁生命周期处理，不另建目录预约框架。独立背景工作归应用级 `BackgroundTaskManager`，不属于执行树。
- 兼容专用方法、属性和类在定义处使用 `[兼容旧专项]` 或 `[兼容旧调用方]` 文档标记，说明保留原因及新代码入口；别名和混合分支使用同样的注释标记。新执行树与插件代码不新增对兼容方法的依赖，旧专项维护保留现有调用。标记本身不改变执行、接口或告警行为。
- 真实类型错误应修复；只对已确认的临时兼容或动态生成契约局部抑制并注明原因。配置集合绑定成员泛型，模式使用枚举，客户端契约通过生成器更新。
- 验证要求树顺序与重复、完整建树、动态修改删除、锁前存在性、等待取消、收尾释放、触发时间归属及兼容副作用不重复。按实际改动运行最小回归；Skill 自身的修改不声称已经修改或验证业务实现。
