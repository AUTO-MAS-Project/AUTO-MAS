# 调度框架设计参考

记录已确认的目标调度语义（文件位置、方法清单与常量现场查源码）。

## 一、创建契约、运行树与 L1–L4 分层

```text
要求树 (L1 输入): {"0": {"uid": 队列UUID|"-", "params": {}, "children": {"0": ...}}}
运行树 (内存态): TaskManager[运行UUID] -> TaskItem (L2) -> TaskScriptItem (L3) -> TaskUserItem (L4) -> LogRecord
```

- **统一入口**：`start(mode, tasks, *, trigger: TaskTriggerReason)`；公开模式仅 `AUTO_PROXY` / `SCRIPT_CONFIG` / `SCRIPT_VIEW`（维护操作走独立入口，不扩充 `TaskMode`）。
- **要求树硬约束**：顶层有且仅有键 `"0"`；下级键从 `"0"` 连续递增；非空选择必须是原配置序列的子序列（允许删选，禁逆序/增项）；同一托管在队列出现多次各保留独立执行；`SCRIPT_CONFIG`/`SCRIPT_VIEW` 必须且仅指定 1 个托管 + 1 个目标（用户 UUID 或 `"default"` 共享配置）。
- **L1–L4 职责与锁所有权**：
  - **L1**：短事务校验、展开并建完整树；成功受理才登记并仅更新 `trigger` 对应触发时间（手动不更新）；电源倒计时已启动时 L1 直接拒绝新建。
  - **L2**：按 L1 快照循环，执行队列前后置脚本；**查托管存在 → 拿托管非级联 X 锁 → 核对身份 → 交 L3 → 解锁**（旧专项在 L2 分叉给原 manager）。
  - **L3**：持托管锁后接入游戏/设备资源；逐用户**查存在 → 拿用户级联 X 锁 → 核对身份 → 锁内热读启用态与剩余天数 → 交 L4 → 解锁**（`"default"` 由 L2 托管锁保护）。
  - **L4**：使用已锁配置与上下文执行模式操作与恢复，不重复取锁、不解上层锁。

## 二、高频反模式与真实事故解读（必读）

| ❌ 错误做法（反模式） | 💥 会导致什么真实事故 | ✅ 正确做法 |
| --- | --- | --- |
| 新增 `TaskQueueItem` 或把多队列塞进同一个顶层任务根 | 破坏运行树展平契约，重复托管状态/日志互相覆盖，队列删改污染运行态 | **无 `TaskQueueItem`**；L1 受理时把队列前后置脚本与结束动作快照进任务根，多队列分多次创建独立任务 |
| 先对旧对象取锁、再第一次检查它是否存在 | 对象在等待期间已被删或替换，协程**永久死等一把无人释放的僵尸锁** | **存在性检查必须在取锁前**，且每次等待重试前重新解析对象；失效即记异常跳过，取锁后再核对身份防竞态 |
| L4 自己重取/释放用户锁，或上层非级联锁与旧 manager 锁未经适配叠加 | 引发**同任务自锁死锁**或提前释放导致并发写配置损坏 | 严格遵守「上层持下层锁」；接旧 manager 时明确唯一持锁方；异常/取消由所属层 `final_task` 兜底解锁 |
| 用 `asyncio.create_task` 派生执行树下层，或调用 `task.cancel()` 强杀 | 子层脱离取消 await 链变成游离协程，锁未释放、收尾被截断 | 执行树下层一律 `await self.spawn(child)` 同 Task 运行；停止统一用 `await task.stop()` 等待唯一收尾（独立后台工作才归 `BackgroundTaskManager`） |
| 指望 `final_task` 代交主流程的暂存配置，或在结尾整份回写启动快照 | 主流程暂存归属原 Task，跨协程提交失败或**把用户运行期间的新修改整份盖掉** | 主流程在自身 Task 提交改动字段，`final_task` 只交自己的暂存；提交失败也必须在 `finally` 释放锁 |
| 在 `TaskManager` 里另建影子状态表或给 WS 信息树塞完整日志正文 | 每次状态更新序列化几万行日志卡死事件循环，且首页视图与运行态状态撕裂 | 运行树是唯一状态源；配置类订阅紧跟任务模型声明，正文走增量日志通道（`seq`/`append`/`firstLine`），WS 信息树排除正文；首页/卫星直接查 Config 与持久化历史 |
| 让 timer 写队列上次运行时间，或在任务结束时重置循环会话 | 校验失败时提前记脏时间，或停止当前轮意外破坏定时/循环排期 | 触发时间唯一由 **L1 成功受理时**按 `trigger` 写入；timer 到期直接提交不判空闲、不等旧任务结束 |
| 电源倒计时开始后仍允许 L1 受理新任务，或睡眠/休眠后触发应用 teardown | 倒计时期间插入新任务导致半途强制关机丢数据，或唤醒后程序直接退出了 | 电源倒计时开始后 L1 查 `power_task` 直接拒绝新建；关机/重启/注销走 `ShutdownCoordinator` 退出，**睡眠/休眠不退出应用** |
| 在新插件/新执行树中继续依赖旧 manager 的平铺属性或递归锁 | 旧兼容债向新架构扩散，后续无法移除旧路径 | 兼容代码首行标 `[兼容旧专项]`/`[兼容旧调用方]`，新代码严禁新增对其依赖 |
