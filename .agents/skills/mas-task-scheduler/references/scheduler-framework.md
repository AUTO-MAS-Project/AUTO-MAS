# 调度框架设计

这里记录确认后的目标语义。实际源码可能仍处于迁移中；实现差异应明确指出并按本规范处理，不能把旧行为写回规范。文件位置、完整方法清单、缓存容量和日志行数常量现场查询，不维护实现副本。

设计来源为 `refactor/plugin-migration-v3` 的分层和 TaskBase 方案，并包含后续已确认的要求树、任务根直接包含托管、锁上移至派发层及 L1 记录触发时间等修正。来源代码用于理解原意，不覆盖这些修正，也不自动扩大当前迁移范围。

## 1. 创建契约与参数

内部创建入口接收 `mode`、`tasks` 和显式的任务触发原因，语义示意为 `start(mode, tasks, *, trigger: TaskTriggerReason)`。HTTP 手动入口保留模式与要求树，由后端指定手动原因，不要求内部调用复用 `TaskCreateIn`。手动、启动、定时、循环、QQ、MCP 等入口最终进入同一创建流程。

- `mode` 统一使用 `TaskMode`：自动代理 `AUTO_PROXY`、配置会话 `SCRIPT_CONFIG`、查看会话 `SCRIPT_VIEW`。
- 人工排查不支持；`ManualReview`、`Update`、`CycleRun` 不作为公开创建模式。更新等旧专项维护可有独立业务入口，不能以此扩充公开任务模式或 `start()` 的零散参数。
- `tasks` 顶层必须且只能包含索引 `0` 一个入口，JSON 键为 `"0"`：自动代理指定一个队列 UUID 或 `"-"`，会话指定一个托管 UUID。不得在一次请求中合并多个队列、多个 `"-"` 或混合来源。下级仍为从 0 连续递增的有序字典，允许 `"0"`、`"1"` 等多个托管／用户。索引只表达请求顺序，不是配置 ID 或运行 UUID。
- 节点仅由 `uid`、自定义 JSON 参数字典 `params` 和下级 `children` 组成。叶节点不接受非空下级。
- `params` 默认空字典，按当前节点隔离复制并向相应执行层传递，不隐式合并父级参数。`instance_idx` 属于托管节点参数，不能恢复为创建入口参数；查看语义由枚举表达，不能恢复 `view_only`。
- 队列和队列项只在 L1 选择、解析及记时期间使用；不向托管节点复制 `queue_id`、`queue_item_id`、`queue_params`，也不换成私有映射或偷偷合并到托管 `params`。父级任务信息通过配置基类的 `parent/root` 访问。
- 触发原因是单值标准枚举，仅表达手动、软件启动、定时和循环。运行树仅保存 `info.trigger`，不增加 `trigger_source`、`is_cycle` 等派生字段；查询与推送直接传递触发枚举，统计和社区业务在消费边界转换分类。每次创建只有一个原因，各触发路径独立判定和提交，不设计交叉值、组合标志或多原因合并派发，也不由 `params` 中另一份自由文本决定同一语义。

前端从现有队列、队列项、托管与用户配置接口形成候选，不另建调度可选目标接口。启动前的“本次运行范围”维护唯一有序要求草稿，运行中隐藏；队列项 UUID 区分重复托管的每次出现。动态全选、显式名单与不选择分别保存，空显式选择不得编码为全选；刷新配置不能悄悄扩大显式范围。锁定、禁用或天数不足不应从候选中消失，执行准入归后端。旧专项单 UUID 配置入口仅作标记兼容。

### 自动代理选择

要求树为“队列 → 队列项／直接托管 → 用户”。示意中的名称代表真实 UUID：

```json
{
  "0": {
    "uid": "队列UUID",
    "params": {},
    "children": {
      "0": {
        "uid": "队列项UUID",
        "params": {"instance_idx": 0},
        "children": {
          "0": {"uid": "用户UUID", "params": {}}
        }
      }
    }
  }
}
```

真实队列下的子节点 `uid` 是队列项 UUID。L1 从队列项读取实际托管 UID，不能把二者混用。队列 `uid="-"` 表示不选择队列，此时必须显式列出托管，下级 `uid` 直接是托管 UUID。

真实队列的空 `children` 选择全部有效队列项；托管的空 `children` 选择全部用户。非空选择必须是对应原配置序列的子序列，允许删选，不允许逆序、额外出现次数或新增不存在的对象。唯一顶层入口只校验对应配置存在；在其下分别校验队列项／直接托管、用户的顺序与归属。

同一托管在队列中出现多次时，各队列项独立保留一次执行，不按托管 UUID 去重。直接选择同样不能凭空增加原序列中的出现次数。

### 配置与查看会话

要求树为“托管 → 用户／default”，必须且只能指定一个托管和一个目标。空目标、多个目标、多余层级均拒绝。

用户 UUID 表示独立用户配置，`"default"` 明确表示共享脚本配置，不是“全部用户”。不创建虚拟账号，也不为共享目标锁全部用户。禁用或天数不足只影响自动代理准入，不能据此拒绝打开其配置或查看会话。

## 2. 运行信息与状态身份

```text
调度管理器：dict[运行UUID, TaskItem]

TaskItem                        单次任务的顶层全部信息
├─ TaskScriptItem               一次托管执行
│  ├─ TaskUserItem              一次用户执行或共享配置会话
│  │  └─ LogRecord
│  └─ ...
└─ ...
```

L1 不对应额外信息树根。L2 使用 TaskItem，L3 使用托管运行节点，L4 使用用户运行节点。不存在 TaskQueueItem、空队列节点或包住多个任务的总根。

不保留 TaskQueueSource、队列来源区间或同等分组。L1 只在受理期间使用局部队列引用，同时将已启用的前后脚本、结束动作和延时保存到任务根的执行配置分组；L2 按该快照在托管派发前后执行附加脚本，收尾后向现有全局电源机制交接结束动作。执行和结束路径不重读队列；删改原队列不影响本轮附加动作。执行分组不是队列运行节点，也不保存原队列身份。已有托管／用户脚本仍由各自业务入口负责。

一次创建只受理一个队列或直接托管入口，L1 将其选择解析为按顺序排列的托管执行项，直接进入任务根并返回一个任务 UUID。运行多个队列需要分别创建独立任务；L1 直接处理唯一顶层节点，不增加外层循环、队列来源列表或队列顺序比较。

- 所有运行节点自行生成 UUID，原托管、用户标识是属性。进度指针引用运行 UUID，业务查找使用原配置 ID。运行树已展平队列，不保留原队列身份，也不能将运行父链解释为原队列的反向索引。
- 同一业务配置的重复执行具有独立运行身份、状态、日志、进度和结果；不能用配置 UUID 合并运行记录。
- 运行节点直接复用 Config 基类、类型化集合、信号及虚拟字段能力。任务树只在内存中驻留，不登记为持久化配置根，不整体转换用户已有持久化配置。
- 任务名称在 L1 受理时保存于根 info.name，查询、创建通知、WS 和重连从同一快照读取；不从运行 UUID 反推名称。
- 状态及日志来自同一树；结果按当前子节点动态计算，不建立另一个结果模块或可写状态副本。
- 专项内部的子任务进度、重试及尝试记录由专项自行持有，不向公共任务树添加 `UserTaskProgress` 或同等专用字段，也不改用公共 `current` 分组存放这些数据。公共查询、推送和调度台不承担专项进度传输。
- 公共运行树不复制配置锁状态：不放 `locked`、`recursive_lock` 等投影字段。锁的申请、等待和释放归执行层，配置基类是锁状态和修改权限的依据；前端读取配置状态，不从运行节点推断权限。
- 维护跳过标记、通知明细和排版模式归专项或旧兼容执行器所有，不放 `maintenance_skipped`、`push_log`、`push_log_mode`。需要跨旧用户任务共享时，按运行节点 UUID 在旧执行链内保存，不通过树的私有属性或另一套可写状态树绕回公共模型。公共结果只聚合已有状态与日志，不引入维护计数特例。
- API/WS 契约从模型派生，集合顺序与节点数据使用配置框架既有投影；前端通过生成器更新客户端，不手改生成文件。

## 3. L1：受理、完整建树与记录触发

在短事务内读取当前配置，校验要求树，解析队列项到实际托管 UID，展开空选择并填写名称、配置身份和各级参数。禁用与天数不足的用户仍建节点，不在 L1 过滤本轮可见记录。

完整校验成功后才登记并发布任务，启动 L2。失败不登记、不发布部分树；不要在原始配置上建立长期锁来保护建树快照。

成功受理时，由 L1 为唯一真实队列提交触发原因对应的时间记录：

- 不保留通用上次运行时间；手动触发不修改三种自动触发时间，直接选托管不伪造队列或队列时间。
- 启动触发只更新启动记录，循环触发只更新循环基准；不因其他机制同时启用而更新其专属记录。
- 定时触发只更新独立的定时受理记录，定时去重和唤醒补跑均读取它；手动、启动或循环不得占用定时时间槽。旧数据中的通用时间不转换为任何触发记录。
- 校验失败或未受理不提前记时。记录表示成功创建，已创建后取消不撤销，也不等待真正开始或执行完成。
- 按当前热态对象、实际字段和事务边界提交；不恢复已删除／替换的队列，不覆盖用户刚重置的计时值，不从任务结束回写旧快照。

timer 只提供原因并提交请求，不再在创建后另写队列时间。任务完成路径同样不拥有循环更新时间的职责。

停止全部时的创建屏障归 L1：封闭新创建，等待已受理创建结清，再等待各执行器完整停止；不能仅截取当前运行表而漏掉正在创建的任务。电源任务已进入倒计时时，L1 创建入口直接结束本次请求，不建树、不登记、不记触发时间；不创建空任务或伪完成记录。

## 4. L2：持托管锁并派发

按 L1 的托管执行快照顺序循环。队列和队列项的新增、删除、重排不改变本轮清单；不重新展开原队列，不锁队列。队列项的星期限制由 L2 根据保留的执行条件判断跳过。

队列附加脚本直接复用基础执行器并沿主任务 await 链取消，不创建另一层执行框架；普通执行失败提示后继续。取消时不再启动后续附加脚本或安排队列结束动作。完成事件在后置脚本及必要收尾完成后发布；发布前将结束动作及延时交给 Power，非强制设置，不覆盖已有意图或电源任务。执行结束后的触发和退出衔接见“完成后电源”。

每项顺序为：

```text
重新解析托管并先确认存在、身份有效
→ 尝试取得托管本体非级联 X 锁
→ 未取得则等待；下一次尝试前重新解析并确认存在
→ 保存锁凭证，核对当前配置仍是刚才确认的对象
→ 将已锁托管配置、当前运行节点和上下文传给 L3
→ 等待下层完整执行和收尾
→ L2 解锁并清除当前凭证
```

存在性检查必须在尝试取锁之前；不能先对旧对象取锁、再第一次查询它是否存在。取锁后的身份核对只处理解析到取锁之间的竞态。等待期间删除或替换，保留对应运行节点记录异常并结束该分支，不无限等待、不重建配置、不换对象执行。

托管锁凭证始终由 L2 保留，下层不重复取锁。正常路径解锁，异常和取消时 `final_task` 对仍持有的当前凭证兜底；已释放则不重复释放。锁持有到全部用户及托管级恢复完成。

## 5. L3：托管准备、持用户锁并派发

使用 L2 传入的已锁托管配置执行检查和准备。游戏接入位置在取得托管锁之后、派发用户之前；订阅真实游戏／设备资源，恢复后由对应所有者释放，不引入空成功实现。

按本轮用户快照顺序循环，对每个真实用户：

```text
从当前托管配置中解析用户，先确认存在、归属和身份
→ 尝试取得用户级联 X 锁
→ 未取得则等待；每次重试先重新解析并确认存在
→ L3 保存凭证，核对对象身份
→ 在锁内读取当前字段，判断自动代理启用状态与剩余天数
→ 将已锁用户配置、运行节点和当前节点参数传给 L4
→ 等待 L4 完整执行和恢复
→ L3 解锁并清除当前凭证
```

配置失效记异常，禁用或剩余天数不足记跳过，继续其他用户。预先做的准入判断不能替代取得锁后的最新判断。用户集合本身不加锁，未占用用户仍可修改或删除，当前用户冲突操作由后端拒绝。

`default` 没有用户配置，不申请用户锁，直接在 L2 持有的托管锁保护下派发共享目标。托管级恢复在 L2 解锁前完成。L3 的 `final_task` 对仍持有的用户凭证兜底，不能替 L2 释放托管锁。

## 6. L4：执行与结果

接收已解析、已加锁的配置和上下文，执行检查、准备、实际模式操作、结果记录与恢复。L4 不重新选择目标、不重复申请用户锁，也不释放上层凭证。必须明确给出实际结果，不把空执行或没有插件能力当成成功。

实际脚本执行和成败判定复用脚本公开入口，遵守专项黑箱边界。MAS 负责账号、编排、资源生命周期等自身领域，不推断上游私有配置或内部运行状态。

## 7. 生命周期、取消与提交

采用来源 TaskBase 的最小执行契约：`main_task`、`final_task`、`on_crash`、顶层启动停止和完成通知。业务超时、维护检查、通知、历史与背景工作归对应层或已有基础库，不扩充基类职责。

- 下层一律 `await self.spawn(child)`，其语义为同一个 asyncio Task 内直接等待 `child.run()`，覆盖子层完整生命周期。不要把执行树下层改成 detached Task。
- 取消沿直接 await 链传播；顶层 `stop()` 请求取消并等待收尾。启动前取消也补齐收尾，重复取消不截断唯一 finalizer。`on_crash` 自身须保护异常。
- `ended` 在顶层完整收尾后清理运行登记，`accomplish` 随后完成，避免已报告结束却仍占用运行表的窗口。
- 上层持有下层资源：L4 恢复完成后 L3 解用户锁，L3 托管恢复完成后 L2 解托管锁。正常路径与 final_task 兜底按实际持有状态处理，不重复解锁。
- 主流程在产生暂存的同一 Task 内完成必要 commit。独立 finalizer 只提交自己的暂存；不能用它代交主流程修改。直接 await 不等于把长期执行放进一个长配置事务。
- 使用热态字段和公开集合操作，只提交实际修改，不整份回写启动快照。恢复或提交失败也通过 finally 释放凭证，终态在必要收尾完成后发布。
- 直接取消与超时取消都属于协作机制；等待超时不是任务已停止。外部进程、设备和线程的实际停止由其能力所有者处理，不能用超时或丢弃引用代替。

## 8. 推送、日志与可写性

查询、重连快照、WS 和前端展示从同一运行树读取，保留统一信封。直接订阅 Config 信号，在事务内导出推送；接受过程态通知，不擅自改为提交后通知、后台发布队列或状态镜像。过程通知不是事务已提交的保证。

日志是按行保存、正常以换行结尾的字符串列表。运行树、写入端及查询导出不裁剪日志正文；旧托管流程日志同样保留完整内容。移除信息树的 first_line 及相关写入，完整正文从第 1 行开始。运行节点 ID 与业务配置 ID 在展示、历史和本机关联中明确区分。

信息与日志分类订阅：正文变化只进入日志通道，状态和结构变化发送不含正文的 WS 信息树；完成树也不重复正文。元数据投影先排除正文再导出，不能先复制并序列化全部日志再丢弃。HTTP 查询、重连与终态留存继续使用完整树，不能套用这个投影。

日志恢复旧增量协议：每任务独立递增 seq，append 决定追加或替换，firstLine 表示替换包的起始行号。首次、重置、切换来源或追加过大时替换；通常只发送新增片段，正文未变不重复发送。传输替换包及前端显示缓冲可以各自限长，不反向裁剪信息树；首行号在传输／显示裁剪时计算。具体预算现场查询源码，不维护常量副本。必要的日志游标由任务根 PrivateAttr 保存，只服务于传输，不进入公开字段、持久化或配置回滚；任务结束清理。信息与日志接收者直接声明在任务模型定义之后，随模型导入安装配置类订阅；不挪到管理器模块、不在管理器构造或任务启动路径绑定。接收者按实际运行登记筛选事件，未受理或已注销的树不发布。复用配置事务入口的串行语义，不增加管理器日志表或推送锁。状态与日志推送属于任务模型业务，接收者直接生成投影／增量并调用既有 WS 发送能力，不再注入或保存发送回调。发送所需的 TaskManager、Publisher 和传输契约在回调执行时解析，避免 WS 契约与任务模型循环导入；仅导入模型仍不初始化宿主，也不要求先启动 WS 服务端监听。普通按行日志用列表长度及切片计算新增内容，基线只浅拷贝行引用，不缓存整份拼接正文；事件旧值与已发基线不符时替换恢复。

前端缺少基线或序号不连续时丢弃增量并拉完整快照。快照携带完整日志及匹配的 logSeq/logFirstLine；若事务过程态游标与当前正文不一致，不提供可追加序号。WS 元数据不得覆盖或清空独立日志缓冲，迟到快照不得覆盖更新的日志序号。信号仍在原事务协程中执行，不引入发布后台队列或修改配置事务语义。

字段、集合操作等业务可写性由模型订阅信号拒绝并上抛，配置事务负责回退；不要在配置服务 CRUD 中重复堆积开关判断。界面禁用反映业务模型，不能替代后端拒绝。

真实类型问题修复，兼容别名或动态派生契约的抑制限于相应位置并注明原因。模式、节点、集合和参数使用准确类型，不能以 Any 掩盖身份或锁职责错误。

卫星等主页配置展示由 Config 查询现存配置关系及持久化历史，不能为了展示排期、最近失败而把配置聚合或会话结果缓存加入 TaskManager。运行快照只包含实际任务，调度面板仍消费运行树；按实际任务暂停动效的性能策略属于独立消费者。历史关联沿真实存储能力处理，无法可靠区分的记录保持未知，不用运行缓存补造结果。配置／历史查询不依赖 task.* 推送，不能沿用 WS 连通时停止查询的旧兜底条件。

## 9. 启动、定时与循环

队列 Info 定义独立触发设置：启动策略是关闭／每次启动／每天首次启动，定时与循环各有 bool 开关。关闭定时或循环时，其对应模块配置项禁用，后端约束和前端展示保持一致。

循环配置是固定的一组间隔、上次循环时间、虚拟下次运行时间和重置触发器；重置将循环基准设为当前时间。另保留隐藏的通用上次运行时间及启动运行日期。运行记录由 L1 在成功创建时提交，重置触发器仍由其自身模型动作执行。

- timer 统一负责三种原因的到期判定；启动检查作为全局每次软件启动仅运行一次的异步流程，不保留另一套启动业务。
- 业务时间、星期与“每天首次”使用本机时区判定，存储序列化遵守配置框架统一规则。
- 到期直接提交普通任务，不判断队列空闲，不等待开始或完成；同时运行的互斥等待由 L2/L3 等调度执行层承担。
- 保留适合此结构的定时补跑、到期去重。启动、定时与循环各自提交单一原因的任务，不相互合并，一类触发失败不阻断其余触发路径；不要扩展成循环执行会话。
- 队列项自己的星期周期保留，由 L2 跳过，不因队列级循环间隔而删除。
- 停止当前轮不关闭排期。删除、修改后的配置按下次检查生效；已删除对象不回写恢复。任务结束不重置循环时间、不启动下一轮、不维护循环会话状态。

## 10. 兼容、扩展与背景任务

L2 的 ScriptExpander 是兼容分叉：真实插件能力进入严格 L3/L4；旧 task 直接进入原 manager，用户展开、执行和专项收尾仍由 manager 完成，不把完整 manager 包成新的单用户 L4，也不在上层重复展开或重复控制其生命周期。

本次迁移中“旧版”兼容基线指 v5.4.0 的专项任务语义；实际存量 manager 可能已有后续增强，接入时现场核对并保留其能力，不能把当前 dev 的临时结构误称为已确认的新框架。

新路径遵守 L2/L3 的锁所有权。接旧 manager 时现场确认其取锁方式，选择唯一持锁／释放方并保留必要递归保护；不能让上层非级联锁与旧 manager 的另一把互相阻塞的锁未经适配便叠加。旧平铺属性、重建用户、粗粒度锁及类型抑制是带移除方向的兼容例外，不能推广到插件路径。

插件模式、执行能力和配置访问在托管类型解析处接入真实声明；游戏订阅在托管锁内、用户执行前接入，释放在对应恢复后、解锁前接入。缺失模块仅留有明确顺序和责任的注释，不创建占位 API、假注册表、空成功能力。既有设备能力继续由其实际 owner 管理；游戏管理最终迁移不另建旧新两套游戏兼容体系。

文件目录访问依附对应配置的互斥和持锁生命周期，不另建统一目录预约模块。队列解析和建树逻辑留在 L1 编排位置，不拆没有真实复用的 builder／loader。简单一次性操作和脚本调用直接复用基础能力，避免为分支功能扩充调度主干。

背景子任务是独立应用能力，由 BackgroundTaskManager 的任务组持有，不能冒充执行树子任务。任务组可申请注销，分别限制执行与记录容量，保留或一次性提取结果，提供直接取消、执行超时取消、等待期限和未提取结果过期丢弃；超时或取消未真正退出前继续持有引用。等待方取消不自动取消背景执行。业务文件清理由历史／回放等实际 owner 负责，不因丢弃结果引用而遗失清理职责。

### 完成后电源

Power 是应用级单例，拥有待执行信号、延时和唯一电源 Task；这些运行状态不放在 Config。TaskManager 在执行器完整结束、注销运行登记之后发布结束信号；Power 订阅该信号，每次判断是否适合触发。仍有运行或创建、正在停止全部、结束原因是取消或没有电源意图时，直接跳过，不创建等待空闲的任务。后续任务结束时可再次判定。

电源动作统一使用电源工具契约中的 PowerSignal 字符串枚举，配置字段、任务快照、API／WS 和执行传参共享该类型，外部协议与持久化保持原字符串值，前端复用生成的枚举。

Power 的信号设置接收显式 overwrite 参数：API 强制覆盖尚未消费的意图；队列交接非强制，只填补空意图。power_task 是唯一的电源占用标识，倒计时创建时登记，完成、失败或取消后清除；不增加执行中／已交接标志、占用影子字段或取消锁。已有电源任务不覆盖，另有取消入口。delay 是唯一倒计时秒数，默认 60，不叠加静默延时或另一段固定倒计时；队列按分钟配置，默认及最小值均为 1，填写多少分钟就倒计时多少分钟，旧配置的 0 迁为 1。显式取消等待该 Task 退出，不能撤回已发出的系统动作。

条件满足就开始倒计时，不等待 BackgroundTaskManager，也不消费其结果，不新增后台受理屏障。倒计时开始后，普通调度与旧维护的新建入口读取同一个 power_task 并直接结束请求；Power 不再检查运行任务、临近排期或提前／补跑窗口，不因这些条件撤销电源动作，也不向退出流程交接未来排期。MainTimer 自身的系统唤醒注册与启动来源识别保留。电源倒计时由 Power 持有，退出流程由 ShutdownCoordinator 独立持有。

关机、重启及注销成功发出后，Power 请求程序退出，沿宿主既有幂等 teardown 停止调度、timer 和后台任务并释放资源；退出／重启主程序直接进入该流程。睡眠、休眠是可恢复状态，不请求应用退出、不触发 teardown；原生动作返回后清除电源任务占用，保留调度和后台任务继续运行。原生调用失败不请求程序退出。当前明确接受先系统动作、后应用退出的顺序；立即关机、强制操作可能先终止进程，无法保证收尾及时完成，只留注释，后续另行优化，不能报告为已解决。

通用进程操作和平台电源／自启动原语归 utils，调用方传入对象与必要参数；utils 不反向读取 Config 或其他业务单例。旧专项维护适配与未来维护任务标准方案均整体推迟至插件迁移时讨论，本轮电源交接不代表其查询、取消或停写能力已经适配。维护操作归属与身份、查询／日志接口、结果消费方、取消及停写未确认后的处理尚未定案；此前插件业务服务持有后台任务组等建议仅为草案，不能作为已确认规范或据此新增接线。现有 BackgroundTaskManager 与已确认的电源／退出机制继续保留。

历史、通知、恢复、统计和资源释放各自明确唯一 owner，避免旧 manager 与新层级重复执行或重复通知。统计复用实际业务终态的已有观察入口，不在每层重复上报；匿名属性不携带业务 UUID、路径、账号或日志。

## 11. 验证重点

按变更选取真实公共入口的最小回归，必要时覆盖：

- 自动代理空选择、直接托管、队列项解析、顺序子序列、超额重复，以及配置／查看唯一目标和 default。
- 无队列运行层、独立运行 UUID、重复托管独立结果、全部校验后发布，失效选择不遗留部分任务或触发时间。
- 建树后删改队列不改本轮清单，等待前／等待期间删除托管或用户不挂死，后续用户修改被热态读取。
- L2 托管锁与 L3 用户锁的唯一所有权，锁前存在性，取得后身份及准入复核，当前配置拒绝冲突写、其他用户可改。
- 启动前取消、等锁取消、执行中取消、重复停止、停止全部与并发创建，以及下层恢复／提交失败后释放全部凭证。
- 同 Task 提交、不覆写用户修改、重连读取同一树、事务内过程通知与终态区分，兼容路径不重复历史／报告／统计。
- 独立触发与单一原因记账、创建失败不记时、已创建后停止仍保留记录、重置／删除不被旧读值覆盖，循环不依赖执行完成或空闲。

说明实际验证范围。测试通过不代表未迁入的插件、游戏管理或真实设备流程已经实现；修改本 Skill 本身也不授权顺带修改这些模块。
