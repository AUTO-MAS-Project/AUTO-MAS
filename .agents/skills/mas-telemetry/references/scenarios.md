# 场景决策与已验证反例

## 先判断是否需要新埋点

| 变更 | 默认处理 |
| --- | --- |
| 新的用户操作、可观察结果或独立引导阶段 | 同步接入，先复用现有事件族/操作类别 |
| 新增业务页面或入口 | 检查页面白名单、来源类别及操作是否复用现有观察 |
| 同一保存操作增加一个 UI 入口 | 共用已有持久化观察，不在 UI 再发一次保存成功 |
| 改超时、取消、异常、部分完成、重试 | 即使没有新按钮，也要复核现有结果分类和去重 |
| 纯文案、样式、静态图标、内部命名调整 | 不新增事件；说明继续复用现有覆盖即可 |
| 打开页面的自动查询、快照恢复、心跳、轮询或自动退避 | 默认不新增逐次事件；有明确分析需求时按既有摘要/首批边界处理 |
| 新敏感输入，如账号、路径、命令、日志、正则 | 不上传输入；需要评估操作时只记录安全类别和结果 |
| 没有可确认最终结果的上游操作 | 只记录现有受理/观察信号，不读取私有状态来补完成 |
| 只读审查或调研 | 检查并报告差距，不因本 Skill 自动改代码或发布评论 |

## 活动首载与手动刷新

已发生过的错误：首载还在飞，刷新被 busy 跳过，但观察层读取当前 `whenLoaded()`，把首载同一结果再记成多条 manual success。

当前约定：`useHomeActivitySource.whenLoaded()` 对同一次实际加载返回稳定 Promise；跳过请求不替换它。多个来源使用 `combineActivityLoads`，只有子批次变化才创建新的组合 Promise。观察层在操作前后比较批次，未产生新批次就不消费旧结果。

因此扩展活动来源时必须保留这一约定。不要在每次 getter 里直接重新 `Promise.all(...).then(...)`，否则即使没有新请求，身份也会变化。多服务器结果按一个游戏卡汇总为 success/partial/failure/unknown；自动定时刷新和退避不扩大事件数量。

## 用户目标与脚本类别

OK-WW 更新的任务目标是用户 UID，但类型缓存按脚本 UID 登记。把任务 target 当缓存键会令已知 Okww 变成 unknown。

当前 `requestScriptUpdateStart(targetId, scriptType)` 要求入口明确传固定脚本类型；保留原来的用户目标。其他脚本/用户/队列混合入口也要分开传业务标识和分析类别。新专项需检查类型归一化及 flavor 映射，不为统计改请求目标或额外查配置。

## 已持久化后发生附带失败

- 计划基础创建成功，随后默认名称保存失败：创建成功和 rename 失败分别记，不能把创建改成失败。
- 主题/桌宠资源已安装，保存当前选择失败：整体为 partial；不宣称资源没安装，也不提示全部成功。
- 扫码或 QQ 连接/解绑确认后，后续开关保存失败：绑定结果先确认，开关保存单独统计。
- API 确认更新检查/保存结果后，音效或页面回读失败：不反转已确认结果。

对应实际代码优先参考 `usePlanApi.ts`、`useAppearanceSettings.ts`、`useOnlineAppearance.ts`、`useClawBinding.ts`、`useQrLogin.ts`。它们的具体信号不同，不能机械复制 catch 范围。

## 异步轮询和会话替换

扫码创建前保存 context 和当前尝试；当前会话的确认、过期、失败、取消、替换、卸载只产生一个终态。不按每次轮询计数。旧二维码、旧解绑或旧登录响应不能结束新的尝试，已绑定状态恢复也不是新登录。

原生配置的 open/view/save/close/timeout/discard 来自实际操作原因；失败后是否保留窗口不是操作来源。主列表、独立编辑器和自动超时均需核对，不能仅埋一个按钮。没有上游最终保存信号时保留 accepted，不推测保存完成。

## 无操作 ID 的后台完成

模拟器某设备旧操作超过界面等待窗口后仍可能完成。若又发同设备同操作，旧完成帧不能记给新操作。网络请求失败也不代表后台没受理。

沿用现有未决/歧义键和容量上限；不要仅因超时删除旧关联，再把下一帧配给最新请求。真正有可靠 operation ID 时可在本机有界关联，但不上传 ID，重连快照不重演历史操作。

## 任务、队列和逐脚本逐轮

任务启动受理、整任务结束和逐脚本逐轮是不同层级。混合队列、循环每轮的结果复用 MAS 已有领域状态，不从脚本日志或私有配置推断。缺少开始或关联不明的终态不补造；部分帧被丢弃要承认观察样本不全。

“立即运行一次”如果只是修改下次调度时间，只记录调度写入；真正任务创建仍由共用任务入口记录。指定脚本继续和限定用户范围不必然是“失败重试”，只归类已知请求范围。

## Runtime、更新和退出

- Runtime 接管的 pip/Git 不等于各自实际安装成功。完整 bootstrap 按真实命令返回，不从 completed 进度帧补造逐段成功。
- 失败页手动更新 Runtime 与初始化前对齐是不同实际入口，都需要观察真实返回，不能让后续 bootstrap 的校验替代刚才更新的失败和耗时。
- 安装 HTTP 接口仅创建异步任务即返回，code=200 为 accepted；不表示安装器已启动或版本已切换。
- 下载开始、重试、换源和终态沿用一次尝试所有者；首帧/HTTP/WS 竞争不得重复，恢复快照不当新下载。尚未知来源时保留 unknown。
- 后端主动更新的预期断线不能记作故障事故；恢复原因与结果在已有协调层归类。
- 退出统计只能尽力发送，不延长关闭期限、不 flush、不把缺少退出事件解释为崩溃。

## 专项与新字段

专项统计属于 MAS 的配置、引导、调度与管理领域。上游执行成败、任务语义和游戏内状态仍由上游公开信号负责；不得反推私有格式。

新增专项除类型/白名单外，要查创建、现有独立保存、原生会话、导入、更新和实际存在的专属工具。General 模板上传/日志规则调试等子入口若未接，应如实列为未覆盖；不能用“通用保存已接”证明每个子工具都覆盖。

页面导航只在成功进入白名单后记录，来源也只取有限类别；日志、检索条件、route params/query 均不外发。设置、主题、语言、桌宠和性能档位只在显式修改并按实际保存结果记录；启动回填、迁移和清理失效选择不算用户采用。
