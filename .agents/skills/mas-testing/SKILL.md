# MAS 测试撰写规范

测试应从真实使用场景或公共调用契约出发，验证实际可能发生且值得防范的问题。长期测试应替代程序员反复逐项校对；持续节省的验证成本和避免的错误损失，应足以抵偿开发、执行、误报与维护成本。

完成标准是受影响行为有适当的验证证据，需要长期守护的问题有收益与成本相称的覆盖。测试数量、覆盖率增长和“每个 Bug 都补一个测试”不作为完成标准。

## 先判断是否值得长期保留

本次验证与测试入库是两个决定。能够复现、稳定重跑或证明修复前失败、修复后通过，只说明这次验证有效，不能单独证明它值得长期维护。扩展已有用例中的断言，也要经过同一判断。

新增长期检查前，说明它防止的实际错误、替代的重复人工校对，以及相对现有覆盖的新增收益。收益不足或缺少依据时，使用本次复现、页面检查或临时探针留下证据，不提交长期用例；无需为不新增测试另造一个较小的测试。

先追踪实际调用链，定位承担该保证的责任边界。共同写入路径、对象标识或前后端字段对应关系的问题，应在负责该关系的边界核对并复用覆盖；不按页面、日期或账号逐项增加“改一个、检查另一个没变”的间接断言来替代它。

多个专项依赖同一方法或共同契约时，在负责它的公共边界集中验证；专项用例只增加真实接入差异的覆盖，不复制同义的更新、恢复或失败处理场景。计划中的公共入口与已有覆盖分开记录，不能把尚未实现的通用测试写成现成替代证据。

MAS 内部功能更新按 [迁移规则](../mas-data-model/SKILL.md#evolution-and-migration)处理。测试评估迁移与迁移后的现行行为，不以长期兼容新旧业务为保留理由；迁移测试同样须通过长期收益判断。

低风险的局部样式、像素对齐和展示文案调整通常以页面核验完成。需要长期守护操作不可达、数据错误等实际故障时，再选择相应的行为测试；不把页面参数组合或当前视觉细节逐项固化为断言。

真实场景可以在公共函数、协议、存储或调度边界复现，不要求所有测试都经过 GUI。低频但会造成数据损坏、泄露或无法恢复的故障也有长期价值，不能只按发生频率或测试形式取舍。

## 先复用，再选择验证方式

先读需求、实际调用者和相关已有检查。比较能发现目标错误的验证方式，计入环境准备、执行时间、稳定性、维护和人工操作成本；用能证明同一契约且总成本最低的检查。

| 改动与已有能力 | 验证选择 |
| --- | --- |
| 已有检查能捕获目标错误 | 直接复用；缺少断言时优先扩展原用例，不另建同义测试 |
| 纯逻辑或稳定公共接口的独立行为 | 使用现有单元、组件或接口测试入口，不按辅助函数逐个铺测试 |
| 跨模块协作或界面到调度的行为 | 选择覆盖这条链路的最小集成检查；浏览器和真实运行按 [mas-e2e](../mas-e2e/SKILL.md)，不能把所有单测升级为 E2E |
| Bug 有确定的复现路径 | 复用已有测试或最小复现命令，对照修复前后的同一场景 |
| 新测试需要大量脆弱 mock、无关夹具或缺失的真实环境 | 先找现有入口或针对性复现命令；说明覆盖缺口，不另造测试框架 |
| 仅文档、格式或生成结果，未改变运行行为 | 使用对应静态检查；生成器逻辑有变化时验证生成契约 |

按目标行为选择验证，不规定统一的测试先行流程。用户明确要求的验证与项目必需检查不能因成本判断省略；无法完成时说明具体阻碍。

## 写测试前先说明边界

新增检查前明确以下依据，用一段说明覆盖相关行为即可，无需为每条测试新增审批或交付表格：

- **可达场景**：用户操作或公共调用入口、前置条件、错误触发方式及可观察后果。先确认流程本身合理且受支持，内部函数能拼出状态不等于真实场景；不以测试固化不合理流程。仅演示内部机制正常工作，不能代替实际故障场景。输入必须能经过实际初始化和校验到达被测边界。外部故障也要说明发生条件，不能绕过上层约束制造生产中不存在的状态。
- **独立预期**：来自需求、公共契约、已核实的正确实例或领域规则。不能运行当前实现后把输出抄成答案，也不能照着实现重写算法来算期望值。尚未形成稳定契约、需开发者持续权衡的策略名单或取值，记录当次判断，不固化为持续门禁；与已确认的安全、数据契约分别判断，不能把现状认定为正确。
- **长期收益**：它能抓住哪个实际错误、替代哪些重复人工校对、为何值得持续维护，现有测试为什么抓不住。已有覆盖足够时复用；参数不同但触发条件、错误与契约相同的用例应合并或省略。

测试沿用生产入口已建立的约束；要验证入口对非法输入的处理，就从该入口注入输入。生产校验与兜底的取舍遵循 [mas-defensive-programming](../mas-defensive-programming/SKILL.md)，不能由绕过初始化的测试替身反向要求生产代码补分支。

测试边界是对外可观察的接口，可以是公共函数、HTTP 接口、组件交互或实际调度入口，不要求所有测试都走完整 GUI。纯逻辑单测必须守护调用方实际依赖的契约；集成行为不能用只测辅助函数代替。

用户已给出的场景和边界直接沿用；只有边界或预期存在会影响验收的歧义时才询问。无需为每条测试重新请求确认。说明测试能证明什么、不能证明什么，再写测试。

## 用执行证据证明结果

Bug 使用相同输入对照修复前后，确认原先因目标错误失败、修复后通过；导入或依赖报错不算复现。实现已写好时可在隔离工作树运行原始基线，保留当前修改。无法运行基线时明确说明，不补写未经执行的结论。

新功能从选定入口验证当前需求中的行为。请求受理、进程创建、mock 被调用或配置值已写入，只能证明那一步；例如任务进入队列不能证明脚本执行成功。

满足受影响契约后停止扩写；补充用例须有不同的可达故障或契约依据，不按函数、分支或参数组合铺满。探索或模糊测试发现的状态先确认属于受支持契约，再作为回归缺陷处理。

## 保持测试独立于实现

编写或审查断言时读 [tests.md](tests.md)；需要隔离外部依赖时再读 [mocking.md](mocking.md)。行为被破坏时测试应失败，内部实现改变而契约不变时测试应继续通过。

- 从公开接口断言输出和可观察副作用。内部调用次数和顺序不作为契约；通知去重、任务重复启动或有明确要求的顺序可以是行为断言。
- 只在系统边界隔离外部依赖，不 mock 被测业务或内部协作来使流程通过。测试数据使用真实保存样本或按公共契约构造的最小夹具，并遵守仓库已有初始化与隔离方式。
- 测试期望必须能独立于实现得到；快照须先核实正确，不能自动接受当前输出来锁定潜在 Bug。

## 降低重复验证成本

优先复用项目的启动入口、配置隔离夹具、种子数据、场景选择、结果采集和清理机制。后端入口与隔离按 [tests/AGENTS.md](../../../tests/AGENTS.md)，前端按 [mas-frontend-standards](../mas-frontend-standards/SKILL.md)，E2E 的启动与证据由 `mas-e2e` 负责，不复制一套命令或另造启动器。

同类验证反复要求人工准备、执行或清理时，在本次授权范围内优先补齐现有工具，使后续可用同一入口重跑。只有确定会复用的工作才提取公共夹具或脚本；不为小改动新增测试依赖、通用框架或只供测试使用的生产接口。自动化须实际运行，不能把新增说明文件当作已减少人工操作。

开发迭代先运行相关检查，完成后执行项目要求的其余检查；不自行增加全量运行、真实账号验收或逐用例确认等门槛。

## 存量与交付

新增前查重，重复时优先复用已有测试。审查存量时同样判断长期收益，具体到用例或断言：记录真实入口、守护的错误、重复或失效的证据及替代验证，再决定删除、合并、保留或待核实。混合用例只清理低价值部分，不连带删除有效的业务覆盖；证据不足时列为待核实，不能只因数量多、运行慢或本次无关就删除。目录与受保护用例见 [tests/AGENTS.md](../../../tests/AGENTS.md)。

交付时按“场景 → 可观察断言 → 执行结果”说明，Bug 附修复前后同一条验证的命令和结果，并写明环境与未覆盖范围。把新增行为证据和相关已有测试分开报告，不以“通过 N 项”作为功能完成或质量提高的依据。
