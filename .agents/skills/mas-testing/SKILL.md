# MAS 测试撰写规范

测试应从真实使用场景或公共调用契约出发，验证实际可能发生且值得防范的问题。长期测试应替代程序员反复逐项校对；持续节省的验证成本和避免的错误损失，应足以抵偿开发、执行、误报与维护成本。

完成标准是受影响行为有适当的验证证据，需要长期守护的问题有收益与成本相称的覆盖。测试数量、覆盖率增长和“每个 Bug 都补一个测试”不作为完成标准。

## 先判断是否值得长期保留

本次验证与测试入库是两个决定。能够复现、稳定重跑或证明修复前失败、修复后通过，只说明这次验证有效，不能单独证明它值得长期维护。扩展已有用例中的断言，也要经过同一判断。

编写、审查和清理测试都按以下顺序判断，先选值得防守的故障，再决定测试形式：

1. **说清防守价值。** 读真实入口和实际调用链，说明用户在什么前提下做什么操作，可能发生什么错误、造成什么可观察损失，以及测试在哪个责任边界用什么断言抓住它。只有内部函数能拼出某种状态，不算可达故障。
2. **核对已有证据。** 读相关测试体和被测调用链，确认现有断言能否抓住同一错误。已有覆盖足够就复用；缺少断言时先评估扩展原场景。共同写入、对象定位或跨专项的共同保证在公共责任边界验证，专项只增加实际接入差异。
3. **决定是否长期入库。** 只有具体故障值得持续防守、现有覆盖抓不住，且节省的人工回归与避免的损失足以抵偿维护成本时，才新增长期检查。新增断言也按同一标准判断。依据不足时用本次复现、页面检查或临时探针留下证据，无需另造较小用例；高损失边界按下文例外处理。
4. **选择强度并执行。** 按下表选能证明目标结果的最低成本验证，实际运行后再报告覆盖。一次真实验收是否需要执行，与其脚本是否值得长期入库分别决定。

计划中的公共入口与已有覆盖分开记录，不能把尚未实现的通用测试写成现成替代证据。

MAS 内部功能更新按 [迁移规则](../mas-data-model/SKILL.md#evolution-and-migration)处理。测试评估迁移与迁移后的现行行为，不以长期兼容新旧业务为保留理由；迁移测试同样须通过长期收益判断。

低风险的局部样式、像素对齐和展示文案调整通常以页面核验完成。需要长期守护操作不可达、数据错误等实际故障时，再选择相应的行为测试；不把页面参数组合或当前视觉细节逐项固化为断言。

真实场景可以在公共函数、协议、存储或调度边界复现，不要求所有测试都经过 GUI。发生频率或测试形式都不能单独决定取舍，高损失边界例外见下节。

### AI 增量测试偏差

生成测试的成本远低于阅读、运行和维护测试的成本，AI 因此容易把“证明当前实现正确”误当成“值得长期守护”。默认不新增长期测试，按上面的工作流举证后再决定。

测试数量、覆盖率、参数数量和“每个函数都有单测”都不能证明质量。
同义输入只保留能区分真实分支或故障结果的最小代表；不得为同一契约
逐页面、逐日期、逐账号或逐参数铺用例。
一个真实故障选择足以证明它且总成本最低的证据。更强场景实际覆盖了同一故障时，合并重复检查；执行链更长或叫作 E2E 本身不代表更强。

AI 生成的测试还要审查是否只证明实现本身：断言内部调用次数或顺序、固定日志文案、私有字段初值、方法转发、样式值或源码片段，通常不应长期保留。测试应让契约变化时失败，让无害重构后继续通过；能证明修复前失败、修复后通过，也不等于值得长期维护。

新增长期用例默认扩展已有测试入口；只有出现新的责任边界或独立用户流程时才新建文件。新增功能、修复 Bug 或增加了生产分支都不自动要求增加测试；不能只因测试是功能的附属品就提交。存量清理按下节的保留举证规则执行，不默认迁移每条旧断言。

数据损坏、泄露、不可恢复、安全边界和真实进程/文件/网络越界属于例外：写明具体损失、可达入口和承担保证的边界；即使低频、运行成本较高或难以完全复现，只要能在该边界稳定验证，也应优先保留，删除前必须有等效或更强的边界证据。不能仅凭文件操作、异常分支或“安全”标签把普通检查列为例外。

## 先复用，再选择验证方式

强度由目标错误需要经过哪些真实依赖才能暴露决定。比较环境准备、执行时间、稳定性、维护和人工操作成本，在满足目标断言的一层停止；每次升级都要说清较低一层会漏掉什么。

| 目标错误与触发条件 | 最小充分验证 | 证据边界 |
| --- | --- | --- |
| 仅文档、格式、文案或低风险外观调整，没有新的行为风险 | 静态检查或本次页面核验 | 不因此新增长期行为测试；生成器行为变化仍需验证生成契约 |
| 错误能在稳定公共函数、接口、协议或隔离存储边界暴露 | 复用相应行为测试，执行真实业务逻辑 | 局部边界足够时不升级 GUI；写盘契约应读取真实隔离文件，不能只断言保存 mock 被调用 |
| 要防的是页面进入或主要入口不可达 | 复用相关 smoke，覆盖实际入口与可见结果 | 本仓库 `@smoke` 只证明基础导航；冷启动、保存、任务成功和故障恢复各需对应场景 |
| 错误依赖界面操作、HTTP/WS 与状态回读之间的协作 | 相关标签的隔离浏览器 E2E，核对受影响操作的最终结果 | 通用 smoke 不够时才扩展目标流程；刷新回读不证明后端重启持久化 |
| 错误取决于进程退出、文件替换、网络传输、权限或原生 IPC | 在承担保证的边界执行真实集成；无法独立证明时才做相关原生端到端验证 | 保留真实边界，隔离账号与用户数据；浏览器替身或进程 mock 不能证明实际退出、回滚或授权有效 |
| 错误取决于真实 Runtime、上游脚本、模拟器或游戏的实际行为 | 作者本机针对性真实验收；脚本、账号与游戏调度走受影响目标的 `@real` E2E | 观察公共结果及必要收尾；请求受理、任务入队或 mock 成功不能替代真实执行结果 |

高损失决定必须守住哪些结果，不机械决定测试层级。例如配置损坏可在真实临时文件上稳定验证，不必启动游戏；验证真实游戏执行结果则不能降为普通 smoke。若判断需要真实验收但环境不可用，明确缺少的目标、前提和证据，不用更多低层测试冒充完成。

浏览器、原生与真实流程的入口、隔离和证据按 [mas-e2e](../mas-e2e/SKILL.md)。真实验收通过不自动产生长期 E2E；需大量脆弱内部 mock 才能通过时，先核对入口和夹具，不另造测试框架。

按目标行为选择验证，不规定统一的测试先行流程。用户明确要求的验证与项目必需检查不能因成本判断省略；无法完成时说明具体阻碍。

## 写测试前先说明边界

新增检查前明确以下依据，用一段说明覆盖相关行为即可，无需为每条测试新增审批或交付表格：

- **可达场景**：用户操作或公共调用入口、前置条件、错误触发方式及可观察后果。先确认流程本身合理且受支持，内部函数能拼出状态不等于真实场景；不以测试固化不合理流程。仅演示内部机制正常工作，不能代替实际故障场景。输入必须能经过实际初始化和校验到达被测边界。外部故障也要说明发生条件，不能绕过上层约束制造生产中不存在的状态。
- **独立预期**：来自需求、公共契约、已核实的正确实例或领域规则。不能运行当前实现后把输出抄成答案，也不能照着实现重写算法来算期望值。尚未形成稳定契约、需开发者持续权衡的策略名单或取值，记录当次判断，不固化为持续门禁；与已确认的安全、数据契约分别判断，不能把现状认定为正确。
- **长期收益**：它能抓住哪个实际错误、替代哪些重复人工校对、为何值得持续维护，现有测试为什么抓不住。已有覆盖足够时复用；参数不同但触发条件、错误与契约相同的用例应合并或省略。

防守理由必须具体到“真实操作 → 可达错误 → 用户损失 → 边界断言 → 现有覆盖缺口”。“保证逻辑正确”“补齐覆盖率”“这个函数刚改过”都不是故障依据；说不清时不新增长期测试。

测试沿用生产入口已建立的约束；要验证入口对非法输入的处理，就从该入口注入输入。生产校验与兜底的取舍遵循 [mas-defensive-programming](../mas-defensive-programming/SKILL.md)，不能由绕过初始化的测试替身反向要求生产代码补分支。

测试边界是对外可观察的接口，可以是公共函数、HTTP 接口、组件交互或实际调度入口，不要求所有测试都走完整 GUI。纯逻辑单测必须守护调用方实际依赖的契约；集成行为不能用只测辅助函数代替。

用户已给出的场景和边界直接沿用；只有边界或预期存在会影响验收的歧义时才询问。无需为每条测试重新请求确认。说明测试能证明什么、不能证明什么，再写测试。

## 用执行证据证明结果

Bug 使用相同输入对照修复前后，确认原先因目标错误失败、修复后通过；导入或依赖报错不算复现。实现已写好时可在隔离工作树运行原始基线，保留当前修改。无法运行基线时明确说明，不补写未经执行的结论。

新功能从选定入口验证当前需求中的行为。请求受理、进程创建、mock 被调用或配置值已写入，只能证明那一步；例如任务进入队列不能证明脚本执行成功。

满足受影响契约后停止扩写；补充用例须有不同的可达故障或契约依据，不按函数、分支或参数组合铺满。探索或模糊测试发现的状态先确认属于受支持契约，再作为回归缺陷处理。

## 保持测试独立于实现

编写或审查断言时读 [tests.md](tests.md)；需要隔离外部依赖时再读 [mocking.md](mocking.md)。行为被破坏时测试应失败，内部实现改变而契约不变时测试应继续通过。

- 从公开接口断言输出和可观察副作用。内部调用次数和顺序不作为契约；通知去重、任务重复启动或有明确要求的顺序可以是行为断言。
- 只在系统边界隔离外部依赖，不 mock 被测业务或内部协作来使流程通过。测试数据使用真实保存样本或按公共契约构造的最小夹具，并遵守仓库已有初始化与隔离方式。
- 测试期望必须能独立于实现得到；快照须先核实正确，不能自动接受当前输出来锁定潜在 Bug。

## 降低重复验证成本

优先复用项目的启动入口、配置隔离夹具、种子数据、场景选择、结果采集和清理机制。后端入口与隔离按 [tests/AGENTS.md](../../../tests/AGENTS.md)，前端按 [mas-frontend-standards](../mas-frontend-standards/SKILL.md)，E2E 的启动与证据由 `mas-e2e` 负责，不复制一套命令或另造启动器。

同类验证反复要求人工准备、执行或清理时，在本次授权范围内优先补齐现有工具，使后续可用同一入口重跑。只有确定会复用的工作才提取公共夹具或脚本；不为小改动新增测试依赖、通用框架或只供测试使用的生产接口。自动化须实际运行，不能把新增说明文件当作已减少人工操作。

开发迭代先运行相关检查，完成后执行项目要求的其余检查；不自行增加全量运行、真实账号验收或逐用例确认等门槛。

## 存量与交付

清理存量沿用上述工作流，逐条读测试体与实际调用链，不按文件、用例名或目录批量判价值。先选择必须防守的故障边界，再判断是否需要独立用例；同一真实操作和生命周期内的重复覆盖可以合并，独立前提或真实边界不能为压数量而硬拼。

保留项承担举证责任：说明真实入口、可观察错误、长期收益及现有断言实际证明的结果；测试已经存在、分支不同、暂未找到替代或“万一用上”都不是保留理由。[明确受保护的用例](../../../tests/AGENTS.md)继续保留；其他测试保留某项保证时，不必沿用原文件或全部旧断言。

未对应具体场景、仅证明当前实现或不再有持续校对收益的测试可以删除，无需先造替代测试或把旧断言逐条迁走。混合用例只留下所选故障所需的断言、参数和夹具，不把无关旧检查拼成巨大场景。数量、覆盖率和diff大小不作为目标；上文高损失保证不能随之丢失。重要缺口单独记录并按长期收益补齐，不能把计划覆盖说成已有证据，也不能以保留一组弱测试代替它。

需要替代覆盖的合并项，先补齐目标场景的有效断言并运行，再删除原测试，分批运行对应范围，同时清理无引用的夹具和导入。无法证明替代覆盖时保留缺口说明，不能声称已经迁移；低价值项不为退出而补造替代场景。

交付时按“场景 → 可观察断言 → 执行结果”说明，Bug 附修复前后同一条验证的命令和结果，并写明环境与未覆盖范围。把新增行为证据和相关已有测试分开报告，不以“通过 N 项”作为功能完成或质量提高的依据。
