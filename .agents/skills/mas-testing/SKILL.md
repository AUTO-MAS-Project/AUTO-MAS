# MAS 测试撰写规范

以最小开发、执行和维护成本证明受影响行为。完成标准是目标行为有执行证据、新增检查能发现独立错误，且复用了适用的已有覆盖。测试数量和覆盖率增长不作为完成标准，也不要求每个函数新增单测。

本 Skill 决定本项目的验证方式与测试范围，TDD 是选定后的实施方法。基于 Matt Pocock 的 `tdd` 改编，见 [来源与许可](CREDITS.md)。

## 先复用，再选择验证方式

先读需求、实际调用者和相关已有检查。比较能发现目标错误的验证方式，计入环境准备、执行时间、稳定性、维护和人工操作成本；用能证明同一契约且总成本最低的检查。

| 改动与已有能力 | 验证选择 |
| --- | --- |
| 已有检查能捕获目标错误 | 直接复用；缺少断言时优先扩展原用例，不另建同义测试 |
| 纯逻辑或稳定公共接口的独立行为 | 使用现有单元、组件或接口测试入口，不按辅助函数逐个铺测试 |
| 跨模块协作或界面到调度的行为 | 选择覆盖这条链路的最小集成检查；浏览器和真实运行按 [mas-e2e](../mas-e2e/SKILL.md)，不能把所有单测升级为 E2E |
| 用户明确要求 TDD，或 Bug 有便宜、确定的自动复现路径 | 使用下文红绿循环，已有测试也可承担复现 |
| 新测试需要大量脆弱 mock、无关夹具或缺失的真实环境 | 先找现有入口或针对性复现命令；报告覆盖缺口，不为满足 TDD 仪式搭建新框架 |
| 仅文档、格式或生成结果，未改变运行行为 | 使用对应静态检查；生成器逻辑有变化时验证生成契约 |

选择验证、是否测试先行和是否长期保留测试是独立决策。可稳定复现的 Bug 尽量保留修复前失败、修复后通过的对照；用户明确要求的验证与项目必需检查不能因成本判断省略。无法完成时说明具体阻碍。

## 写测试前先说明边界

新增检查前明确以下依据，用一段说明覆盖相关行为即可，无需为每条测试新增审批或交付表格：

- **可达场景**：用户操作或公共调用入口、前置条件与触发方式。输入必须能经过实际初始化和校验到达被测边界。外部故障也要说明发生条件，不能绕过上层约束制造生产中不存在的状态。
- **独立预期**：来自需求、公共契约、已核实的正确实例或领域规则。不能运行当前实现后把输出抄成答案，也不能照着实现重写算法来算期望值。预期不明确时先核实，不能把现状认定为正确。
- **新增价值**：它能抓住哪个具体错误，现有测试为什么抓不住。已有覆盖足够时复用；参数不同但触发条件、错误与契约相同的用例应合并或省略。

不绕过已生效的入口校验构造内部非法状态，也不为这类测试给生产代码增加兜底分支。外部输入、存储故障、网络、并发和取消仍按真实契约验证；类型注解本身不是运行时保证。生产校验与错误处理遵循 [mas-code-standards](../mas-code-standards/SKILL.md)。

测试边界是对外可观察的接口，可以是公共函数、HTTP 接口、组件交互或实际调度入口，不要求所有测试都走完整 GUI。纯逻辑单测必须守护调用方实际依赖的契约；集成行为不能用只测辅助函数代替。

用户已给出的场景和边界直接沿用；只有边界或预期存在会影响验收的歧义时才询问。无需为每条测试重新请求确认。说明测试能证明什么、不能证明什么，再写测试。

## 选用 TDD 时，一次走通一个红绿循环

1. **Bug 先复现**：让同一测试与输入在修复前因目标行为错误而失败，再在修复后通过。导入、依赖或测试代码本身报错不算复现；必要时用隔离工作树对照，保留已有修改。实现已经写好时也要补跑原始基线，不能声称先红后绿而没有执行。
2. **新功能验证最短链路**：从选定公开入口写一条失败的行为测试，再做使其通过的最小实现。每轮只补当前需求中的下一个独立行为，避免先铺整批猜想用例；未选择 TDD 时也须执行目标行为检查。
3. **验证到结果**：断言用户或调用方关心的结果。请求受理、进程创建、mock 被调用或配置值已写入，只能证明那一步，不能冒充完整功能已经跑通。
4. **满足范围即停止扩写**：补充用例须有不同的可达故障或契约依据；不为凑数量、覆盖每个分支或枚举参数组合制造场景。仍需运行项目要求的相关已有检查。

无法执行基线、缺少真实环境或只能做静态分析时，报告具体缺口和替代验证，不宣称完成红绿验证。探索或模糊测试发现的状态须先确认属于受支持契约，再作为回归缺陷处理。

## 保持测试独立于实现

编写或审查断言时读 [tests.md](tests.md)；需要隔离外部依赖时再读 [mocking.md](mocking.md)。行为被破坏时测试应失败，内部实现改变而契约不变时测试应继续通过。

- 从公开接口断言输出和可观察副作用。内部调用次数和顺序不作为契约；外部重复扣款、消息次数或有明确要求的顺序可以是行为断言。
- 只在系统边界隔离外部依赖，不 mock 被测业务或内部协作来使流程通过。测试数据使用真实保存样本或按公共契约构造的最小夹具，并遵守仓库已有初始化与隔离方式。
- 测试期望必须能独立于实现得到；快照须先核实正确，不能自动接受当前输出来锁定潜在 Bug。

## 降低重复验证成本

优先复用项目的启动入口、配置隔离夹具、种子数据、场景选择、结果采集和清理机制。后端入口与隔离按 [tests/AGENTS.md](../../../tests/AGENTS.md)，前端按 [mas-frontend-standards](../mas-frontend-standards/SKILL.md)，E2E 的启动与证据由 `mas-e2e` 负责，不复制一套命令或另造启动器。

同类验证反复要求人工准备、执行或清理时，在本次授权范围内优先补齐现有工具，使后续可用同一入口重跑。只有确定会复用的工作才提取公共夹具或脚本；不为小改动新增测试依赖、通用框架或只供测试使用的生产接口。自动化须实际运行，不能把新增说明文件当作已减少人工操作。

开发迭代先运行相关检查，完成后执行项目要求的其余检查；不自行增加全量运行、真实账号验收或逐用例确认等门槛。

## 存量与交付

新增前查重，重复时优先扩展或替换已有测试。清理存量时按它守护的行为和替代证据判断，不能只因数量多、运行慢或本次无关就删除；保留和删除规则见 [tests/AGENTS.md](../../../tests/AGENTS.md)。

交付时按“场景 → 可观察断言 → 执行结果”说明，Bug 附修复前后同一条验证的命令和结果，并写明环境与未覆盖范围。把新增行为证据和相关已有测试分开报告，不以“通过 N 项”作为功能完成或质量提高的依据。
