# 测试隔离与 mock

隔离会影响重复性或产生外部副作用的边界，被测业务仍执行真实逻辑。边界由职责决定，既可能是外部 API，也可能是项目自己的进程、传输或存储适配器；不以模块归属判断是否允许 mock。

## 优先复用现有隔离

- 使用已有临时目录、配置根、测试数据库、时钟与随机数控制。后端配置激活与路径隔离见 [tests/AGENTS.md](../../../tests/AGENTS.md)。
- 网络、进程、系统能力等不适合真实执行时，替换现有边界入口；响应必须符合已核实的公共契约，不能为让流程通过编造状态。
- 补丁指向被测调用方实际查找的符号，及时恢复修改；不要全局替换内部业务模块，使多个用例互相污染。
- 不 mock 正在验证的业务判断、校验器或事务逻辑。需要大量内部 mock 才能通过时，先检查入口是否选错或已有夹具是否可复用。

例如验证通知重试时，只在传输边界注入超时，被测重试与结果汇总保持真实；验证任务配置时优先用真实配置类及已有激活夹具，不能用缺字段的临时对象制造额外兜底需求。

## 只改变必要的生产结构

复用现有依赖传递与适配边界。仅当真实职责混杂或重复依赖管理已影响业务维护时才调整生产结构；测试不方便本身不足以引入新服务、接口、工厂或一套依赖注入框架。

前端生成 API 与 Electron IPC 的隔离按 [mas-frontend-standards](../mas-frontend-standards/SKILL.md)，真实脚本与账号验证按 [mas-e2e](../mas-e2e/SKILL.md)。边界 mock 通过只能证明 MAS 对该契约的处理，不能据此宣称真实网络、游戏或模拟器流程成功。
