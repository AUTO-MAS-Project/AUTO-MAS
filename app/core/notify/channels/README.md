# 内置通知渠道

本目录只容纳随应用 Git 工作树交付的可信代码，不加载用户目录或外部插件。
进程内模块没有安全沙箱；这里不提供安装、热加载或卸载能力。

新增渠道时创建 `<id>/manifest.json`、`<id>/__init__.py` 及传输实现：

```json
{
  "interface_version": 1,
  "id": "example",
  "entrypoint": "app.core.notify.channels.example:register",
  "requires": []
}
```

`requires` 为必需的第三方顶层模块名。发现只读取清单；注册阶段显式调用
`register() -> NotifyChannel`，完整校验后登记。入口包及声明应仅依赖标准库、
通知契约和本包代码，外部传输库通过宿主注入，便于缺依赖时仍保留目标和失败记录。
禁止在导入、注册或发送器构造时联网、发送、启动任务或修改全局注册表。

声明中同时提供稳定 ID、本地化键、顺序、目标构造器、单次发送适配器与
发送器工厂，以及有连接状态时的可选启停入口。目录按 `(order, key)` 排序，
重复 ID 不覆盖；坏声明隔离并诊断。
缺依赖的有效声明保持可见，但不绑定发送器，已启用目标会明确发送失败。
入口或清单损坏、无法取得有效声明时隔离该包，其他渠道继续使用。
宿主把“通知渠道目录未确认”快照带入结果，不能将未知渠道的缺席当作全部送达；
不为此伪造目标、递增投递次数或绕过已送达 ID 去重。由于无法从损坏声明判断
启用状态和作用域，即使尚未启用的坏包也会报告目录未确认，但绝不自动发送。

目标构造器只读取宿主的 `ChannelConfig` 视图。必须依据现有显式启用配置构造
目标，不能因发现或注册而启用；`enable_field` 是渠道开关，Webhook 等按目标
启用的渠道在构造器中检查每个目标。目标 ID 与名称分离，名称相同也保留独立 ID。
地址、密钥、模板、方法及请求头在本次目标创建时固定；重试不重新枚举目标。
内容能力由目标快照提供，宿主按该快照渲染。

管理器在首次使用渠道时准备内部 `ChannelDependencies`，并为每个
渠道创建一个实例。`ChannelDependencies` 只留在注册装配边界，工厂为实例构造
邮件、HTTP、WebSocket、系统提示、Koishi 或 QQ 会话的窄依赖对象。发送器不能
取得其它传输工厂。配置视图沿用现有
字段、校验、加密和保存流程，不迁移配置。每个发送器执行一次发送；`None`/`True` 表示成功，`False`
表示失败，普通异常及取消向上传播。宿主负责渲染、重试、汇总与业务收尾。
超时无法证明消息未送达，不承诺 exactly-once。默认重试次数不变；明确的配置
错误和不可重试的协议拒绝提前结束，未知错误仍沿用重试上限。

QQ 的扫码、凭据、网关和发送使用同一个已装配实例；原扫码 API 直接访问该实例，
路由和响应保持不变。Koishi 实例持有自己的连接管理器和认证、命令消息处理，
公共 WebSocket 工具不读取配置或识别业务消息类型。
主定时器启动后，宿主按 `lifecycle_order` 调用启停入口；QQ 先于 Koishi 恢复连接。
单个渠道启动失败不影响其他渠道。退出先结束通知任务所有者，再逆序停止渠道。
HTTP/SMTP 继续使用单次上下文，不增加连接池、队列或后台运行机制。
业务系统提示使用全局 `Notify.send_notice()`；Webhook 草稿测试使用
`Notify.test_webhook()`，禁用草稿仍可测试。两者直接使用已装配渠道的真实能力，
旧 `Notify.push_plyer` 和 `Notify.WebhookPush` 转发已退役，普通禁用目标仍跳过。
Webhook 传输只接受准备好的快照，不再读取配置对象；正式目标和草稿测试各自在入口固定输入。

目标声明是否为本地提示，以及业务请求紧凑摘要时采用的策略；编排层按目标声明
处理，不根据具体渠道 ID 调整内容。统一投递协议只提供 `send_channel`，渠道
内部的协议方法不进入公共发送面。

设置 API 使用显式展示字段白名单，不能直接序列化完整声明、工厂、依赖或目标。
现有表单和保存 API 保持不变；新增配置能力仍需正常的配置、API 与表单开发。
运行时直接使用注册表的渠道声明；设置目录额外加入通知策略控件，策略不参与投递。

正式产物由 Runtime 使用完整 Git 工作树，CI 验证包也预置精确提交的浅克隆；
清单和动态入口均随仓库交付，无需另加中央渠道名单或打包包含名单。

## 单次通知的准备与投递

```text
core.notify 创建全局 Notify = NotificationManager()
  -> 业务 / 任务报告协调器直接使用 core.Notify
  -> notify.manager.NotificationManager：按全局/用户范围读取配置、逐渠道准备目标
  -> models.notification_channel：NotifyTarget + DeliveryChannel + ChannelTarget
  -> notify.dispatch：显式 Notifier、渲染、重试、并发与结果
  -> notify.transport：选择已装配会话或本次无会话发送器
  -> 渠道传输
  -> DispatchResult 返回业务所有者
```

投递服务不导入 core、全局配置或通知单例，发送器和渲染器必须显式传入。
业务使用 `from app.core import Notify` 取得全局实例。管理器直接读取 Config，
API 不再通过 Depends 或 app.state 取实例，定时器、日历和任务不再绑定通知能力。
渠道内部仍保留协议适配和固定传输快照，避免任务结束后配置变化影响已准备的通知。

manager 直接向通知管理器提交强类型代理结果。简单统计共用 `notify.task_content` 的两种
正文构造，复杂统计由 BetterGI、MAA、MaaEnd、Whimbox 和 MaaFW 的纯内容适配提供。
这些适配只生成正文、模板与图片声明，不选择目标、不调用发送服务或持有渠道连接。
M9A 统计随 MaaFW 使用 `MaaFW_statistics.html`，旧 `m9a_statistics.html` 已退役。
结果和统计邮件各自共享相同的 CSS 片段，渲染后仍为内联样式；专项正文独立保留。
社区通知的直接生成与预准备路径共用正文和图片生成实现，仍按目标能力惰性计算。
渠道目录可以缓存不可变声明，发送器、渲染器和待投递状态则由全局管理器持有。

通知渠道仍在后台可选初始化步骤启动。退出先停止入口和业务任务，再由
`RuntimeTasks.shutdown()` 回收已托管任务，随后关闭服务的渲染器、渠道与配置订阅，
最后统一保存配置；停用未来某个插件不应关闭应用共享的通知资源。
`DeliveryChannel` 只保留稳定 key 和发送适配器，投递流程不携带完整渠道声明、
表单元数据、目标构造器、传输工厂或启停入口。

目标构造逐渠道隔离异常；失败记入 `preparation_failures`。它与目录错误一起组成
`NotifyTarget.unresolved`，不伪造实际投递次数。即使已知目标全部成功或被跳过，
未解析目标也继续出现在结果中；日历不能据此完成提醒，任务报告不能消费签到摘要。
解析异常只记录异常类型，不输出可能包含凭据的原文。

`DispatchResult.failures` 为每项失败保留目标 ID（已解析时）、阶段、类别、可重试性、
实际发送次数和异常类型；`failed_ids` 与展示名称分开，目录和准备失败没有伪造 ID。
`failed` 等历史展示字段继续可用。协议适配层通过 `NotificationDeliveryError` 声明
可重试性，执行器不解析响应文案；HTTP 限流、服务异常和永久拒绝分别处理。

### 按需内容与降级

`NotifyPayload` 的 HTML、Markdown 和图片可以使用 `DeferredContent`。目标选择该
表达时才生成，同一通知缓存生成成功或失败的结果；纯文本、紧凑摘要目标无需读取
模板、字体或图片环境。模板普通数据容器在入口取快照；不透明扩展沿用原对象的
展示语义，不调用其复制钩子。快照准备失败也只影响该可选表达。
可选正文生成失败时按目标的格式顺序选择下一种表达，图片失败保留文字；发送重试
始终复用该目标已经生成的 `RenderedNotification`。模板和图片生成不属于发送重试。

`app.models` 和 `app.services` 的包导出改为按需加载，通知叶子模块导入不再触发
配置、升级、系统服务、模板或 Pillow 初始化；原包导出及显式历史导入保持兼容。

### 无会话传输快照

无会话渠道声明 `transport_fields`：元组列出从全局 Notify 固定的字段，空元组
表示只固定代理。邮件固定 SMTP 地址、发件人和授权码；系统提示固定本次开关；
Server 酱、Webhook 和移动消息固定代理。接收者及 Webhook 地址、模板等仍由原有
目标快照提供。用户级通知的传输设置来自全局，接收目标来自用户配置。

宿主在准备目标时生成不可变 `NotificationTransportSnapshot`。绑定表通过原发送器
工厂注入本次快照和固定代理，重试沿用同一数据。下一次准备目标读取最新配置。
快照仅在内存存在，凭据和代理不进入对象 repr，不增加配置副本、持久化或连接池。
直接系统提示和 Webhook 测试入口继续读取调用时的配置。

`transport_fields=None` 使用原已装配实例；QQ 和 Koishi 的连接、token 与锁由实例
持有。带启停入口的渠道不能声明无会话快照，避免重建活跃会话。QQ 仍在发送前核对
当前绑定身份、接收位置及群有效性，解绑或目标撤销后不通过旧快照继续发送。

### 执行顺序与退出

一次分发中不同渠道最多四路同时执行，同一渠道内的目标按原顺序投递。渲染结果
在目标重试期间固定，普通异常或显式 False 只影响该目标；返回结果按输入顺序汇总。
配置事务内由 core 门面切换为同 Task 串行执行，保持原目标顺序，避免父事务等待
需要写配置的子任务。投递服务接受显式执行策略，不反向读取配置框架。

调用方继续等待完整 `DispatchResult`。取消向上传播，并取消、等待本次分发创建的
全部渠道子任务；重复取消不会打断渠道 finally 中的异步清理，不留下游离协程。
底层 HTTP/SMTP/WebSocket 超时保持原设置；
线程内的 SMTP 或系统调用仍受底层能力限制，取消协程不能证明外部消息未送达。

任务报告入口由 `core/task_report.py` 装配；等待、合并、已送达集合和迟到补发由
`core/notification_report.py` 的协调器管理。日历按成功 ID 更新提醒进度。
通用投递器不接收 task_info，也不修改业务状态。
现有后台任务所有者、电源动作前的等待以及退出时先结束通知任务、再关闭渠道的
顺序保持不变。此路径不引入后台消息队列，也不承诺进程重启后恢复未完成通知。

## 任务通知编排

```text
manager -> TaskResultReport -> Notify.push_proxy_result
  -> notify.task_report：策略快照、独立通知状态与外部能力装配
  -> notify.coordinator：等待、摘要去重、迟到补发
       -> ReportRenderer + 显式 NotificationDispatcher
AutoProxy / runner -> 共用或专项正文构造 -> NotifyPayload
  -> Notify.push_statistics_report -> dispatch_task_notification
MAA 喜报 / HSR 云登录提醒 -> NotifyPayload -> dispatch_task_notification
以上路径共用宿主的目标准备、投递、失败反馈与后台任务所有者
```

`PreparedTaskReport` 在一次报告入口读取不可变 `TaskReportPolicy`，是否发送、等待
和摘要合并共用该策略。等待期间修改配置不改变已经准备的报告；迟到补发属于
下一次通知，重新读取策略，关闭签到通知后不再补发。目标仍沿用该报告固定的
目标快照；没有报告的任务在补发入口准备默认目标。

报告与补发使用同一个全局 Notify。管理器在首次使用时准备发送器；底层投递器
仍接收明确的目标、发送器和渲染器，任务报告的状态按任务保存。

`TaskReportCoordinator` 只持有 `TaskNotificationState`，与任务共享结果、消费标记和
已送达 ID；失败渠道通过每次投递的 `DispatchResult` 返回。
协调器不持有完整任务对象，自身不读取全局配置，也不直接访问 Publisher
或 RuntimeTasks。投递、策略读取、默认目标准备、后台任务注册和失败反馈通过
`TaskReportDependencies` 注入，配置与任务页面反馈留在 core 入口装配。内容实现
由通知模块装配为 `DefaultReportRenderer`；协调器自身不导入内容模块，且导入
`app.core` 不再急切加载 Config，因此可以在没有模板、Pillow 或配置实例时运行。
报告入口只接收 `TaskItem` 或无任务上下文，直接复用任务的通知状态；旧字段别名、
object 字段投影和同步观察端口已退役。投递事实通过 DispatchResult 返回；失败反馈另外交宿主任务
所有者持有，反馈异常或延迟不改变投递结果。电源前有限等待、退出回收同时覆盖反馈。
任务和通知批次的失败通过常驻系统提示发布；无任务、无批次的独立报告失败仍只记录日志。
电源动作等待 `Notify.tasks.drain_notifications`，通知回收使用统一任务所有者。

报告与补发共享一把锁；签到先完成时合并进报告，短暂等待超时则先发送带待确认
提示的报告，签到继续执行。后续报告对已收到签到摘要的渠道只发送原始内容，
未收到的渠道继续带摘要。正常空结果与异常终态结清待确认提示，异常不推断
实际签到失败；零目标、未知渠道和目标准备失败不能被当作全部送达。

社区格式化和报告摘要组合只依赖显式数据，不读取配置或修改任务状态。专项仍
拥有自己的报告内容与模板，不在通用投递器中识别专项或签到业务。

通知消费不可变 `CommunityNotificationResult` 快照，使用 success / already_signed /
risk_control / failed 机器状态。旧字典、中文状态及占位过滤仅在入口适配；日期、
`_completed` 判定和 API 保存仍由签到业务处理，不由通知状态反推。
`community_notification_results` 和 `from_legacy` 是现役业务适配，继续承担上述转换；
`tools/community_notify.py` 和 `core.community_notify` 的旧入口已退役，独立社区通知
由宿主 Service 装配，纯内容生成使用 `services.community_notification`。

共享结果入口接收不可变 `TaskResultReport`，开始/结束时间、数量和结果都是明确
字段；`TaskResultData` 标出生产端的公共字段。模板扩展经边界透传，不
参与共享发送决策。任务统计入口只接收已生成的 `NotifyPayload`，并保留即时托管、
事务内同 Task 投递与失败反馈；插件的独立 `send_statistics` 不承担任务托管。
专项字典只进入正文构造，旧模式路由和 `TaskNoticeMode` 已退役。用户通知配置协议
描述实际的只读分组属性，不要求配置实例提供旧式
get/set；渠道仅通过宿主的 `TargetConfigView` 获取字段。
签到摘要只由协调器消费结构化结果后追加；旧内嵌摘要标记、正文剥离和替换路径已退役。
即时任务通知固定立即托管，普通报告使用默认单次投递；重试参数只保留在实际需要配置的发送入口。

## 独立社区通知与日历

手动签到 API 和非任务定时签到直接使用 `Notify.community`。协调器由
全局 Notify 创建；开关、默认目标、内容生成、失败反馈和任务注册
均通过依赖提供。短暂等待超时或 HTTP 请求取消后，通知继续由 `RuntimeTasks`
持有；电源动作等待使用统一剩余时限，退出先回收通知再关闭渠道。
独立社区通知只发送本次结果；目标去重和完成提示由任务报告协调器处理，不另设通用覆盖入口。

日历直接调用 Notify 准备目标和投递，只持有提醒及其已送达 ID。
未知目标保留在失败结果中，不能结清提醒。MAA 喜报仅声明 announcement 展示
意图，Webhook 自行声明该意图下的正文能力，专项不识别或修改渠道 ID 与能力。
