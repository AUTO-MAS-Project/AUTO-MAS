# 更新日志碎片

每个 PR 在这个目录下放**一个**文件，写一句给用户看的话。PR 合并后工作流立刻把它编译进
`CHANGELOG.md` 顶部的「未发布」段并删掉碎片；发版时「未发布」段变成新的版本段。所以平时
不要改 `CHANGELOG.md`、`res/version.json` 和任何版本号，它们只由入账机器人与发版 PR 更新。

## 怎么写

```powershell
python scripts/changelog.py add fix maa "修复理智不足时剿灭被误记为本周已完成的问题"
# → changelog.d/<当前分支名>.fix.md（在 dev / main 或游离 HEAD 上是时间戳），内容：
#   project: maa
#   修复理智不足时剿灭被误记为本周已完成的问题
```

也可以手动新建文件：

- 文件名 `<PR 号或分支名>.<分类>.md`，例如 `683.feat.md`、`mumu-force-kill.fix.md`。
- 首行 `project: <项目键>`，键从下面的项目表里选，**必填**；只有 `dev` 碎片可以不写
  （命令行写 `-`），因为开发流程不进公告。
- 正文一行、**不超过 50 字**，只写做了什么，不用 `- ` 开头，不写项目名、PR 号和署名——
  这三样入账时按碎片和它的合并提交自动补成 `【项目】做了什么 (#PR) by @作者`。
- 署名默认取合并那个提交的作者（squash 合并就是 PR 作者），**不读 Co-authored-by**。替别人提交、
  或者一个 PR 是几个人一起做的，加一行 `author: 甲, 乙` 把人列全（逗号、顿号、空格分隔都行），
  公告里每人一个 by；多人 PR 只有这一条路。
- 维护者觉得这条值得放进「本次亮点」，就再加一行 `highlight: true`；编译时这条进「本次亮点」
  而不是原分类。
- 改的是本周期更早 beta 才带进来的功能（正式版用户从没见过它之前的样子），加一行 `beta-only: true`：
  公测公告照常显示，转正汇总时自动丢掉。判据见下面「写作要求」。
- 不要重命名或改写别人的碎片：署名按最近一次新增该文件的提交算，重命名会把署名转给重命名的人；
  文件名要改请让作者自己改，或在碎片里写明 `author:`。只加减 `highlight:` / `beta-only:`
  两行不算改别人的碎片。

| 后缀 | 编译后的分类 | 用途 |
| --- | --- | --- |
| `breaking` | 破坏性变更 | 需要用户动手确认，或会改变既有行为 |
| `feat` | 新增 | 新功能 |
| `change` | 变更 | 对现有功能的调整与优化；拿不准时宁可写 change 不要写 fix |
| `remove` | 移除 | 已经移除，或不再建议使用、即将移除 |
| `fix` | 修复 | bug 修复 |
| `security` | 安全 | 安全性改进 |
| `dev` | 开发流程 | 只影响贡献者、用户看不见；不进公告 |

「本次亮点」没有后缀，只能由 `highlight: true` 标出来。

项目键（公告里同一分类内按这个顺序排）：

| 键 | 公告里显示 | 键 | 公告里显示 |
| --- | --- | --- | --- |
| `maa` | MAA | `mfw` | MFW |
| `end` | end（MaaEnd） | `general` | 通用脚本 |
| `m9a` | M9A | `home` | 主页 |
| `hsr` | HSR | `scheduler` | 调度 |
| `bgi` | bgi（BetterGI） | `emulator` | 模拟器 |
| `zzz` | 绝区零一条龙 | `notify` | 通知 |
| `okww` | ok-ww | `tools` | 工具 |
| `oknte` | ok-nte | `settings` | 设置 |
| `baah` | BAAH | `update` | 更新 |
| `whimbox` | 奇想盒（Whimbox） |  |  |
| `mss` | MSS | `runtime` | Runtime |
| `src` | SRC |  |  |

表在 `scripts/changelog.py` 的 `PROJECTS` 里，新专项加一行即可。没有兜底键，归不进的**就近归**：

- 虚拟显示器、界面语言 / 文案、帮助入口 → `settings`
- 游戏社区（签到、社区活动）、日志页 / 打包日志 → `tools`
- 历史记录、脚本 / 用户的增删改、配置备份恢复、运行中锁配置 → 对应专项；跨全部专项的配置来源、
  快速配置、配置恢复能力 → `scheduler`
- 调度中心、调度队列、计划管理 → `scheduler`
- 启动界面、初始化、依赖安装 → `runtime`
- 性能与清理类 → 改到哪个页面就归哪个；一条改动横跨几个项目时选最主要的那个

## 写作要求

- **面向用户**：只描述用户可观察到的改动或修复，删掉实现细节、类型名、接口路径、状态码。
- **写症状，不写根因**：写「修复了什么现象」，不写「为什么、怎么改的」。
- **一条 PR 一句话**：把全部改动概括成一句，不要拆成多条；50 字写不下就是该删细节了。
- **一个功能在公告里只出现一次，判据只有一条：这个功能是哪一版带进来的。** 上一个正式版的公告
  里查不到的功能，就是本 X.Y.0 周期带进来的（5.5.0 周期里如 Runtime 初始化、虚拟显示器、
  Emulator 2.0、MFW、BetterGI、BAAH、绝区零一条龙、配置恢复、干员养成）。对这类功能，之后
  **所有修复、维护和补充修改**——修 bug、改成弹窗询问、加提示、调默认值、改页面布局、接词表、
  清理——**一律仅公测**：
  - 同一 beta 内（那条新增还在「未发布」段里，或它的碎片还在这个目录里）：不写碎片，PR 打
    `skip-changelog`；要改那条新增的描述，在 PR 里写明，由维护者改「未发布」段。合并前期间发了
    beta、那条新增已经发出去，就改成补一个 `beta-only` 碎片。
  - 跨 beta：碎片加 `beta-only: true`。周期内新增又移除、破坏性变更又回退，同样标。
  - 后来给它加的子能力也一样仅公测：正式版公告里一个新专项就是一句「【bgi】新增 bgi 专项」，
    一个新功能就是它那条新增；最终行为与新增写的不一样，在发版 PR 里改那条新增的正文。
  - 上一个正式版就有的功能，修复和调整正常写。
- 纯文档、CI、测试或用户不可见的重构不需要碎片，同样打 `skip-changelog` 标签。

## CI 会检查什么

- 改了 `app/`、`frontend/src/`、`frontend/electron/` 或 `main.py` 的 PR 必须恰好新增一个碎片
  （或打 `skip-changelog`）。
- 碎片必须有 `project:` 且键在项目表里（`dev` 除外），正文不超过 50 字。
- 普通 PR 不得改 `CHANGELOG.md`、`res/version.json`，也不得改动 `pyproject.toml`、
  `frontend/package.json`、`app/core/config.py`、`uv.lock` 里的版本号。
- 不要修改或删除别人的碎片（加减 `highlight:` / `beta-only:` 除外）。
- 维护者整理历史更新日志时给 PR 打 `changelog-maintenance` 标签，上述限制放开。

## 合并后与发版时发生什么

- **合并即入账**：带碎片的提交进了 `dev` 或 `release/*`，「入账更新日志碎片」工作流就把碎片
  编译进 `CHANGELOG.md` 顶部的 `## [未发布]` 段与 `res/version.json`，删掉碎片，以机器人身份
  推回。作者与 PR 号取自合并那一刻的提交。开发构建的「当前版本更新日志」能看到未发布段。
- **准备发版**：维护者在 Actions 里运行「准备发版」，选 `beta` / `stable` / `patch`：脚本按最新
  tag 推出版本号（公测 N+1；转正与最后一个 beta 同号；补丁 Z+1），把「未发布」段改成
  `## [vX.Y.Z] - 日期`（还没入账的碎片一并编译），写入五处版本号，开出 `Release vX.Y.Z` PR。
  发版 PR 开出后又有 PR 合并入账，发版 PR 会和 dev 冲突，重跑一次「准备发版」即可。
- **转正**：同号的全部 beta 段并成一个正式版段（同项目同正文去重、按项目排序），带 `（仅公测）`
  的条目丢掉并在发版 PR 里列出，beta 段从文件里移除。稳定通道的用户看到的就是整个周期的汇总。
- **构建守门**：顶部还有带条目的「未发布」段、碎片没清空、版本号没比 tag 新，构建都不会开始。

Release 正文首行是给客户端更新提示用的 JSON（客户端只显示比本机新的段）：公测版带本周期
全部 beta 段，正式版只带本次汇总，补丁版带同一 X.Y 线上的正式版段，上一个周期的内容一律
不带。Mirror 酱只保留前 20000 字符，脚本给首行 18000 字符的预算：超预算时从最老的版本段
开始丢；本版段自己就超预算也不会让发版失败——脚本从段末尾一条条熔断，首行仍是完整 JSON，
末尾补一条「还有 N 条未显示」，发版 PR 正文会预告将丢哪些，发布后工作流自动开 issue 列出
丢掉的条目。想全部保留，就在合并前在发版 PR 里直接改 `CHANGELOG.md` 新版本段精简或合并
条目，改完运行 `python scripts/changelog.py sync` 一起提交。
