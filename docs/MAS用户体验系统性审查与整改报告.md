# AUTO-MAS（MAS）用户体验系统性审查与整改报告

> 目的：从普通用户的实际心智模型出发，系统性识别“改动被丢弃、保存结果不确定、失败后不知道下一步怎么做、页面显示与真实状态不一致”等问题，并给出可直接交给智能体团队执行的整改方案。
>
> 审查日期：2026-10-07
> 审查基线：`origin/dev`，提交 `d93c88054`
> 参考案例：PR #1251（配置会话改动被丢弃时显式通知）
> 工作区状态：当前工作区存在未提交改动。它们只作为“正在进行中的修复方向”参考，不计入基线已完成能力。

## 1. 结论摘要

### 1.1 总体判断

MAS 当前不是单点提示缺失，而是缺少一套统一的“用户可感知结果契约”：

1. 用户发起的是“保存/启动/停止/恢复/导入”。
2. 系统内部实际执行的是“请求已接受、任务已结束、配置是否写盘、是否因保护规则回退、是否成功回读”。
3. 前端经常把第 2 步中的中间结果当成最终结果。
4. 失败或自动修正经常只写日志，页面继续展示看似正常的值。
5. 关键结果依赖一次性 WebSocket 消息，断线、切页、切窗口时可能永久错过。

因此，用户最容易形成的错误认知是：

- “弹了已保存，所以肯定写入了。”
- “页面上还是我刚改的值，所以肯定成功了。”
- “页面空了，所以原来没有数据。”
- “配置恢复成功，所以当前页面已经是恢复后的值。”
- “任务停止成功，所以原生程序的配置也保存了。”
- “没有错误提示，所以系统没有发生任何改变。”

### 1.2 最高优先级问题

| 优先级 | 问题 | 用户后果 | 主要责任 |
|---|---|---|---|
| P0 | 配置会话最终结果不具备可回读、可补偿的权威来源 | 改动被丢弃后仍显示保存成功，或断线后永久无提示 | 后端平台 + 前端平台 |
| P0 | 原生配置会话未统一接入 `task.config.discarded` | 同一种操作在不同入口得到不同结果 | 前端平台 + 各专项入口 |
| P0 | “成功”提示与最终业务状态脱钩 | 用户会继续使用未落盘配置 | 前端平台 |
| P1 | 保存状态没有统一状态机 | 用户不知道未保存、保存中、失败保留草稿还是结果未知 | 前端平台 |
| P1 | 自动修正、损坏恢复、密文不可读没有面向用户的解释 | 用户以为程序吞掉了自己的设置 | 后端配置平台 + 前端设置页 |
| P1 | 队列、计划、历史、模拟器等页面失败后缺少恢复动作 | 页面空白或旧数据被误认为真实数据 | 各页面维护者 |
| P1 | 离开编辑页的保护只覆盖部分入口 | 用户从侧栏、路由、关闭窗口离开时可能丢草稿 | 前端平台 + 各编辑页 |
| P2 | 技术错误直接显示给用户 | 用户看不懂，也无法据此行动 | 前端平台 |

### 1.3 必须统一的产品承诺

任何会改变用户数据或运行状态的操作，界面必须同时回答：

1. **发生了什么？**
2. **最终结果是什么？**
3. **我的数据现在在哪里？**
4. **下一步可以做什么？**

例如“配置会话改动被丢弃”不能只写“保存失败”，至少要说明：

> 这次原生配置中的改动没有写入 MAS。原因是任务列表在打开配置后发生了变化，为避免覆盖其他修改，系统放弃了本次写回。请重新打开配置，只修改任务开关和高级选项后再次保存。

## 2. 审查范围与方法

### 2.1 覆盖范围

- 配置会话：MAA、SRC、MaaEnd、ok-ww、ok-nte、BetterGI、ZZZ-OD、脚本管理页入口。
- 编辑页：用户配置、脚本配置、MaaFW/M9A/MSS 等统一页面。
- 队列、计划、调度器、历史记录。
- 模拟器管理与 Emulator 2.0。
- 初始化、后端启动、Runtime 更新、应用生命周期。
- 设置、通知、游戏社区签到、配置备份与恢复。
- HTTP 错误、WebSocket 连接、任务终态、页面卸载和路由离开。

### 2.2 审查方式

1. 以 `origin/dev` 为基线静态阅读前后端实现。
2. 追踪“用户点击 → 请求 → 后端任务 → WS/HTTP 返回 → 页面状态”的完整链路。
3. 对每个异常路径检查：
   - 是否给用户反馈；
   - 反馈是否解释数据去向；
   - 是否提供重试/恢复；
   - 页面值是否仍代表真实落盘值；
   - 断线后能否补齐结果。
4. 对照已存在的较好实现，提取平台级模式，而不是重复造专项逻辑。

### 2.3 审查限制

- 本报告是代码和交互契约审查，不等同于完整人工可用性测试。
- 未覆盖所有第三方原生程序版本、系统权限、网络环境和多显示器组合。
- 报告中的“可能”表示代码路径允许该情况发生，不代表每次运行都必现。
- 生产整改前仍需按验收矩阵执行真实环境测试。

## 3. 用户心智模型

用户不应该需要知道以下内部概念：

- `final_task`
- 快照、基线、队列结构校验
- `task.completed` 和 `task.config.discarded` 的先后顺序
- HTTP 200 但 body `code != 200`
- 原生配置目录、MAS 侧车、副本、恢复池
- WebSocket 是否正好在线

用户只需要理解以下业务概念：

| 用户概念 | 系统应呈现的状态 |
|---|---|
| 我正在修改 | 未保存 |
| 系统正在写入 | 保存中 |
| 已经写入 | 已保存 |
| 后端拒绝写入 | 未保存，原值保留 |
| 系统为防覆盖放弃写入 | 改动未写入，原因可读 |
| 网络/连接中断 | 结果未知，正在确认 |
| 自动修正了我的值 | 已自动修正，显示修正前后，允许恢复 |
| 页面数据来自旧缓存 | 数据可能过期，可刷新 |
| 恢复操作已完成 | 当前页面已重新读取恢复结果 |

## 4. 严重度定义

- **P0**：会造成用户数据丢失、覆盖、误以为成功，或无法恢复；必须优先处理。
- **P1**：用户无法判断真实状态，或失败后没有明确恢复路径；影响核心工作流。
- **P2**：提示不清晰、技术细节泄漏、体验不一致，但有其他方式完成任务。
- **P3**：视觉、文案、可访问性或一致性问题，不阻断主流程。

## 5. 统一问题清单

## 5.1 跨模块结果契约

### UX-X001：关键结果只通过一次性 WebSocket 通知

**现象**

- 后端发布器 `app/core/ws/publisher.py:36-67` 明确“不缓存、不重放”，主连接未就绪时消息直接丢弃。
- 配置丢弃通知位于 `app/core/ws/protocol.py:56-58`、`app/task/MAA/ScriptConfig.py:376-440`。
- 前端收到 `task.completed` 后通常直接关闭遮罩或提示成功。

**用户困惑**

- 保存时恰好断线，用户看不到“改动被丢弃”。
- 重连后页面没有任何历史结果，用户无法判断刚才是否写入。
- 切换窗口或从页面离开时，结果消息可能没有订阅者。

**整改要求**

1. 将“任务完成结果”持久化为任务终态或可查询的业务结果。
2. 设计 `GET /dispatch/task/{task_id}/result` 或等价快照接口。
3. WebSocket 只负责实时加速，不再承担唯一事实来源。
4. 前端在以下时机查询终态：
   - 停止接口返回后；
   - 收到 `task.completed` 后；
   - 重连成功后；
   - 页面重新进入时；
   - 保存结果等待超时后。
5. 查询结果必须包含：
   - `outcome`：`saved`、`discarded`、`failed`、`cancelled`、`unknown`；
   - `reason`；
   - `affected_scope`；
   - `data_preserved`；
   - `retryable`；
   - `finished_at`；
   - 可供日志关联的 `task_id`。

**验收**

- 断开 WS 后完成配置会话，重连后页面能显示最终结果。
- 收到停止 HTTP 成功但漏掉 WS 时，不能显示“已保存”，而是查询确认。
- 结果查询失败时显示“结果确认中/未知”，不能伪造成功。

### UX-X002：请求成功不等于业务成功

**代码证据**

- 多个端点使用 HTTP 200 + body `code` 表达业务失败。
- `frontend/src/api/core/request.ts:252-283` 会生成 `Bad Request`、`Internal Server Error`、`Generic Error` 等技术错误。
- 部分页面只判断请求是否抛异常，没有统一判断业务码。

**整改**

- 建立统一 `BusinessResult<T>` 解析器。
- API 层返回结构化错误，不在 API 层直接弹 Toast。
- 页面层根据业务动作决定文案和恢复动作。
- 每个 mutation 必须明确“提交成功”“业务拒绝”“结果未知”三类结果。

### UX-X003：错误信息直接暴露技术细节

**代码证据**

- `frontend/src/views/scheduler/useSchedulerLogic.ts:1018-1022`
- `frontend/src/composables/useNativeGuiSession.ts:171-175`
- `frontend/src/views/Scripts.vue:729-737`
- 多处直接显示 `error.message`、`String(error)`、`Failed to fetch`。

**整改**

统一错误分类：

| 分类 | 用户文案方向 | 恢复动作 |
|---|---|---|
| `network_unavailable` | 无法连接 MAS 服务 | 重试、检查后端 |
| `backend_unavailable` | 后端正在启动或已停止 | 等待、重启后端 |
| `invalid_input` | 这个值不符合要求 | 定位字段并保留输入 |
| `conflict` | 数据已被其他操作改变 | 重新读取、比较后重试 |
| `protected_discard` | 为防止覆盖，本次改动未写入 | 重新打开并按提示操作 |
| `external_program` | 外部程序没有写出配置 | 打开程序检查、再次保存 |
| `permission_denied` | 文件或目录不可写 | 更换目录/提升权限 |
| `unknown` | 操作结果暂时无法确认 | 查询状态、导出诊断 |

技术异常只进入日志和“复制诊断信息”区域。

### UX-X004：没有统一的“失败后恢复动作”

所有失败反馈必须至少包含一个动作：

- 重试当前请求；
- 重新读取页面；
- 保留草稿并继续编辑；
- 打开相关目录/日志；
- 恢复上一次备份；
- 返回可用页面；
- 联系支持并复制诊断信息。

仅 `message.error('失败')` 不满足要求。

## 5.2 原生配置会话

### UX-C001：脚本管理页在基线未接收丢弃通知

**基线证据**

- `origin/dev:frontend/src/views/Scripts.vue:634-672` 仅订阅 `WS_TASK_NOTICE`、`WS_TASK_COMPLETED`。
- 当前工作区的未提交修改已开始增加 `WS_TASK_CONFIG_DISCARDED`，但不应视为基线能力。

**用户路径**

1. 用户从脚本管理页打开 MAA/SRC/MaaEnd/ok-ww 配置。
2. 用户改变了任务结构或原生程序没有写盘。
3. 后端安全地丢弃改动。
4. 脚本页只收到完成消息并显示“配置完成/保存成功”。

**整改**

- 脚本管理页必须复用统一会话 composable，不再维护自己的停止/完成判断。
- 若暂时不能重构，至少补订阅、结果判定、超时查询和消息去重。
- 所有入口的成功文案必须由最终 `outcome=saved` 驱动。

### UX-C002：SRC 会话缺少丢弃事件处理

**代码证据**

- `frontend/src/views/EditView/User/SRCUserEdit.vue:603-653` 只订阅任务通知和完成消息。
- `:701-729` 可能在停止成功后显示保存成功，但没有读取丢弃结果。

**整改**

- SRC 接入统一会话实现。
- 查看会话与编辑会话使用不同结果语义：
  - 查看会话：关闭，不写回，不提示“已保存”；
  - 编辑会话：只在最终 `saved` 时提示保存成功；
  - `discarded`：显示原因和重新操作建议。

### UX-C003：BetterGI、OK-NTE、ZZZ-OD 等会话实现不一致

**代码证据**

- `frontend/src/composables/useBettergiGuiSession.ts:8-144`
- `frontend/src/composables/useOknteGuiSession.ts:8-129`
- `frontend/src/composables/useZzzodGuiSession.ts:8-134`
- 这些实现主要订阅 `WS_TASK_NOTICE` 和 `WS_TASK_COMPLETED`，并在 `stopSession` 成功后直接提示保存。

**整改**

- 统一到一个会话状态机：
  - `idle`
  - `starting`
  - `open_edit`
  - `open_view`
  - `stopping`
  - `confirming_result`
  - `saved`
  - `discarded`
  - `failed`
  - `unknown`
- 专项包装器只注入：
  - 日志名；
  - 文案 key；
  - 是否支持原生写回；
  - 备份/回读适配器。

### UX-C004：停止响应、丢弃帧、完成帧存在竞态

`useNativeGuiSession.ts` 已尝试使用 300ms grace period 处理顺序差异，但这不是可靠的业务确认机制：

- 300ms 不能保证跨重连、系统调度、主进程阻塞时的消息到达。
- 关闭订阅后仍可能丢失后续终态。
- “停止接口返回 200”并不等于原生配置写回成功。

**整改**

1. 后端停止接口返回任务终态摘要，或提供可立即查询的结果。
2. 前端使用“停止 → 查询终态 → 清理订阅”的顺序。
3. WebSocket 仅作为提前通知，不能决定成功。
4. 任何 `unknown` 结果保留提示条，直到用户主动刷新或结果确认。

### UX-C005：原生会话超时后自动保存，但用户不清楚数据去向

当前实现会在 30 分钟后提醒并自动停止/保存：

- 用户可能离开电脑，回来看到界面已关闭；
- 若写回失败，页面不一定仍在，用户看不到错误；
- 查看会话超时静默关闭，用户不知道“只是关闭查看”还是发生了失败。

**整改**

- 超时前显示倒计时和明确按钮：
  - “继续编辑”
  - “现在保存并关闭”
  - “放弃本次会话”
- 超时后的结果写入任务终态中心。
- 回到 MAS 时显示“上次配置会话结果”通知。
- 查看会话关闭文案必须明确“查看窗口已关闭，未保存任何修改”。

## 5.3 编辑页保存与离开保护

### UX-E001：字段即时保存没有统一可见状态

**较好参考**

- `frontend/src/composables/useSaveQueue.ts`
- `frontend/src/views/MAAUserEdit/useMAAFieldSave.ts`
- `frontend/src/views/MAAUserEdit/useMAAEditorLifecycle.ts`

这些实现已经包含串行保存、失败回读、草稿保护和离开守卫，应提取为平台规范。

**问题**

- 其他编辑页仍大量使用 blur/change 触发保存，但字段旁没有状态。
- 用户快速修改多个字段时，无法知道哪个字段仍在队列中。
- 保存失败后，有的页面回滚，有的页面保留新值，有的页面只写日志。

**整改**

字段或页面必须显示以下之一：

- 未保存；
- 保存中；
- 已保存；
- 保存失败，已保留草稿；
- 保存失败，已恢复旧值；
- 结果未知，正在确认。

### UX-E002：MaaFW 用户页的离开保护不完整

**代码证据**

- `frontend/src/views/EditView/User/MaaFWUserEdit/useMaaFWUserPage.ts:313-364` 主要通过 `handleCancel` 与 `beforeunload` 保护。
- 缺少与 MAA 编辑页同等的 `onBeforeRouteLeave`、统一保存队列等待和应用关闭协调。

**风险**

- 从侧栏、面包屑、浏览器式导航、路由替换离开时可能绕过手动取消逻辑。
- `onUnmounted` 的异步备份不能阻止页面已离开后发生的保存竞态。

**整改**

- 提取统一 `useEditorLifecycleGuard`。
- 所有用户/脚本编辑页必须接入：
  - 路由离开守卫；
  - 应用关闭守卫；
  - 等待保存队列；
  - 处理原生配置会话；
  - 保存失败时阻止离开；
  - 离开后再做备份归档。

### UX-E003：自动备份不是用户可见的恢复承诺

`ConfigRestoreSection.vue` 提供了备份、预览、恢复，但“自动备份失败”多在日志或 warning 中出现：

- `frontend/src/views/EditView/User/components/ConfigRestoreSection.vue:372-639`
- `frontend/src/views/EditView/User/SRCUserEdit.vue:500-525`
- `frontend/src/views/EditView/User/MaaFWUserEdit/useMaaFWUserPage.ts:339-363`

**整改**

- 备份归档失败必须标记为“恢复点可能不完整”。
- 恢复列表显示来源、时间、是否完整。
- 恢复后父页面必须重新读取并显示“已从 YYYY-MM-DD HH:mm:ss 恢复”。
- 恢复失败不能关闭预览弹窗。

## 5.4 队列、计划和调度

### UX-Q001：队列列表加载失败后清空页面，仅写日志

**代码证据**

- `frontend/src/views/queue/index.vue:345-390`。
- 请求失败时可能清空列表，用户无法区分“确实没有队列”和“请求失败”。

**整改**

- 保留上一次成功数据；
- 显示错误横幅：“队列列表加载失败，下面是上次数据”；
- 提供“重试”；
- 首次加载失败显示专门错误页，不显示普通空状态；
- 记录数据时间戳。

### UX-Q002：队列子数据失败被静默降级

- `loadQueueData:394-445`
- `refreshTimeSets:447-510`
- `refreshQueueItems:513-566`

子请求失败时只记录日志，页面可能继续展示旧定时项或旧队列项。

**整改**

- 每个区域单独显示 `fresh/stale/error` 状态。
- 旧数据必须标注“上次成功读取于……，刷新失败”。
- 子数据失败允许局部重试，不阻塞其他区域。

### UX-Q003：切换队列失败导致空白和状态误判

- `onQueueChange:712-727` 先改变选中队列并清空内容，再请求新数据。

## 6. 目标交互模型

## 6.1 统一保存状态机

建议平台级类型：

```text
idle
dirty
saving
saved
failed_draft_kept
failed_reverted
rejected
discarded
unknown
```

状态转换规则：

1. 用户修改字段：`idle/saved -> dirty`。
2. 发起保存：`dirty -> saving`。
3. 后端确认落盘：`saving -> saved`。
4. 参数或业务拒绝：`saving -> rejected`，保留用户输入。
5. 写入失败但草稿仍在：`saving -> failed_draft_kept`。
6. 写入失败且已回读旧值：`saving -> failed_reverted`。
7. 配置保护丢弃：`saving -> discarded`。
8. 网络/断线导致无法确认：`saving -> unknown`。
9. `unknown` 只能通过查询终态转为其他终态，不能直接显示成功。

## 6.2 统一任务结果契约

后端平台负责提供，所有任务类型复用：

```json
{
  "task_id": "uuid",
  "outcome": "saved",
  "reason": null,
  "scope": "native_config",
  "data_preserved": true,
  "retryable": true,
  "message_key": "config_saved",
  "finished_at": "2026-10-07T12:00:00Z"
}
```

`outcome` 至少支持：

- `saved`
- `discarded`
- `failed`
- `cancelled`
- `completed_without_write`
- `unknown`

## 6.3 统一错误呈现组件

建议新增或复用平台组件，不要求每个专项自行实现：

- `OperationStatusBanner`
- `SaveStateIndicator`
- `RetryableErrorState`
- `ResultUnknownNotice`
- `DiscardedChangeDialog`
- `DiagnosticsDetails`

组件只负责展示，不读取上游私有配置格式，不跨越专项边界。

## 6.4 统一页面数据状态

任何列表/详情接口都必须显式区分：

```text
not_loaded
loading
loaded_fresh
loaded_stale
empty
error_with_previous_data
error_without_data
```

空数组不能同时代表“真正为空”和“请求失败”。

## 7. 责任分布与边界

### 7.1 后端平台团队

负责：

- 任务终态结果模型和查询接口；
- 配置会话的保存/丢弃/未写盘原因；
- WebSocket 断线后的可恢复查询；
- 配置加载状态和规范化事件；
- 不同专项共用的任务结果持久化。

禁止：

- 读取前端私有状态；
- 为了提示文案读取第三方程序内部格式；
- 把专项脚本逻辑复制到 MAS 平台层；
- 只增加日志而不提供可查询结果。

### 7.2 前端平台团队

负责：

- 统一结果状态机；
- 统一错误分类和文案参数；
- 统一保存队列、离开守卫、重连补偿；
- 统一配置会话 composable；
- 页面数据 freshness/error 状态组件。

禁止：

- 在每个专项复制一份不同的保存状态机；
- 仅靠增加 Toast 解决终态不确定；
- 把技术异常字符串直接交给用户。

### 7.3 各专项维护者

负责：

- 注入专项名称、文案 key、数据范围；
- 提供专项的回读/备份适配器；
- 按统一契约标记可恢复动作；
- 验证第三方程序真实行为。

禁止：

- 解析或反推上游私有格式；
- 在专项内重新实现任务终态；
- 把“脚本该做的事”搬到 MAS。

### 7.4 QA/测试团队

负责：

- 断线、重连、窗口切换、重复点击、快速编辑、超时、权限失败测试；
- 对每个结果状态执行验收矩阵；
- 验证多语言、可访问性和移动/窄窗口布局；
- 记录真实用户可见文案和数据去向。

### 7.5 文档与支持团队

负责：

- 把“改动为什么没有写入”写成用户文档；
- 提供错误代码到操作步骤的映射；
- 维护诊断包收集说明；
- 不以开发者术语解释用户行为。

## 10. 验收标准

## 10.1 P0 必测场景

1. **配置丢弃**
   - 打开原生配置；
   - 修改任务结构；
   - 保存；
   - 结果显示“改动未写入”、原因、下一步；
   - 不显示“保存成功”。
2. **断线丢弃**
   - 保存前断开 WS；
   - 后端完成任务；
   - 恢复连接；
   - 页面能补齐最终结果。
3. **停止 HTTP 成功但业务失败**
   - stop 返回成功；
   - 终态为 discarded/failed；
   - 前端必须显示失败终态。
4. **脚本管理页入口**
   - 从 `/scripts` 打开每个支持的专项；
   - 成功、丢弃、失败、超时文案一致。
5. **重复点击**
   - 连续点击保存/停止；
   - 只允许一个有效请求；
   - 不重复提示、不清理错误会话。

## 10.2 P1 必测场景

1. 快速连续编辑多个字段，最后值必保存。
2. 保存失败后页面显示草稿保留或回滚结果。
3. 任意导航离开编辑页都会触发保护。
4. 队列/计划网络失败时不显示假空数据。
5. 配置 JSON 损坏时不直接覆盖原文件。
6. 密文不可解时不把占位值静默写回。
7. 非法枚举被纠正时可看到前后值。
8. 恢复后页面重新读取并显示恢复时间。

## 10.3 P2/P3 必测场景

1. 技术错误不作为主文案，诊断信息可复制。
2. 中英文、日文词条语义一致。
3. 窄窗口、长路径、长错误文本不重叠。
4. 屏幕阅读器能读出加载/错误/成功状态。
5. 后台轮询失败不会每 10 秒弹 Toast。

## 11. 需要明确拒绝的“伪整改”

以下方案不能单独作为完成标准：

- 只在每个页面加一个 `message.error`；
- 只订阅 `WS_TASK_CONFIG_DISCARDED`，不提供断线补偿；
- 只把原始异常字符串翻译成中文；
- 只在按钮上加 loading，不显示最终是否落盘；
- 只做前端回滚，不确认后端真实值；
- 只保留日志，不给用户下一步；
- 只增加备份，不显示备份是否成功；
- 在每个专项复制一套不同的结果判断；
- 为了“体验一致”读取第三方脚本私有状态。

## 12. 最终交付定义

本次系统性整改完成的判据不是“所有页面都弹了提示”，而是：

1. 用户操作的最终业务结果可查询。
2. WebSocket 断线不再造成结果永久丢失。
3. 所有数据改变都有明确的数据去向。
4. 所有失败都有恢复动作。
5. 页面展示值能说明是否已落盘。
6. 自动修正和默认回退可见、可追踪、可恢复。
7. 原生配置会话在所有入口语义一致。
8. 不跨越脚本专项黑箱边界。
9. P0/P1 场景有实际验收记录。
