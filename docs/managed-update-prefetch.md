# 托管更新预下载机制

顺序队列和循环队列执行多个脚本时，可在**前一个脚本运行期间**提前在后台下载下一个脚本的更新包，缩短切换等待时间；实际安装与目录切换仍严格推迟到目标脚本启动前、确认安装目录空闲后执行。

## 三层职责

1. **调度中心**（`app/core/task_manager/`）：决定本轮运行顺序与循环到期项，仅向公共更新入口发送 `watch` / `take` / `finish` / `close` 信号。
2. **公用预下载协调层**（`app/core/script_update.py`、`app/core/script_update_queue.py`）：确定下一个实际可运行脚本、等待 60 秒稳定窗口、异步预下载、持有候选缓存、校验配置基线并在取消或失效时清理。**后台只下载，不安装。**
3. **各脚本更新逻辑**：仅在开启托管更新时检查版本与下载，沿用各自的安装锁、完整性校验、回滚与失败恢复流程。

## 触发与收尾规则

- **稳定窗口**：当前脚本产生本轮首个成功任务节点后，继续稳定运行满 60 秒才触发下一项预下载。同脚本切号不重置计时，紧邻的同一脚本不重复发起。
- **有效目标过滤**：跳过无选中账号、非当日排期、已删除或已锁定的项；循环队列只预取调度中心标记本轮已到期的下一项。
- **启动前移交**：上一脚本结束后，等待已发起的预下载收敛，再进入下一脚本的常规安装流程；安装前重新核验候选版本、摘要与配置基线，若期间配置变化或发生原生更新则丢弃过期候选。
- **取消与隔离**：后台预下载失败不阻断当前脚本。遇到用户停止、重试或前项失败时，撤销预取并等待底层写入者（FluxDown / 内置下载器 / 子进程）真正停写后再清理，避免破坏正在写入的文件。

## 核心设计约束

- **冻结下载参数**：开始预下载前冻结更新通道、来源、凭据与代理；凭据不写入日志、文件名或缓存清单。
- **下载与安装解耦**：预下载只写入 MAS 缓存，不持有目标安装目录锁，也不因下载而中断当前运行的脚本。
- **严格停写确认**：底层下载器（包括 FluxDown）在未确认停写前，不得直接覆盖目标文件、切换下载器或交接下一脚本。
- **下载完成 ≠ 安装完成**：预下载成功只代表候选包就绪，实际更新结果仍以安装器事务确认为准。
