## 1. 配置事务与外部副作用的一致性

状态：第一项冲突已讨论解决。以下最终决定取代此前的候选机制，不重新列为待实现前置能力。

### 1.1 术语修正

本项讨论的不是“仅一次执行”。
用户所指的是：配置修改最终回退，但通知已经发出，不能保证接收者只在修改真正应用后执行通知。

更准确的表述是“缺少提交后触发保证”，属于配置事务与外部副作用的一致性缺口。
通知示例可以描述为回滚后的幽灵通知或未提交副作用泄漏；不把这个现象称为执行次数问题。
“仅一次”不再作为本项需求，也不据此扩展事务内汇集或去重机制。

### 1.2 最新确认的范围

用户决定：来源插件生命周期若已自行承担操作与恢复，则本阶段不为配置基类提供以下两项通用担保：

1. **提交后触发保证**：不保证通知、进程操作等外部副作用只在相关配置事务成功后发生。
2. **外部副作用完整回退保证**：不保证配置回退时，已执行的任意业务副作用会被框架自动恢复。

经 1.3 节源码核实，插件启停的主要路径符合该前提，因此按此决定执行。
两项暂不解决，由配置接收者、操作调用方及插件作者自行尝试规避或在所属业务内处理。

这不削弱已有配置工作区、关联配置变更、订阅增删和异常触发回退的数据契约。
也不免除插件生命周期本身已经明确承担的资源释放和失败清理责任。

### 1.3 来源插件链路核实

来源有效实现集中于：

- [插件注册表模型](https://github.com/AUTO-MAS-Project/AUTO-MAS/blob/8196f7a8058e8aafb943dc336f3308109befe43f/app/models/config/plugin.py)。
- [插件接口](https://github.com/AUTO-MAS-Project/AUTO-MAS/blob/8196f7a8058e8aafb943dc336f3308109befe43f/app/api/plugin.py)。
- [插件管理器](https://github.com/AUTO-MAS-Project/AUTO-MAS/blob/8196f7a8058e8aafb943dc336f3308109befe43f/app/core/plugin_manager.py)。

实际调用关系：

```text
插件注册表接口仅接受 enable/disable/reload/uninstall Trigger
→ 配置模型的 Trigger 处理器转交 Plugin 对应方法
→ 插件管理器执行预检、依赖编排和生命周期钩子
→ 成功后由管理器提交 enabled、state 等结果
→ 失败时由管理器执行失败清理并保留故障诊断
```

关键事实：

- 注册表更新接口剔除非 Trigger 字段，用户不会通过该接口直接把运行状态或 enabled 改成成功。
- 启用先提交“正在启用”状态，执行依赖、配置激活、用户钩子、服务及 HTTP 等系统登记。
- 这些步骤成功后才提交 `enabled=True` 和启用稳态。
- 取消或异常进入 `_fail_branch()`；它注销宿主服务、卸下 HTTP、释放配置等，
  并调用适配器 `system_rollback()`、插件 `on_fail_cleanup()`，最后写故障态和错误信息。
- 失败清理的责任在插件管理器和插件钩子，不依赖配置基类登记通用外部恢复函数。

因此，插件生命周期已经避开了“把整个插件启用当成一个配置字段事务，由配置基类自动撤销所有资源”的设计。
它没有承诺任意插件副作用都可逆；例如已经发出的通知仍无法收回。
插件负责约定范围内的恢复，故障信息也不能因回退而一并抹掉。

### 1.4 来源最新版的额外能力必须单独标明

来源 `app/config/core/entry.py::_dispatch_trigger()` 在事务存在时把命令暂存进上下文，
通过宿主 `TriggerDispatcher` 于提交成功后受理；失败事务丢弃命令。
来源还提供提交后配置观察能力。

这些是来源额外实现的保证，不能说来源整套配置系统都只是当前的即时转发机制。
本轮决定也不能反过来作为它们已经迁入当前 dev 的证据。

本阶段不因迁入插件生命周期而自动移植上述通用保证：

- 配置基类在本轮只沿用已有字段、事务和触发传递能力。
- 插件管理器负责接收操作、执行生命周期、记录结果及失败恢复。
- 来源提交后观察接口不能用普通事务内事件冒充；未提供的保证需在插件能力说明中明确。
- Trigger 操作的身份、查询、取消、重复请求及生命周期归属属于下一讨论项，
  不由本项顺带决定其全部迁入或全部移除。

### 1.5 当前配置基类可复用的能力与边界

现有实现：

- [node.py](../app/config/core/node.py)：对象路由、过滤包装、信号及订阅工作区。
- [manager.py](../app/config/core/manager.py)：实际执行者归属、父子事务、工作区提交和回退。
- [entry.py](../app/config/core/entry.py)：字段提交及当前 Trigger 处理器派发。

当前事务内信号已经支持关联配置修改共同回退，订阅增删也参与工作区回退。
当前 Trigger 可以调用处理函数或派发其异步执行，但传递触发本身不代表业务成功。

框架没有保存“已执行外部副作用”的日志，也没有通用补偿承诺；这一边界本轮保持。
配置提交完成、外部动作完成、配置文件落盘是不同结果，不互相代替。
既有任务信息树事务内直接推送的约定继续保持。

### 1.6 本项不实施的扩展

- 不新增全局或节点级事务完成信号。
- 不迁入逐观察者的提交后队列、重放缓存或实例观察管理器。
- 不增加 `connect(..., rollback=...)` 参数或通用回退方法登记入口。
- 不增加外部调用执行日志、绑定版本缓存或相应的异步回退执行阶段。
- 不为本项调整 L1/L2、TaskBase、配置文件格式或 HTTP/WS 契约。

此前关于这些机制的建议已经撤回，不作为实施计划或新增框架需求。
此前提出“回退方法自身处理错误，框架捕获意外异常并记录”的规则，
只在未来确实重新引入该扩展时作为讨论依据；本轮没有通用回退回调可供框架派发。
现有插件清理仍按其生命周期契约处理与记录异常。

### 1.7 使用者自行规避的方向

以下是调用方可选择的业务安排，不是配置框架提供的强制保证：

- 需要通知最终结果时，由业务在确认实际成功后发送通知。
- 能独立调用的配置更新与操作分开编排，先等待配置更新成功，再请求相关操作。
- 功能开启失败需要恢复配置时，由所属管理器明确选择恢复字段、保护并发修改并记录故障。
- 插件释放自己实际取得的资源，复用现有生命周期钩子，避免与正常关闭重复释放。
- 不把任意配置快照整份写回，也不把不抛异常等同于外部状态一定恢复。

### 1.8 已有验证与记录状态

2026-11-09 的隔离现状实验：

- `tests/models/test_config_signal_rejection.py` 现有两项通过。

本轮仅核实来源代码并更新决策记录；未运行真实插件或实施配置基类变更。

### 2.3 Trigger 的主要差异是受理契约，不能用“异步执行”概括

**事实：** 当前 `app/config/shortcuts.py:94` 不接受 `cancellable`，
`app/config/core/entry.py:543` 同步调用 handler，异步返回值另建 Task，
`update():572` 不返回操作 ID。
来源 PluginRecord 的四个生命周期 Trigger 均使用 `cancellable=False`；原样导入先会在装饰器处失败。

来源 `app/core/operations.py:99` 提供命令身份与受理：同 Entry、同 group/field、同值复用在途 ID，
不同值冲突；它不是所有插件生命周期的全局去重或排队机制。
生命周期实际互斥仍由 PluginManager `_hold():270` 的全局忙锁控制，忙时直接拒绝。
`OperationInfo` 是命令快照，不能等同于插件当前状态或配置持久化结果。

来源 `app/config/core/entry.py:440–452` 的事务后暂存/派发，以及 `update():456–523`
收集 Trigger、先提交普通字段、返回 ID，是另外一组契约变化；迁入 Operations 并不必然要求
把这整套事务实现一起替换到当前框架。

**建议：** 保留宿主命令有身份、可查询、归属明确的方向；单独决定怎样从配置 Trigger 接到宿主。
明确受理成功、执行成功、插件稳态和落盘成功各自的含义。
本阶段不默认提供事务后受理保证；混合“配置更新 + 操作”是否拆成明确两步，应在此项讨论。

### 2.4 Operations 与 BackgroundTaskManager 有真实语义差异

**事实：** 当前 `app/core/background_tasks.py:158` 的 query 可重复读取状态，不消费结果；
`:170` 的 try_take 才一次性取值，不能把该组件概括为“一切查询都只能一次”。
该组件已有容量限制、超时、取消、结果期限和持有在途引用的关闭能力。

但来源 Operations 还保存 configUid、字段、owner、可取消标记及有限终态历史，
并按 owner 临时阻止受理；其 `shutdown():210` 对不可取消命令等待完成。
当前后台组 `_close():271` 会取消全部在途任务；注销后组不再受理，不能代替可恢复的 owner 暂停。
来源 Operations 则没有后台组现有的运行容量限制，不能因为保留 200 条终态就声称运行数有上限。

**建议：** 保留命令层的业务元数据与可重复查询；执行是否复用后台组另行决定。
如复用，必须解决不可取消命令、临时暂停/恢复与终态保留，不能让全局后台关闭绕过命令取消策略。
如保留来源 `_TriggerTask`，改为引用当前 `app.task.lifecycle.TaskBase` 即可继续评估，
不需要改 L1/L2 或 TaskBase。二者不能只按“都 create_task”判为重复框架。

### 2.5 配置根不仅有保存失败问题，创建失败也存在归属缺口

**事实一：** 来源 `_release_config():974–998` 吞掉 commit 和写盘异常，仍注销根、清除引用。
当前 `app/config/core/manager.py:205` 要求调用方确认该根落盘后再注销，
保存失败应留在可追踪、可恢复的状态。
直接复制来源代码会使尚未保存的数据离开正常保存/重试扫描集。

**事实二：** 来源 `enable():423` 调用 `config_cls.build(file=...)`，构造时即登记持久化根；
随后构造插件并执行 pre_enable，直到 `:468–469` 激活成功才写入 `record._config`。
当前 `app/config/core/entry.py:185` 同样在构造时登记根。
若插件构造、pre_enable 或 activate 抛错，清理函数只看 `record._config`，看不到这个新根。
pre_enable 的异常分支 `:446–449` 也没有注销它。重复尝试可留下多个指向同一文件的根；
若激活部分成功，还可能让失败实例继续参与保存。

**事实三：** 模型注释声称插件配置 UID 复用注册项，但来源 `build(file=...)` 未传 `uid=record.uid`。
不能把注释里的“同一 UID”当作已实现的 Operations 定位契约。

**建议：** 按构造、激活、挂载、释放四个阶段明确新根的所有者，并保护所有失败出口。
成功释放须确认保存完成；失败时保留什么状态、如何重试、是否需要定向保存，分别讨论。
UID 的定位方式也须统一，但不以共享 UID 自动替代节点身份核验。
这些是插件宿主自身的资源责任，无须为此建设通用外部副作用补偿框架。

### 2.6 暂停 Trigger 没有覆盖全部释放入口和在途调用

**事实一：** 来源 `disable():550`、`unload():653`、`reload():740` 的外层入口，
先进入 `_pause_operations`，再取管理器忙锁。
但 `uninstall():894–897` 直接取忙锁后调用 `unload(held=True)`；
后者及其内部 `disable(held=True)` 均跳过暂停。
因此，安装包卸载入口没有普通 unload 所具有的 owner 命令暂停/等待边界。

**事实二：** `_pause_operations` 只跟踪 Operations 内的 Trigger。
`app/api/plugin.py:296–345` 取出绑定 handler 后直接 await；
`app/plugin/services.py` 返回真实服务对象，不管理已取出的引用或在途调用。
与此同时，disable 直到 `plugin_manager.py:619–620` 才卸服务和 HTTP，
此前 `on_disable` 与配置释放已经执行。
一个在 await 中的 HTTP handler 可以与同插件的资源释放交错；卸挂载不会结束已开始的调用。

**建议：** 生命周期释放的准入与等待必须覆盖实际开放的入口。
卸载入口应与其他释放入口遵守同一顺序；HTTP、服务和插件独立后台任务的责任需明确。
可选择等待已受理调用结束，或在活动调用存在时拒绝释放，不能用“已暂停 Trigger”证明资源已空闲。
对于可长期持有的服务引用，还需明确调用方契约，不能声称注销注册表就能撤回既有引用。

### 2.7 HTTP 网关存在可重复执行业务的来源缺陷

**事实：** 来源 `app/api/plugin.py:328–345` 的同一个 try 同时覆盖签名检查、handler 调用与 await。
它在捕获 `TypeError/ValueError` 后再次执行 `handler(request)`。
对于接收 Request 的处理器，若第一次已执行副作用再抛这两类异常，第二次就会重复执行该副作用。
这是业务异常被误当成参数适配异常，不是网络重试需求。

**建议：** 参数调用方式在执行前确定，业务处理只调用一次，异常交给网关失败边界。
若本阶段开放声明式 HTTP，这一处应随迁入修正；不应等真实插件出现重复动作后再处理。
该项独立于第 1 节的配置事务一致性决定。

### 2.8 版本与发行依赖配套调整（迁移工作，非独立阻断项）

**事实：** 来源 `app/plugin/types.py:14` 的协议为 `6`，
SDK `plugins/auto_mas_core/pyproject.toml` 的发行版本为 `6.0.0`，
MUMU 示例声明 `auto_mas_core>=6,<7`。
但 `plugin_manager.py:121–137` 使用 `Config.VERSION` 合成同名发行包 METADATA：
来源应用版本为 5.6.2，当前 dev 为 5.8.0，两者均不满足示例声明的依赖范围。
loader 对协议主版本的检查不能替代 uv 的发行依赖解析。

`app/plugin/uv/precheck.py` 虽有 core 升版预检，生产调用点检索只发现包导出，
没有发现主程序更新流程实际调用它；不能把“提供 helper”报告为“更新已受兼容预检保护”。

**已确认原则：** 用户允许迁移时调整版本号；合成元数据、SDK 包版本、协议检查和插件依赖范围
应配套对齐，不要求保留来源的具体数值。数值不一致不再作为独立架构冲突或迁移阻断项。
“主程序更新是否实际调用兼容预检”仍是独立的接线事实，不能用调整版本号宣称该能力已接入；
它是否属于本阶段，随安装/更新能力范围核对。

### 2.9 路径、依赖和已有宿主接口是具体接线工作

**事实：** 当前 Config 明确区分 `source_path`、`resource_path` 与 `plugins_path`。
来源 `plugin_manager.py:112` 把内置 SDK 固定放在 cwd/plugins，
`:416` 从 cwd 拼配置目录；discover `:145` 读取当前不存在的 `Config.plugin_path`。
在 Runtime 的源码与用户目录分离布局中，内置 SDK 和用户安装插件不能用同一 cwd 假设定位。

来源还导入当前已移除的 `app.utils.tools/io/constants` 路径，
且 `to_pep440` 在当前工具中不存在；应按现有工具入口适配，不恢复一批旧路径别名。
`pyproject-metadata` 与 `watchdog` 在来源声明为生产依赖，当前未声明。
迁入 discover/watch 时需要同步真实生产依赖及锁文件，不能依赖本机碰巧安装。

来源插件 uv 层已支持 `AUTO_MAS_UV_EXE`，不是完全忽略 Runtime；
但初始化无条件执行 `uv.ensure()`，市场镜像又依赖不存在的 `setting.uv.preferred_mirror`。
是否让纯本地插件加载也以 uv 可用为前提，是启动行为取舍，不能当成既有 dev 保证。
当前可复用的 uv 查找仍分散在 MFW 等具体领域，不能未经归属判断就宣称已有通用 Runtime 服务可直接调用。

**建议：** 区分源码资源、用户插件、插件依赖安装目标和配置文件，沿真实宿主能力适配。
安装目标的第三方依赖与宿主解释器共享模块搜索空间，是否允许覆盖宿主依赖也需明确；
现有 `--target` 目录本身不构成进程或依赖隔离保证。

### 2.10 国际化与通知不止是改名单例名称

**事实：** 来源 discover `:264–266` 调用小写 i18n.invalidate，
PluginMeta 读取 `setting.language.locale`。
当前 `app/core/i18n.py` 使用 I18n、固定 AppLocale、`core.*` 命名空间、内容 revision 与一致快照，
并明确预留插件资源来源接入点；没有旧的 invalidate 方法，也没有对应全局语言配置。
来源刷新成功后照抄该调用，仍会在末尾失败。

来源 HostNotifications 从 `app.core` 导入小写 notify，
push_proxy_result 仍引用当前不存在的 `app.task.notify_core`；
SDK services 又导出当前不再存在于 app.services 的 Matomo/Notify/System/Updater。
当前通知实际归 `app/core/notify/`，已有目标选择、批次与后台发送生命周期。

**建议：** 让插件通知委托真实 Notify；避免复制整套旧通知系统。
插件语言资源应加入当前快照与命名空间契约，或明确本阶段仅支持哪些元数据展示；
不能加一个返回成功的空 invalidate 就声称插件翻译已生效。
前端语言与动态页面的具体迁移未在本轮审查，不据此自动扩大本阶段范围。

### 2.11 领域适配还有高影响行为，不能由基础框架迁入顺带决定

**事实：** 当前集合已有热态 add/remove/reload/replace_type，
来源适配器另依赖当前不存在的 register_initial_type/remove_initial_type，
配合“先插件类型登记、后领域配置激活”的启动顺序。
dev 当前启动直接按既有类型和引用关系完成配置加载，HTTP 契约也由专项联合类型派生。
仅向集合登记类，不会自动让既有创建接口、生成客户端及编辑器支持它。

此外，来源 `app/core/plugin_adapters.py:402–427` 在普通禁用时 remove_type 脚本及计划类型；
`:196–214` 对游戏也如此。当前 `app/config/core/collection.py:548` 明确该操作级联删除全部该类成员。
来源游戏重载 `plugin_adapters.py:156–163` 还会删除旧设备类型及其成员，再登记新类型。

**建议：** 这几项属于后续领域阶段的启动、数据保留和公开契约决定。
“一次性迁移、不做长期双轨”并不意味着用户已批准“禁用插件即删除托管/计划/设备配置”。
基础阶段可以先不启用这些领域路径，不能用假集合、删数据或整体覆盖 dev 模型来解除导入。

### 2.12 退出与最新 dev 增量的实际约束

**事实：** 来源退出使用 Operations、RuntimeTasks、committed 和 PluginRuntime；
当前 `main.py:549–617` 已协调任务、历史、屏幕资源、电源、下载、BackgroundTaskManager、Notify 和最终 flush。
来源 `Plugin.shutdown():233–255` 先 seal 服务，再调用依赖方的 on_teardown；
此时若收尾钩子重新通过 services.require 查询上游，会被拒绝。
保留服务引用的插件可能仍能清理，但不能假设所有收尾都可在 seal 后继续解析服务。

**建议：** 保留“退出不改启用意图、不 remove_type”的来源语义；
明确停止外部受理、排空命令/调用、插件 teardown、后台组关闭、通知关闭和 flush 的先后依赖。
若插件 teardown 允许通知或访问上游服务，相关能力必须活到使用结束。
不复制整个旧 main，不重建 ShutdownCoordinator，也不因插件接线重设电源策略。

**最新 dev 事实：** `bda55de47` 已恢复旧专项预下载。
`origin/dev:app/task/script_expander.py:48–59` 已持有 ScriptUpdateSession，
`:153–164` 的 `_make_prefetch_manager` 在 plugin_expander 非空时直接返回 None。
因此现在不能再把“L2 没有预下载”当作事实；但也不能声称未来插件已有预下载能力。
若后续绑定全局 plugin_expander 来逐个迁移专项，该条件会连未迁移的旧专项一起停止预下载。
这是未来逐专项接入时必须处理的混合路径冲突，基础发现/生命周期阶段尚不要求修改 L2。

### 2.13 下一轮讨论建议

本节已按第 3 节澄清修正。交接中的 8 项不应原样保留为 8 个独立决策：

1. 原第 2、3 项合并讨论操作受理、查询、取消、插件归属与执行承载。
2. 原第 5 项保留为动态类型注册与配置激活顺序的独立讨论。
3. 原第 6、7 项合并讨论插件资源完整生命周期，配置保存作为其中的具体释放条件。

Operations 与 BackgroundTaskManager 是否复用执行，应在第 1 项明确取消和查询语义后决定，
不预先锁定“全部合并”或“全部独立”的实现。
基础基类与必要声明同步迁移；领域配置的删除语义和混合预下载问题在对应实际接入之前解决，

### 4.2 第一项的讨论起点（建议，未确认）

本节记录讨论过程；当前采用的讨论方向见第 6 节。

事实链：Trigger 声明命令；来源 Operations 拥有受理身份、owner、重复请求判断、
查询和取消策略；当前 BackgroundTaskManager 拥有背景执行引用、限额、超时与结果提取。
这些职责可以分层组合，现有差异本身并不证明必须保留两套独立执行所有者。

建议先确定业务职责：

- 配置框架负责声明/校验触发值，并转交宿主；不执行插件业务编排，不新增提交后受理担保。
- Operations 保留来源的命令业务层：操作 ID、目标和 owner、受理/拒绝、同目标重复请求、
  查询、取消策略与有限历史。操作完成不自动表示配置文件已保存。
- BackgroundTaskManager 若作为实际执行承载，Operations 持有它的句柄，
  避免再持有另一份独立启动的 TaskBase 任务；插件自身的失败清理继续归插件生命周期。
  这是本轮倾向方案，不是已确认实现。

复用执行需要具体满足：取消前查询 cancellable；owner 暂停只作用于对应命令、并可恢复，
不拿永久注销任务组代替；命令的可重复历史查询不消费后台结果；关闭时先封禁 Operations 受理、
取消可取消命令并等待不可取消命令，再进入后台组全局关闭。
通过明确退出顺序即可处理正常关停的取消策略差异，不预先要求改写整个后台管理器。
完成回传、启动前取消和错误传播仍需在实际适配时核对，不能仅包装 source TaskBase.run()
就假定后台结果一致，因为 TaskBase 会捕获普通异常并记录到自身 error。

来源的另一种可选实现是 Operations 继续直接持有 _TriggerTask，普通后台工作仍归后台管理器；
它更接近来源，但保留独立的执行引用与关闭入口。
本次先讨论上述职责划分与执行承载取舍，不将清单中的其他议题顺带判为已解决。

### 4.3 第一项的来源核对：原设计差异与整合建议分开

本节补充来源依据，修正将“采用建议方案后需要适配”表述为“原设计已经冲突”的问题。
4.2 的复用执行方案始终只是建议，没有得到用户确认；它不应成为迁移前置要求。

**来源分支的既有设计：**

- 固定来源 `docs/zh/plugin-trigger-operations.md` 明确规定 TriggerDispatcher 注入、
  Operations 身份/查询/取消、同值在途去重、不可取消声明、owner 暂停与退出等待。

- 同一固定来源还存在 `app/runtime_tasks.py` 的 RuntimeTasks，面向短生命周期的独立后台工作，

- 来源 `main.py:471` 先 `Operations.shutdown()`，`:484` 后 `RuntimeTasks.shutdown()`。
  因而不可取消命令的等待策略，与普通后台任务的取消策略，在来源通过归属和退出顺序共存。

**当前 dev 的既有设计：**

- `docs/task-scheduler-implementation.md` 第 22 节记录 BackgroundTaskManager 替换原 runtime_tasks，
  为普通独立后台工作增加任务组、容量、超时、结果保留/唯一提取及可靠关闭；不改来源 TaskBase。
  实现为 `app/core/background_tasks.py`，随 `99534087a`（#1845）进入当前基线。
- 它当前服务通知、回放采集、启动预热等调用方，不保存配置字段、插件 owner 或前端操作历史。
  这些调用方需要有界持有执行和结果；该组件并未宣称实现来源的命令业务层。
- 当前配置 Trigger 则仍在 `app/config/core/entry.py:543` 直接调用处理器或创建异步 Task，
  尚未接 Operations；现有业务使用包括 `app/models/config/queue.py:265` 的循环计时重置。

**分别归类：**

1. Operations 的业务身份、查询、去重、取消与 owner 协调来自来源，不是本轮新设计。
2. 后台任务组的容量、结果提取/过期与关闭策略来自当前 dev，不是来源 Operations 的缺陷描述。
3. “Operations 保留业务层、改用 BackgroundTaskManager 实际执行”是本轮整合建议，
   并非来源已这样实现，也不是用户此前批准的统一执行要求。
4. 不可取消命令与后台组统一取消、命令历史与结果提取、临时 owner 暂停与永久注销，
   都是**选择该整合建议时**要适配的语义差异；两组件各自运行时并不存在这些替换冲突。
5. 真实迁移差异仍是当前 Trigger 尚未接宿主分发器、装饰器缺 cancellable、
   来源事务后受理与本轮已确认裁剪不同，以及来源旧后台注册表在 dev 已被替换。
   原样迁入来源整体配置文件会覆盖 dev 的既有能力，故应接接口并保留当前配置框架。
6. 原 Trigger 事务后受理是来源真实能力；本轮暂不迁入通用保证来自第 1 节用户决定，
   这项差异有明确的本次范围依据，不能说来源没有设计它，也不重新要求通用提交后机制。

**修正后的讨论基准：** 先沿来源的 Operations/TriggerDispatcher 设计接入并适配当前配置框架，
通用后台工作承接现有 BackgroundTaskManager；是否让 Operations 再复用后台执行，
作为有实际收益时再评估的可选整合，不因两处都创建 Task 就要求先统一。
此处修正的是建议和冲突的分类，尚未决定生产代码实现，也不撤销完整清单中的真实实现缺陷。

## 5. 最新 dev 的预下载与背景任务协作核实

2026-11-09 按用户要求 fetch，并将当前分支从 `99534087a` 快进至
`e27e53e969077e0634200d73cc1dfc7c84b69edc`。未创建新提交，两份未提交文档保留。
以下为该提交的静态源码事实；没有运行下载、专项或新增测试。

### 5.1 层级与所有权

- L1 受理并建立本轮托管清单，不启动预下载。
- L2 `app/task/script_expander.py:50` 为每个任务根创建 ScriptUpdateSession，
  在托管循环 `:126` 启动观察，`:139` 等待本轮预下载收敛，`:259` 取出候选 manager，
  `final_task():318` 最终关闭会话。
- 会话位于 `app/core/script_update.py`，负责选择后续可预取托管、校验身份与配置、
  临时取得目标托管的非级联 X 锁、保存候选和交接。
- `app/core/script_update_queue.py:74` 与 `:101` 直接创建 watcher/download asyncio Task，
  两者引用由该队列持有，生命周期由 L2 会话等待和取消；没有提交 BackgroundTaskManager。
- 实际版本检查和下载调用旧专项 manager.prefetch_script_update，安装仍由专项启动前入口负责。
  这是旧 manager 兼容路径的业务实现，不是新建一个 L3/L4 预下载 Worker。

因此，预下载是 **L2 所拥有、与当前托管并行的准备工作**，不是独立 L1 任务，
不是用户 L4 任务，也不是新的运行树节点。会话代码中“第三层适配器”的注释不能直接理解为
新调度 UserExpander 已经接入了预下载。公共展示写入 TaskItem.current.prefetch。

### 5.2 与 BackgroundTaskManager 的真实联系

下载主协程及候选交接没有使用后台组的 spawn/query/take。
候选由 ScriptUpdateSession._pending 持有，并由其 take/discard 交接或丢弃。

间接协作发生在进度回调：`script_update.py:233` 使用 manager.callbacks.submit，
把进度写入与 commit 交给旧同步/线程回调桥 LegacyCallbacks。
`app/task/legacy.py:86–95` 为该桥申请 BackgroundTaskManager 组，
以一个串行消费者执行回调，完成即释放；`:115–131` 提供 drain 和 close。
预下载完成或异常时会等待该桥结清，丢弃候选时关闭桥；成功交接的 manager 在后续执行收尾时关闭桥。

两个后台执行名额用于消费者结束与 done 回调之间的批次衔接，不表示并行下载两个托管。
普通通知、历史等其他背景组仍按其原有所有者运行，不拥有预下载结果。

### 5.3 时机、交接与取消

- 自动代理模式下选择后续首个符合条件的托管，每轮只准备一项；目标与当前托管同配置则不启动。
- 当前专项通过既有成功结果面报告首次成功；此后持续运行满 60 秒才开始预取，
  不以 L1 受理或托管启动时间作为起算点。
- 当前托管正常结束后，若下载已开始，L2 等其完成再进入后项；未开始的观察则直接结束。
  正常账号切换不取消；真正失败重试会清掉成功时刻、确认预取停止并丢弃旧候选后重新观察。
- 到目标执行时复核安装身份/更新策略/配置对象等；有效才交接同一个 manager，
  随后专项在原有保护内执行安装与启动，身份变化则丢弃候选。
- 普通预取失败记录提示，由后项启动前更新继续处理；取消等待清理和停写确认。
  FluxdownCancelUnconfirmed 不作为普通失败降级，保留异常并阻断下一托管。
- 应用退出在 `main.py:586` 先停止运行任务，在 `:608` 后关闭全局背景任务组。
  预下载主协程主要靠 L2 会话的停止/收尾回收，不能仅靠全局 BackgroundTaskManager.shutdown。

### 5.4 与插件迁移讨论的关系

该实例表明：后台运行不自动意味着由 BackgroundTaskManager 管理。
有明确上层所有者、必须在切换业务步骤前收敛的并行工作，当前由所属业务会话持有；
需要统一执行持有的旧回调消费者则委托背景组。
所以“都创建 asyncio Task”不能证明 Operations 和后台任务管理器必须合并。

`script_expander.py:155` 仍在全局 plugin_expander 非空时禁用旧专项预取工厂，
完整清单第 7 项的混合路径问题仍存在，没有因本次拉取而解决。

## 6. 第一项继续讨论：Operations 复用 core 背景任务

用户提出 Operations 可以改为使用 core 背景任务实现。本轮确认该组合技术上可行，
后续按这一方向细化；当前仅更新设计记录，未开始修改生产源码。

职责划分：

- Trigger 负责声明、校验并转交命令，沿用此前不增加通用提交后受理保证的决定。
- Operations 是命令业务层：持有目标、插件 owner、操作 ID 与后台句柄的关联，
  负责受理、去重/冲突、查询历史、可取消策略及 owner 暂停/恢复。
- core.BackgroundTaskManager 是实际执行所有者：通过任务组创建执行，持有 Task，
  管理容量、完成结果与取消等待。Operations 不再额外启动独立的 _TriggerTask 顶层任务。
- 插件业务的失败恢复和资源释放继续归插件生命周期；背景管理器不理解插件语义。

需要做的适配是正常整合工作，不构成二者无法组合的设计冲突：

1. 后台结果由 Operations 作为唯一业务消费者接收；命令查询读有限操作记录，
   不让前端查询消费后台结果。启动前取消、异常和清理结束也必须更新终态。
   现有后台接口的完成回传方式在实现前核对，不能只改成 spawn 就宣称链路完整。
2. Operations 检查 cancellable 后才请求后台句柄取消；暂停某插件只封禁其相关命令，
   不能用注销整个操作任务组代替可恢复暂停。
3. 不给不可取消命令叠加会绕过其策略的统一执行超时；应用退出先封闭 Operations，
   取消可取消命令并等待其余命令收尾，再关闭后台组。
4. 不保留 TaskBase 吞掉异常而后台却记录成功的包装方式；实际失败须准确进入后台结果和操作终态。
5. 不为该整合修改 L1/L2 或来源 TaskBase，也不将预下载强制改交背景组。

当前明确的是复用方向与职责；具体接口及清单其他议题不因本轮讨论自动视为完成。

当前基类的注销契约是先完成保存；注销后普通保存与 flush 都不会再扫描该根。
磁盘满、权限等实际 IO 错误不属于字段值校正，不能用配置默认机制代替保存完成。

迁入时须把根的持有与清理覆盖到构造/预检等真实失败出口，并保留“确认保存后注销”的条件。
保存失败后的操作故障状态与配置引用如何保留，是本组待定行为；不预设新增通用保存框架。
注册项 UID 与配置根 UID 的注释/实现不一致，作为定位契约修正处理，不单独立项新架构。

### 8.2 生命周期互斥不等于所有在途使用均已结束

来源 disable/unload/reload 的外层先暂停所属和下游 Operations，再取管理器锁；
uninstall():894–897 却先取锁后调用 unload(held=True)，实际跳过同一暂停入口。
这是可定位的入口遗漏，迁移时应统一，不需要额外创建一种卸载流程。

此外，Operations 只覆盖经它受理的命令。HTTP 网关直接 await 插件绑定方法，
服务注册表返回真实对象/方法；它们没有因某个 Operations 完成而自动停止。
当前 disable 在 on_disable 和配置释放后才卸 HTTP/服务。
若 HTTP 请求在 await 期间与禁用交错，就可能在插件释放资源后继续执行；
注销服务名也不能撤回调用方已拿到的引用。

需明确哪些使用由宿主跟踪并等待/取消，哪些由插件在钩子中停止，及能否因仍忙而拒绝释放。
这是一条使用与释放的契约，不自动要求增加通用租约/补偿框架。

### 8.3 退出语义与依赖资源的存活顺序

来源退出只执行 on_teardown，不改 enabled 意图、不 remove_type；此语义继续保留。
退出调用顺序需接入当前 ShutdownCoordinator、任务/历史关闭、背景任务组、Notify 和最终 flush，
不能整份搬回旧 main，也不能在插件还需要通知或后台执行时先关闭其依赖。
第 1 项已经决定 Operations 复用背景组，因此先处理操作受理与收尾，再进入全局背景关闭。

来源在调用 teardown 前 seal HTTP 和服务，这是明确设计，不直接判为实现错误。
它意味着收尾阶段 services.require 已拒绝新查询；插件可使用已经持有的资源，
若允许收尾时重新解析依赖则需要调整该约定。
这一点应核对使用契约，不以假想的钩子调用要求重写整个服务总线。

本组当前要对齐的是资源持有、保存完成与在途使用三个释放条件。
明确的根清理遗漏、保存吞错和 uninstall 漏暂停可随迁移修正；
对其他入口的统一等待范围、失败后的可恢复状态和退出依赖顺序再按具体行为讨论。

### 8.4 现有职责边界：宿主登记与插件内部资源

来源宿主已经负责：

- 配置根的构造/激活/保存/注销及注册表状态；
- 按 provides_services 声明登记和撤销服务方法，按 plugin_route 挂载和卸下 HTTP；
- requires 服务依赖的启用编排、下游优先禁用，以及生命周期互斥和钩子调用；
- 经 Operations 受理的命令身份、暂停、取消及等待；
- 适配器的宿主类型登记/锁预检/恢复，具体领域资源仍交其真实所有者。

插件已经负责：

- on_enable 内创建的业务连接、客户端、监听器、线程、进程及自建异步工作；
- on_disable/on_teardown 的释放，on_fail_cleanup 的部分启用失败清理；
- 每个命令/后台协程 finally 中的业务清理，以及外部写入/设备操作确实已停止的确认。

现有宿主不会枚举并自动关闭插件内部全部资源，也不会撤销调用方已取得的任意 Python 引用。
服务总线返回真实对象/方法，尚无通用在途调用登记。
当前 BackgroundTaskManager 只按任务组持有执行，没有插件 owner；来源 BasePlugin 也未绑定专属背景组。
因此“已调用钩子”不等于宿主已经替插件完成业务释放，“任务在背景组内”也不自动等于归属某插件。

requires 的依赖级联只覆盖硬依赖；来源 _downstream():1050–1066 不包含 wants。
wants 允许缺失/降级，不能被解释为长期持有一个服务引用期间始终保证提供者存活。

### 8.5 改进建议：宿主协调可识别的入口与执行，插件释放业务资源

以下方案已获用户确认，迁移时按此实施；尚未落地生产代码：

1. **宿主补齐已有责任。** 配置根从构造开始就有清理所有者，确认保存后才注销；
   禁用、重载、卸载统一进入停止受理/等待流程，修正 uninstall 绕过暂停。
   不以全局扫描 Task 或资源对象猜测插件归属。
2. **宿主统一协调公开入口。** Operations 保持已有管理；HTTP 网关在插件进入停止阶段后拒绝新请求，
   对已经进入插件方法的调用持有执行引用并等待其退出。
   声明式服务方法若也由宿主统一管理，应在暴露方法时提供调用包装，计入实际执行到完成的区间，
   而不只在 get/require 时检查；这是来源尚未提供的补充能力。
   普通对象引用、返回的资源句柄、流或方法中另行派生的工作不因包装而自动完成清理，仍须明确其所有者。
3. **让插件背景工作可登记归属。** 可由宿主向 BasePlugin 绑定属于当前插件实例的背景组入口，
   底层仍使用 core.BackgroundTaskManager；插件提交协程工厂，宿主在释放实例前封禁、取消并等待。
   此入口目前不存在，不能把背景组名称约定当作已经具备的 owner 管理。
   插件私自 create_task 的工作仍由插件自己持有、停止和等待，宿主不承诺自动找回。
4. **插件承担实际业务清理。** 网络客户端/文件/设备句柄/自建监听器/进程等由创建者释放；
   受管协程在 finally 中清理其资源，插件钩子负责实例级资源和未托管工作。
   宿主取消并等待协程，只证明该执行结束；线程、下载守护进程等是否停写仍由业务入口确认。
   重复清理要遵守所属资源的既有幂等约定，不恢复整份旧配置或重做通用副作用补偿。
5. **依赖与退出按生命周期衔接。** 先关闭下游使用者，再释放提供者；
   在途命令/调用及登记背景工作先收敛，再释放它们使用的连接与配置。
   应用退出仍调用 on_teardown 而不修改启用意图，通知、背景组和最终保存活到实际使用结束。
   若沿来源先 seal 服务再 teardown，插件收尾使用已有资源/句柄，不依赖重新查询服务；
   若需要放通生命周期内的跨插件调用，则须显式设计该调用契约，不能直接放开所有新业务受理。

以插件持有连接并执行下载为例：宿主拒绝新命令/HTTP、请求受管下载停止并等待，
下载协程 finally 完成停写及临时资源清理；插件钩子关闭实例连接和自有监听器；
宿主最后完成配置保存、撤销登记及实例释放。
若业务明确不可取消，宿主先等待完成，不能以强制关闭连接代替命令完成。

此建议明确的统一范围是宿主公开的调用入口、登记过的执行及宿主配置/类型资源；
插件自行创建且未登记的资源与外部状态正确性仍归插件。
不声称源实现已经覆盖建议的 HTTP/服务在途跟踪和插件专属背景入口。

### 10.1 来源安装方案已经明确

来源 `app/plugin/uv/ops.py:30` 按 AUTO_MAS_UV_EXE、Runtime tools 目录、PATH 找 uv，
不承担 uv 下载；`plugin_manager.initialize():110` 将 uv 可用作为初始化前置。

### 10.2 目录分开没有消除同进程依赖版本约束

--target 不直接改宿主环境原目录，但插件目录中的同名库可能成为后续 import 的优先来源；
已经导入的模块仍由同一个 sys.modules 持有。插件 reload 清自己的包，也不等于重新加载全部依赖。
因此插件与宿主、不同插件之间，仍要满足同进程下的依赖兼容条件。

例如假设宿主锁定库 X 的 1.x，而新插件要求 X 的 2.x：把 2.x 装到插件目录不能自动保证宿主继续兼容，
实际结果还可能受模块是否已导入及是否重启影响。这是受支持安装入口可能遇到的依赖冲突，
不是已经在用户环境复现的故障。
来源 install(package_spec) 没有显式将宿主 uv.lock 和全部已装插件作为共同约束传给解析器；
从该入口不能认定已有“所有包可共同运行”的保证。

建议保留来源同进程共享目录方案，同时按宿主依赖与全部保留插件约束共同校验；
无法共解时明确拒绝，不通过安装另一份同名依赖掩盖冲突。
若更新需要改变正在使用的依赖版本，应明确重新启动/切换的生效边界，
不能只重载插件包就报告整个新依赖环境已经生效。
这是本项待决定的共存规则，不自动引入另一种插件进程架构。

### 10.3 来源的 core 升级预检有实现，但没有业务调用点

来源 `app/plugin/uv/precheck.py` 在临时目录构造拟定 core 版本的 stub wheel，
使用 uv --dry-run 检查单个插件与该 core 版本能否解析。
precheck_core_bump 逐个检查注册表插件，输出冲突信息。
对固定来源 app/ 和 main.py 的调用点检索仅见定义、内部调用和包导出，
没有插件安装或主程序更新流程实际调用它；这是尚未接线，不是来源没有实现预检能力。

逐个插件与 core 版本可解析，也不等于全部插件共同可解析；
stub 的 METADATA 未包含真实宿主完整依赖，不能将它称作完整运行环境验证。
loader 的 PLUGIN_API_VERSION 主版本检查属于导入阶段协议检查，是另一层契约。

建议迁入来源预检能力并连接实际更新前置阶段，明确检查目标版本和保留插件集合；
确定不兼容与网络失败/信息不足分别报告，不能把未完成检查当作已兼容。
完整共同依赖验证与 core 协议/版本验证分别保留其真实含义。

本轮只核对这些生产入口，未执行真实 Runtime 更新，未修改 Electron 行为。

### 10.5 本项建议边界

- uv 定位、共享安装目录、发行元数据及装卸包机制沿来源迁入，使用当前 Config 路径与 Runtime 工具；
- uv 仍可作为插件系统初始化前置，不额外设计无 uv 降级启动；
- 在安装/升级入口明确同进程的宿主 + 全部插件依赖约束及变更生效边界；
- 接通来源已有 core 兼容预检，区分它与完整依赖共解、实际运行兼容验证；
- 与当前 Runtime/应用更新的真实入口衔接，检查未完成不报告成功，已确定不兼容不强行继续。

真正需要对齐的是共享依赖的允许变更范围和更新前校验行为；
查找 uv、版本数值和工具 import 路径属于普通迁移适配，不分别立项新框架。

### 10.6 用户决定：升级业务前移，后端保留下载管理与预检

用户明确批准上一轮回复的前两条建议：沿来源的 uv、共享目录与装卸包方案迁移，
安装/升级时共同校验宿主和保留插件的依赖，拒绝明确不兼容变更。
同时要求同步调整 core 升级流程：绝大部分业务移到前端，后端提供基于背景任务管理模块的
下载管理接口，其他更新操作均由前端执行；更新预检也提供独立后端接口供前端调用。
这取代此前仅在旧后端更新器中插入预检调用的接线建议。

**前端职责：**

- 版本检查与比较、发布信息/更新日志读取、更新源与目标包选择、更新策略及流程状态；
- 调用后端预检、创建并观察下载、根据结果继续/取消/重试；
- 更新包校验、解压、替换/安装、Runtime 调用、停止/启动后端、重连和最终更新结果；
- 手动、自动及后台准备等相关入口由同一前端更新业务约束，不能只给单一弹窗增加预检。

前端侧包括 Renderer 与 Electron 主进程：Renderer 处理交互/流程展示，
文件、进程、安装器与 Runtime 能力沿 Electron 主进程和已有 IPC 执行，不让 Renderer 直接使用 Node。
复用现有 runtimeUpdateService 等真实更新能力，必要底层操作仍可由其调用 Runtime 完成；
Python 后端不再拥有应用升级的整体编排。

**后端下载管理职责：**

- 使用 core.BackgroundTaskManager 承载实际下载，复用现有内置/FluxDown 下载传输能力；
- 接受前端确定的下载请求，返回下载 ID，提供状态/进度/结果的只读查询及取消接口；
- 下载业务层持有必要的任务句柄和查询记录，由后端唯一消费者接收后台结果，
  前端查询不消费结果，刷新/重连不因一次性 take 清掉下载状态；
- 取消与传输收尾保持既有停写确认，不能仅发 cancel 就报告已经停止；
- 产物归下载业务及后续前端处理，不随背景结果过期自动删除；
- 不在下载接口内隐式检查应用版本、选择升级方案、解压安装、重启程序或决定更新成功。

下载管理的公开能力是启动、查询、列表和取消等传输管理；具体路由/字段随接口实现统一确定，
不继续扩展旧 UpdateHandler 的完整后端升级流程。

**后端预检职责：**

- 前端传入确定的目标 core 版本和必要目标依赖信息，后端结合实际插件注册表/已装版本检查；
- 复用来源预检，并与已确定的共同依赖约束对应，返回明确的可升级、不兼容或检查未完成结果及原因；
- 只执行检查，不替前端启动安装或修改当前环境；不把网络失败/元数据不足伪装成兼容；
- 返回结果对应目标与插件集合，目标或插件集合变化时重新检查，不复用失效结论。

**流程约束：**

前端确定更新目标 → 调用后端预检、提交下载并取得所需产物 → 校验产物与目标一致 →
在确认预检仍对应当前目标/插件集合后停止后端 → 前端侧完成安装/Runtime 切换 → 重启并核实版本。
预检和依赖旧后端提供的下载必须在停机前完成；不保留先停后端再调用它下载/预检的顺序。
预检与下载的具体交互先后可按真实流程组织，但不能跳过上述生效前置条件。

**迁移范围：**

当前源码中的 /api/update/check、下载状态/取消/切源、/install、UpdateHandler，以及
useUpdateChecker/useUpdateDownload/Runtime 更新入口的调用归属需要配套整理；
前端调用点与生成客户端同步迁移，不能保留两套应用升级控制器并行运行。
具体旧接口兼容与 WS/MCP 契约随实施统一处理，不用返回成功的空接口掩盖功能迁出。

本次升级编排指 MAS 应用/core 与 Runtime 更新。插件包安装及依赖管理继续归插件宿主；
专项启动前更新和 L2 预下载保留已确认的执行归属，复用下载传输不等于强制改为独立后台下载任务。
保留已有下载历史、进度、源切换/取消及 Runtime 失败恢复等实际能力，在新所有者内接入。

第 5 项方案据此确定，尚未修改生产源码或宣称接口已经可用。下一项为第 6 项适配器配置保留语义。

## 11. 第 6 项：禁用、卸载和重载适配器时的配置保留（已决定）

本项是来源生命周期语义需要确认，不是来源与当前 ConfigCollection 的 API 冲突。
两边 remove_type 均删除该类型的全部成员，再撤销类型登记；reload_type 则导出载荷、换类重建，
保留成员 UID 与顺序。因此不能把 remove_type 理解成只隐藏插件入口。

### 11.1 核实到的来源行为

固定来源仍为 8196f7a8058e8aafb943dc336f3308109befe43f：

- app/core/plugin_adapters.py 的 ScriptAdapterRuntime.system_disable（402 起）：
  普通禁用对 ScriptConfig 调 remove_type，连同嵌套用户配置删除；若声明专用计划类型，
  也对 PlanConfig 调 remove_type。GameAdapterRuntime.system_disable（196 起）同样删除游戏配置及嵌套设备。
  重新启用只是 add_type，不从已删除数据中恢复原条目。
- 卸载包经 plugin_manager.uninstall → unload → 普通禁用，因而启用中的适配器也经过上述路径。
- 重载语境的 system_disable 跳过删除；脚本与专用计划随后 reload_type，保留 UID。
  游戏配置自身也 reload_type，但其设备集合随后 remove_type 旧设备类，再 add_type 新设备类（148–172）。
- plugins/mumu_adapter/src/mumu_adapter/control.py 的 _sync_devices（135 起）会重新发现设备，
  以官方 index 匹配当前集合；清空后 add 未传 uid，使用集合默认 uuid4，故不恢复旧设备 UID。
  refresh 本身只打开同步时间窗口，不能据此声称重载返回时已经恢复设备。
- app/models/config/script.py 的 game_id 使用 SET_DEFAULT；设备删除信号会重校验 game_device_id（181 起），
  设备不在集合时归一为“未选择”。因此重新发现同一模拟器实例不自动恢复原来的脚本设备绑定。
- 普通插件自身配置根另走 plugin_manager._release_config：保存文件、注销根、释放实例，
  不等于删除配置文件。本项不能泛化为“所有插件禁用都会删自己的配置”。

上述删除是 MAS 配置集合成员的删除，不代表删除脚本本体、模拟器实例或其安装目录。
来源钩子注释明确标出级联删除，说明这里有主动选择的实现；源码不足以证明其产品设计动机。

### 11.2 决策价值与初次建议（历史讨论，非最终方案）

具体影响：用户建了脚本、账号和专用计划后，普通禁用对应适配器可能清掉这些 MAS 条目；
游戏适配器重载则可能出现游戏配置还在、设备重新出现、脚本原设备选择被清空的情况。
这与“暂时停止插件”或“替换代码后继续使用原配置”的预期存在需要确认的差异。
若用户认可来源的删除语义，本项不要求另造配置保留框架。

建议边界：禁用停止业务、保留配置与身份；重载保留游戏、设备、脚本及计划的 UID 和关联；
卸载插件包与清理用户配置分开处理，数据清理作为明确动作。
设备运行状态和重新发现结果可刷新，不能将有引用的设备身份一并当作可随意丢弃的缓存。

若选择保留，不能只删掉 system_disable 中的 remove_type 调用：来源类型登记位于启用阶段，
下次启动禁用插件不登记类型，业务集合便缺少还原这些条目的类型。
需明确禁用时是否仍加载并登记配置类型，以及卸包后如何保存其数据；具体方案随领域接入设计。
这不重新引入第 2 项已排除的通用异常值降级框架，也不默认批准新增原始载荷保留机制。

本节保留初次建议的讨论范围；游戏重载随后已确认，最终决定见 11.5，未改生产源码。

### 11.3 用户决定：游戏重载通过 reload_type 保留身份

用户明确建议游戏重载与托管重载一致，通过 reload_type 保留身份，据此确定该方向。
游戏主配置及设备的 UID、持久化字段、集合顺序和仍有效的关联在重载中保留；
取消来源游戏重载中对旧设备 remove_type → add_type → 重新发现的身份重建路径。

reload_type 保留的是配置身份和载荷，不是旧 Python 对象、控制器、订阅或后台协程。
沿第 8 节的停止受理、锁检查、执行收敛与资源清理顺序释放旧运行资源，
用新类重建后重新装配控制器、实例订阅和刷新工作，再恢复业务受理。
运行状态由新控制器重新获取，不凭旧持久化状态宣称设备当前在线。

来源 MuMuGame 已声明 devices: ConfigCollection[MuMuDevice] = collection(MuMuDevice)。
此类结构通过 GameConfig.reload_type(new_game_class) 从原载荷重建嵌套设备时，
即可使用新设备类和原设备 UID，不必随后再对同一设备集合 remove_type/add_type，
也不要求重复执行一次已经完成的设备 reload_type。
若其他适配器单独动态登记设备类，则由该装配路径在还原前提供正确类型，
独立换设备类时使用设备集合的 reload_type；具体接线须以其声明结构为准。
正常重载遵循现有按类名识别类型的契约，类型改名/领域结构变更另走明确的数据转换。

重载不应发出“设备已删除”来清空仍有效的脚本关联。
之后实际设备发现确认某设备被用户删除时，仍沿真正的设备删除规则处理。

### 11.4 禁用与卸载的具体建议（历史讨论，已撤回）

**禁用保留配置：**插件包仍安装、配置类仍可加载；宿主保留配置类型、成员、UID、字段及引用，
并正常保存。停止业务入口、调度候选、插件控制器和背景工作；已有计划不删除，
其触发时明确报告适配器不可用，不静默跳过，也不自动重新启用插件。
配置仍可查看，先限制为只读，重新启用后恢复使用；不要求禁用期间执行插件业务校验或编辑操作。
宿主自身的显式配置删除不属于插件业务执行，仍遵守已有锁和引用删除规则。

为支持重启后仍保留配置，类型声明登记应属于插件加载阶段，而不是只在启用时执行；
启用阶段负责创建运行实例、挂控制器和业务服务。配置激活不得隐式启用业务。
来源 GameManager.on_add 当前要求已启用的声明并装配控制器，需配套区分配置恢复与运行装配；
不能只保留类型却照搬这一运行时前提。触发器/HTTP/服务/调度入口统一检查可用性，
保留配置不能成为绕过第 8 节停止受理的路径。以上均为待确认建议。

**卸载分开清理的收窄建议：**上一轮“卸载包与删除配置分开”尚未规定卸包后数据存在哪里。
真正允许卸包后继续保留配置，须额外设计缺失插件类型的数据保存/展示/重装恢复及跨插件引用处理；
仅导出一份备份再 remove_type 仍会使活动集合里的关联被清空，不能宣称已完整保留。
本轮建议不提前增加这套能力：没有领域配置和依赖使用者时允许正常卸包；
存在配置时由用户先明确清理或迁移配置，再卸包；需要保留配置时使用禁用。
删除动作列出实际涉及的脚本、账号、游戏设备、专用计划及关联影响，沿既有删除规则执行，
不能在普通禁用或卸包内部隐式清空。普通插件自身持久化配置文件也不随卸包默认删除。

这项收窄建议避免为包卸载直接扩展配置基类；如果用户要求“卸包也完整保留并可重装恢复”，
再将其作为明确生命周期能力设计，不混入异常值自动修正或通用加载失败兜底。

本节为当时提出的建议，用户随后选择沿来源语义并要求卸载删除全部配置，故不实施本节方案。

### 11.5 用户最终决定：其他沿来源语义，卸载删除全部配置

用户明确：“我建议其他设计保留来源语义，卸载时删除所有配置”。
本项据此收敛为以下最终方案，不覆盖前面其他议题已经确认的宿主生命周期等决定：

1. **重载：**沿 11.3 已确认方向，游戏重载与托管重载一致，通过 reload_type 保留配置身份。
   不保留来源游戏重载时删除设备再重新发现的路径。
2. **普通禁用：**本项其余设计沿来源。适配器仍调用 remove_type 并级联删除对应领域配置，
   包括脚本的嵌套账号、游戏的嵌套设备，以及插件声明的专用计划类型成员；
   关联按现有引用/删除规则处理，再次启用不自动恢复被删条目。
   普通插件自身配置根仍沿来源保存并释放，禁用不等于卸包时清除其配置文件。
3. **卸载：**删除该插件全部所属配置，包括上述领域配置与嵌套成员、插件自身持久化配置文件；
   即使插件已经禁用、配置根已经释放，也须清理其遗留配置文件，不能只清内存根。
   “所有”限定于该插件所属配置；共享配置根只删除所属成员，不删除其他插件或宿主的数据，
   对其他配置的引用影响遵循既有规则。脚本本体、模拟器实例及其安装目录不因配置清理自动删除。

撤回 11.2、11.4 中禁用保留类型/条目、禁用期间只读、为此把类型登记前移到加载阶段、
卸载前要求用户单独清理/迁移，以及卸包保留/重装恢复的建议。
不引入缺失插件类型归档或通用原始载荷保留机制；不把“已经存在配置”作为本项新增卸载阻断条件。
继续遵守已确认的锁检查、依赖处理、停止受理和资源收尾，不绕过合法删除与保存顺序。

第 6 项决策完成，仅更新设计和交接记录，尚未修改生产源码或执行实际配置删除。

## 12. 第 7 项：旧专项与插件混合运行时的预下载（双源方向已决定，接口待设计）

本轮继续使用 e27e53e969077e0634200d73cc1dfc7c84b69edc 工作区与固定来源 8196f7a8 核对。
应用 mas-task-scheduler 及其框架参考区分 L2 兼容分派、锁和预下载生命周期。
以下是静态事实及建议，没有执行专项、下载或修改生产源码。

### 12.1 冲突位置与来源

当前 dev 的 _TaskManager 默认 plugin_expander=None，main.py 绑定旧 manager 工厂；
生产入口尚未绑定真实插件解析器，所以不能说当前普通旧专项已经因插件安装而全部失去预下载。
此处的 plugin_expander 是全局执行解析回调，不等于“安装了某个插件”的标志。

app/task/script_expander.py 的两条路径判断粒度不同：

- 正式执行在 213–255 逐个托管调用 plugin_expander；解析返回 None 时释放探测锁，
  再进入旧 manager，说明设计允许同一宿主混合处理新旧托管。
- _make_prefetch_manager 在 155 只要全局 plugin_expander 非空就 return None，
  尚未检查目标托管是否属于旧工厂、是否已有 prefetch_script_update。

因此，在后续宿主绑定真实插件解析器之后，即使当前与下一项均为未迁移的旧专项，
其旧预下载也会被全局关闭；正式执行仍可走旧 manager，启动前更新仍在，只是提前下载机会丢失。
这是当前混合接线的判断过粗，并非来源插件与预下载在架构上不能共存。
来源插件主链按 Plugin.script_types 的真实声明派发 L3，没有当前这套旧 manager 预下载会话接线；
当前 dev 则保留旧专项增强，两者不能靠全局开启/关闭插件模式来拼接。

### 12.2 相关边界不能遗漏

- app/core/script_update.py 的 watch 先选后续首个 `_eligible` 托管，稍后才创建预取 manager。
  _eligible 当前未判断目标预取能力，所以选中插件或无预取能力的类型后，不能声称会自动继续扫描更远目标。
- 首次成功由 script_update_queue.report_script_task_completed 通知，当前调用来自 MAA、HSR、MaaEnd、
  MaaFW 的旧成功结果面；UserExpander 没有通用对应调用。仅删除 155 的全局判断，
  也不能让“当前插件 → 后续旧专项”自动获得同样的首次成功后 60 秒触发能力。
- 不以插件进入 prepare、进程启动或任意一个 L4 返回推断已成功；若要接通该组合，
  应在真实插件结果契约上明确首次成功与真正失败重试的通知位置。
- 只读能力判断不能调用 plugin_expander 来试构造执行器；后者契约要求当前配置已锁定，
  预取能力应通过真实类型声明/旧工厂归属判断，并与正式分派一致，防止旧 manager 处理插件目标。

### 12.3 初次建议处理范围（历史建议，后续以 12.4 为准）

1. 按目标托管的实际执行归属判断能否预取，取消“全局有插件解析器就禁用全部旧预取”的规则。
   未迁移旧类型沿旧工厂和既有 prefetch_script_update，插件类型不能被当成旧 manager 构造。
2. 保留现有可达的旧专项 → 旧专项预下载；目标为尚无预取能力的插件时跳过提前下载，
   由其正常准备入口处理，不凭空报告插件已支持预下载。
   本轮不额外引入越过中间托管扫描更远候选的策略；若以后采用，需配套调整 pending 的保留/消费规则。
3. 当前托管为插件时，真实成功/重试通知随该专项接入明确；在接通前说明其运行中不会触发旧预取，
   不能拿“启动前仍能更新”冒充预下载完成。新插件自身的预取能力也随逐专项迁移决定。
4. 预下载仍由 L2 会话持有：保持一项候选、首次成功后持续运行 60 秒、交接前身份复核、
   使用同一个准备好的 manager，以及取消等待真实停写等既有边界。版本检查/下载由实际专项能力执行，
   安装留在目标启动前受保护的流程，不借本项提前重写 L2 或增加运行树节点。
5. 第 5 项已确定的前端应用更新与后端下载 API 不改变这里的专项预取归属；
   也不因其是并行下载，就强制交给独立应用级背景任务或前端编排。

本项的直接修正是混合分派接线；插件成功通知与插件自身预取是逐专项接入内容。
上述为初次建议；用户后续明确要求预下载直接接入插件系统，后续范围以 12.4 为准。

### 12.4 用户决定：插件预下载声明插槽与双源适配

用户要求预下载接入插件系统，托管专项类插件添加声明预下载业务的插槽，
预下载服务转为双源适配：旧专项 manager 能力与插件预下载声明。
这取代 12.3 中仅先保留旧专项、插件能力整体留到逐专项才讨论的推进范围。
插件接口由用户继续参与设计；本轮先说明现有接口，不能把命名、签名或结果模型当成已批准。

### 12.5 现有预下载声明与运行契约的核实

1. **没有显式预下载声明槽。** 当前 app/task/registration.py 的 ScriptRegistration
   登记 manager_factory，build_script_capabilities 生成配置类型 → 工厂索引；
   并无 prefetch 字段。来源 app/plugin/base/script.py 的 ScriptTypeDecl
   声明配置类、用户类、L3 类、计划类、模式与模拟器期望构造器，也没有预下载插槽。
2. **支持性由方法存在判断。** app/task/script_expander.py:153–164
   按真实配置类型找工厂，构造 manager，然后 hasattr(manager, "prefetch_script_update")。
   没有独立 Protocol/抽象预取基类，也未同时校验 discard 方法。
3. **实际要求的两个方法。** async prefetch_script_update(self) -> None
   执行检查与提前下载，async discard_prefetched_update(self) -> None 释放未交接候选；
   服务直接调用这两个名字。无显式参数，manager 经 script_info.script_id 访问 Config.ScriptConfig，
   并使用现有全局下载设置。返回 None 不能区分下载完成、无需更新或设置关闭而跳过。
4. **结果通过实例/缓存交接。** `_pending` 保存运行节点 UID、身份快照及同一个 manager；
   take 校验后把 manager 交给正常执行。MAA 在 `_github_update_candidate` 中保留候选，
   HSR 在 `_prefetched_updates` 中按引擎保存，MaaEnd/Whimbox 使用 `_update_candidate`，
   MaaFW 保存发现结果/身份/完整包标记并复用共享下载缓存。没有统一候选结果对象或统一 apply 方法；
   正常启动准备在各专项原入口内消费候选、复核/安装。
5. **宿主身份与锁。** ScriptUpdateSession._identity 硬编码旧配置的安装路径、Update、
   部分 Embedded 字段及全局下载设置，包含配置类型与对象身份；不是由各专项声明身份算法。
   实际预取前服务申请目标配置非级联 X 锁，下载阶段结束释放，交接时再校验身份。
   ScriptUpdateRequest 只是更新调用身份，不是预取声明或候选结果。
6. **进度为环境能力。** download_observer ContextVar 注入 (Path, downloaded, total, speed)
   同步回调，download_method 提供实际传输方式；旧 callbacks.submit/drain/close
   把进度写入 TaskItem.current.prefetch。并非 prefetch 方法参数上的 report 回调。
7. **触发条件独立于目标预取声明。** 当前专项真实成功处调用 report_script_task_completed()；
   真正失败重试处可 await report_script_task_retrying()，由 L2 绑定到会话。
   该通知决定什么时候开始准备下一项，不等同于下一项提供 prefetch 方法。
8. **隐式契约确有缺口。** 实现 prefetch_script_update 的旧 manager 有 MAA、HSR、MaaEnd、
   Whimbox、MaaFWEmbeddedManager。前四者有 discard 方法，MaaFWEmbeddedManager 及其
   NotificationTaskBase/TaskExecuteBase 继承链未实现 discard_prefetched_update，
   但服务丢弃/异常路径仍直接调用它。此为静态核实到的接口不完整，未执行该异常路径。

后续新接口需区分声明、一次预取的输入/结果、消费/丢弃与当前执行成功通知，
但本节只核实旧契约，不提前确定具体新接口。仍未改生产源码。

## 13. 当前预下载完整模型与后续设计顺序

用户随后要求：先设计统一下载管理业务，预下载未来基于统一下载管理执行业务，
再据此设计插件预下载业务接口。本节先还原现有模型，不把未来模型当作已经实现。
核实基线为当前 HEAD e27e53e96；这是静态源码核实，未启动下载/专项或执行真实取消。
采用 mas-task-scheduler、mas-data-model 和模块边界规范区分调度、传输、配置和资源所有权。

### 13.1 整体模型与执行持有者

L1 建立本轮 TaskItem → TaskScriptItem → TaskUserItem 清单；预下载不另建运行树节点。
每个 L2 ScriptExpander 持有一个 ScriptUpdateSession，会话持有 ScriptUpdateQueue 与单个候选。
队列直接持有 `_watcher` 与 `_download` 两个 asyncio.Task：前者观察当前托管与成功时刻，
后者执行目标 manager 的检查/准备/下载。候选里的 manager 不在预下载阶段启动完整 _execute_task。

“在后台并行执行”与“交给 BackgroundTaskManager 执行”须区分：
现有 _watcher/_download 由 asyncio.create_task 创建，不调用背景任务管理器 spawn/take。
BackgroundTaskManager 间接承载 LegacyCallbacks 的串行进度提交消费者，retain_result=False；
该背景组结果不是下载产物，也不持有预取候选。
一个 L2 会话最多一个正在准备/待交接候选；多个任务根各有会话，不存在统一下载并发配额或全局等待队列。

### 13.2 调度对象与内部数据

- TaskItem：本轮任务根，持有托管运行清单和 current.prefetch 展示状态。
- TaskScriptItem：某次托管运行节点，有独立运行 UID；info.script_id 指向持久化托管配置，
  _config_ref 保存建树时对象的弱引用，用来发现删除/替换。同一托管重复执行不是同一个运行节点。
- ScriptUpdateSession：_task、make_manager、process_scope、_completed_at、_retrying、_queue、_pending。
  _completed_at 是单调时钟的首次成功时间；_pending 的真实形状是
  tuple[运行节点UID, 身份快照object, TaskExecuteBase实例] | None，不是下载任务记录。
- ScriptUpdateQueue：_watcher、_download 两个可空 asyncio.Task，不存 URL、包列表或可查询的业务状态。
- ScriptUpdateRequest：冻结 dataclass，只有 script_id、script_type、可空 engine；
  用于 run_script_update 的操作归属与进程作用域，不是 URL 请求、任务句柄或结果模型。
- 专项 manager：保存自身预取结果；两个隐式方法与不同专项的结果形式见 12.5。

### 13.3 选择目标与触发

1. L2 在运行当前托管前调用 watch(current, next_index)，并绑定成功/重试 ContextVar 通知。
2. 仅 AUTO_PROXY 自动代理模式可预取。watch 在 L1 固定清单后续部分选择首个 `_eligible` 托管：
   配置仍存在且对象身份一致、未锁定、有运行用户节点、符合本轮星期条件。
   不在这里检查所有用户的动态可执行性，也不先判定该类型是否有预取方法。
3. 若该首个候选对应当前同一托管配置，则本轮不预取；不继续向后搜索。
   目标 manager 不支持预取或插件全局判断拒绝时，本轮也不会自动改选更远候选。
4. watcher 每 0.5 秒检查当前托管。当前为“等待”继续等，“运行”时等待首次真实成功后满 60 秒；
   未达到门槛就已结束/失败则不启动预下载。正常切号不重置成功时刻；真正失败重试主动取消、
   等待停写、丢弃候选、清空成功时刻后重新观察。通知需要专项真实结果面调用，不由宿主推断。

### 13.4 执行、锁和身份有效期

_prefetch 重新判断候选身份，构造旧 manager，申请目标托管非级联 X 锁；锁不可得则不预取。
锁在检查/下载阶段持有，结束后释放，不一直锁到目标正式启动；不在预取阶段锁目标全部用户。
会话设置 download_observer 与 current_process_scope，再 await run_script_update(request, manager.prefetch_script_update)。
run_script_update 在有进程作用域时进入 scope.updating，跟踪真实更新执行，异常/取消原样交还。
L2 提供的 process_scope 当前来自正在执行的旧 manager，供其更新停止检查与强清理协作。

身份快照包含持久化托管 ID、配置 Python 类型、配置对象身份，以及以下字段：
Info 的 Path/RootPath/M7APath/SRAPath，完整 Update，Embedded 的 FollowSource/Report，
全局 Downloader/FluxdownPath/FluxdownSegments/FluxdownServerMode/FluxdownTakeoverAll/
GitHubMirror/MirrorChyanCDK/ProxyAddress/Source。
下载历史、账号运行记录、普通展示字段不纳入身份，防止输出变化让候选自己失效。
准备结束与正式 take 都复核，变化则丢弃。此身份是当前旧配置字段的硬编码投影，不是业务提供者声明。
各专项在消费时还可能复核本地版本/谱系等；宿主配置身份校验不替代这些实际安装前检查。

### 13.5 更新业务、文件传输与候选产物

预取方法负责版本/来源/更新策略判断及下载；安装留在目标正常启动前的受保护流程。
一个候选可涉及多个文件、资源包或多个引擎，也可能无需更新、设置关闭而直接返回。
方法返回 None，宿主只知道协程完成，不知道下载文件数或是否确有可安装更新。

准备结果由不同专项持有，不是统一产物模型：

- MAA GitHub PreparedUpdate：release、version、package、digest；其他来源/资源可使用各自缓存。
- HSR PreparedUpdate：root、DiscoveryResult、package、digest；manager 按引擎保存字典。
- MaaEnd PreparedUpdate：root、当前版本/架构信息、目标版本、arch、destination、size、digest；
  内部 prepare 还可能返回提示字符串，由正常启动路径重新检查。
- Whimbox PreparedUpdate：root、target、current、repairing、wheel、packages、hashes，
  可包含一组依赖包；内部 prepare 同样可返回字符串。
- MaaFW：manager 保存完整包标记、项目身份与版本发现结果，文件留在更新核心共享缓存。

典型传输链为专项工具 → download_script_package → core.downloads.download_file →
services.common.update.fluxdown.download_file → FluxDown 或内置 httpx。
并非所有专项传输都完全经过同一条链；MaaFW 使用其更新核心 download_resumable，并桥接公开进度。
不能把“统一更新操作包装器”误称为已经统一管理全部文件传输任务。

download_script_package 的参数是 URL、目标 Path、source、timeout、proxy、progress、可注入 http_download，
返回下载字节数 int。下载器默认选项 FluxdownOptions 含 downloader/source/cli_path/segments/server_mode/cli_search_dirs。
source 在每次下载启动时冻结；Mirror 酱用内置下载，GitHub 按既有接管策略选择。
FluxDown 的续传映射、目标文件跨进程锁及安全回退由传输层负责，不是 L2 的候选去重/全局排队机制。
哈希校验、缓存发布、候选结构和安装复核由实际专项更新业务负责，并不因下载返回字节数就自动完成。

### 13.6 展示与历史模型

唯一预下载展示入口为 TaskItem.current.prefetch: WSTaskPrefetchData | None，字段全部是字符串：
target、status、package、method、progress、size、rate。
target 是名称，不是下载 ID；progress/size/rate 已格式化，不是原始字节与数值速度。
status 没有统一状态枚举，可能为检查/准备、下载中、准备完成、取消、准备失败、配置变化已丢弃等文案。

底层 DownloadProgress 为 async (downloaded:int, total:int, speed:float) -> None；
预取观察者为 sync (path:Path, downloaded:int, total:int, speed:float) -> None。
total 不知道时按未知大小展示。预取回调通常按 1 秒节流，实际传输方式变化可立即更新；
通过 LegacyCallbacks.submit 在串行消费者中 commit，返回前 drain，丢弃/执行结束后 close。
TaskItem 字段经现有任务更新推送与快照提供给前端，不另设预取查询/取消 API。
一次展示当前文件而非候选的全部文件及总进度；take/discard 清空展示，前端任务完成也清除。

下载历史在 setting.Update.LastUpdateHistory 中保留最近 50 条 FluxdownRecord：
url、destination、size、duration_ms、segments、proxy、checksum、status、error、timestamp。
这是传输层写出的历史，不是每个预取候选一条记录，也不是统一的活动下载列表；
不能假定所有专项的所有内置下载路径都记录同样历史。
会话、协程和 manager 内候选均为内存态，进程重启不恢复这段调度；各下载缓存/续传映射另有持久化。

### 13.7 概念状态与结果交接

以下是按代码行为归纳的状态，不是源码里已有的预下载状态枚举：

选择候选 → 等当前运行/首次成功 → 满足 60 秒 → 检查/准备/下载 → 等待交接 → take 交给目标 → 启动前复核/安装。
任一阶段可因取消、配置变化或业务失败进入收敛/丢弃；无需更新与主动跳过目前仍表现为方法正常返回。

当前托管结束时，未开始下载的观察直接取消；已开始下载则 L2 等待其完成后才进入下一托管。
take(script_run_uid) 一次取走 _pending；目标运行 UID 和身份一致才返回同一个 manager，
否则调用其 discard 并关闭回调桥。实际运行随后绑定 history/context，执行 manager._execute_task。
结果由 manager 与其更新工具在正常启动流程消费，不存在公共 consume/apply 接口。
会话拥有候选到交接为止，交接后归执行中的专项；共享缓存是否保留由所属业务决定。

### 13.8 取消、故障与退出

普通预取故障清理后记录提示，当前托管继续；目标以后仍走正常启动前更新。
取消必须等待 asyncio.Task、下载线程/子进程/daemon 等真正收敛后再切换，不能只发送 cancel。
FluxdownCancelUnconfirmed 表示可能仍在写入，不当作普通取消或可降级失败；
队列保留带异常的 watcher 以持续阻断交接，L2 最终记录错误，防止后续任务在不明写入状态下启动。
不在未确认停写时清空文件或改用另一个下载器写同一目标。

L2 final_task 调用 session.close，取消观察/下载并丢弃未交接候选，随后完成锁、历史等收尾。
应用退出先停止调度任务（main.py:586），后关闭 BackgroundTaskManager（:608）；
只关闭背景组不能回收预下载主协程。候选临时文件按专项 discard 规则清理，共享缓存另归原业务，
不根据“后台结果过期”统一删文件。MaaFW 缺少配套 discard 方法的接口缺口仍按 12.5 记录。

### 13.9 与未来统一下载管理的区分

当前实际存在的是“每轮预取会话 + 一次更新准备业务 + 多次文件传输 + 不透明候选”，
没有统一下载业务 ID、活动列表、可查询结果记录、文件集合总进度、全局等待队列、统一暂停/恢复接口。
L2 固定清单也不是下载管理队列，单候选不是全局并发限制。

后续顺序按用户要求：先设计统一下载管理的业务/任务/文件/结果/取消边界，
明确它如何基于背景任务管理器执行并保留可查询记录，再设计插件预下载插槽与旧专项适配。
需要替换执行承载时保留现有业务时机、身份校验、产物消费与真实停写担保；
不能仅把 create_task 改成 spawn 就宣称获得完整下载管理。
具体新模型、接口及字段尚未决定，本文不提前批准或实现。

### 14.1 可以沿用的职责划分

统一声明的业务语义、旧固定入口/新插件声明双源适配、L2 提前提交与等待、
统一下载中心基于背景任务执行、manager/L3 负责使用文件及安装，整体方向可行。
不需要将完整旧 manager 包成新的 L3/L4，也不要求为每个文件增加任务运行树节点。
URL 可以继续作为查找键，不因评估而默认要求改成 UUID。

### 14.2 单 URL 的适用范围与实际多文件需求

None 只应表示当前确实不需要预下载；网络失败、元数据失败、读取失败应按实际错误表达，
不能返回 None 冒充没有需求。单 URL 返回值可支撑单文件可选预取，但不能完整覆盖现有能力：
MAA 同时准备程序与资源，HSR 可准备两个引擎，Whimbox prepare 还会下载/构建 wheel 依赖。
Whimbox 的依赖准备不是固定 URL 列表即可机械替换的操作；可留在消费文件后的业务准备阶段，
但这会改变提前准备范围，应明确保留策略，不能宣称原预下载能力已全部迁移。

若目标是覆盖现有多文件预取，建议业务输出支持有用途标识的多个请求，空集合表示没有需求；
L2 仍逐 URL 提交、下载中心仍管理单文件，安装决策与业务元信息保留在专项侧。
至少要明确版本、摘要、架构、来源等由谁保存/重取/复核。仅传路径不能自动恢复原 PreparedUpdate。
当前传输还区分 MirrorChyan 与 GitHub、代理、超时等，URL 本身不能可靠表达这些选项。
允许下载中心统一采用固定策略是可行取舍，但若要保留现有按来源策略，就要给请求补传输上下文。

### 14.3 无锁需求发现与锁内消费

无锁做只读发现可行，前提是不写配置、不安装、不启动游戏/设备，也不把后续业务写入带入此入口。
若需要 await 网络查询，应先读取所需字段形成一次请求快照，避免 await 前后读取到混合配置；
这不是复制配置后整体回写，也不要求为整批网络发现持配置锁。
配置基类能校正字段值，不会替调用方保证某个旧 URL 一直匹配后续被修改的通道、架构、路径或插件实例。

每个托管执行前先确认配置仍存在且对象身份有效，再取非级联托管锁；锁内核实准备需求仍适用，
变化时重新解析/提交，明确新旧引用释放；不能把早先 URL 的产物不加复核写进参数就交给业务。
在托管业务锁内等待下载可沿用户方案，但应明确这期间配置不可编辑/禁用/重载；
不要持配置事务等待网络，也不提前锁用户或设备。
旧 manager 自持递归锁，L2 不能像插件路径一样持另一份托管锁直接调用它；
需要在旧兼容入口明确等待与最终复核位置，继续遵守唯一锁所有者。

### 14.4 批量提前提交是明确的调度策略替换

收集本轮全部需求后提交，会替换原首次成功后 60 秒、每轮只预取一项的节奏。
这是可选择的新设计，不因不同于旧代码而必须拒绝，但会提前请求可能不执行的项，
改变网络占用与授权/额度消耗，并可能遇到后续项临时 URL 过期、需求解析耗时阻塞首项等情况。
应说明需求解析的串并行及单项失败影响；某一远期项发现失败不应未经决定就阻止其他独立托管运行。
下载排队时遇到授权过期，由需求业务重新获取 URL，不能把旧短期 URL 当作永不过期的身份。

背景任务组有 max_running/max_retained，spawn 满额时拒绝，没有等待队列。
若“提交全部成功”表示已经受理，下载中心需持有自己的待执行队列，空位出现再 spawn；
若选择容量不足返回 False，L2 必须处理未受理项，不能认为全部 URL 已进入下载。
每个 URL 单独受理，重复 URL 的去重与 owner 关联须在 await 前或既有同步边界内完成。

### 14.5 URL 缓存与共享文件所有权

以 URL 去重可以保留，但不能把 URL 等同于业务版本/架构/安装身份，也不能去掉签名参数后碰撞合并。
同 URL 复用要求请求的表示及预期产物兼容；动态 latest 地址应在业务消费前验证，
失败记录要允许明确重新请求，不能永久占据 URL 缓存。不同任务、前端更新可能同时使用同一 URL。

具体可达问题：任务根 A/B 请求同一 URL，共用一个本地文件；A 结束后 cleanup(URL) 直接删文件，
B 随后收到的 Path 就失效。建议在 URL 条目上登记实际 owner（可直接用现有任务根运行 UID），
同 owner 的重复请求幂等；final 释放本轮 owner，最后一个使用者释放后再取消/等待/删除。
其他 owner 仍需要时只释放当前使用者，不取消共享执行。业务消费共享原件应保持只读，
需要移动/改写/删除时使用自己的副本，或通过明确接管转移文件所有权。
下载中心不因等待方取消而自动取消共享下载，L2 final 必须继续释放本轮已成功受理的所有引用。

### 14.6 查询、等待与结果记录

请求 bool 可以保留，但需定义 True 包括“新受理/已在下载/已有成功缓存”，
重复请求不自动覆盖失败或偷偷重复建立 owner；False 表示未受理并由调用方处理。
query 的 Path/None 若无错误通道，就无法区分进行中、未提交、失败、取消或已清理。
至少定义未知 URL 与终态失败的错误行为；作为未来前端下载管理接口，建议有明确状态、
可空路径、错误、数值进度的只读记录，等待成功才返回 Path，失败/取消/未知则结束并明确报告。
不允许失败任务查询永久 None、等待永久阻塞。等待方取消不自动撤销其他使用者的下载。

BackgroundTaskGroup.try_take/wait_take 只允许结果提取一次，结果还有 TTL（默认 300 秒）。
下载中心应是唯一背景结果消费者，并自行保存 URL 对应的状态和文件记录；
多次查询/多个等待者读取该记录，不直接争抢背景 take，文件有效期也不随背景 TTL 隐式结束。

### 14.7 运行树参数的传递边界

TaskParams 是 JSON 值字典，可承载路径字符串；不直接放 pathlib.Path、后台句柄或插件实例。
宿主可在 TaskScriptItem.info.params 中使用保留键，写入按用途标识的路径映射，
再 commit 并创建 manager/L3 上下文；业务元信息的具体保存位置尚需决定。
不能让外部自定义参数覆盖宿主解析的真实下载结果。

当前 TaskContext.with_params 使用 deepcopy 替换整组参数，并不跨层合并；
L4 构造时会以用户节点参数替换托管上下文参数。
因此“写入信息树参数即可全层自动收到”不成立；若只供 manager/L3 消费则可沿此边界，
若要 L4 直接使用须显式传递，不借预下载顺便恢复未批准的全树参数隐式合并。

### 14.8 清理、停写确认与前端应用更新的衔接

cleanup 成功应意味着相关后台执行和底层写入者已经退出、可删除文件已删、缓存条目已回收；
不能只发 cancel 后立即删文件。失败应保留可定位记录与未确认写入所有权，不能移除记录伪装成功。
manager/L3 的安装/恢复/读取完成前，final 不能提前释放最后一个使用者。
应用级背景任务不继承原 TaskProcessScope，下载中心需实际承担下载进程/线程/daemon 的停止确认，
不能继续依赖旧 manager 的退出顺便清理；复用既有传输层的目标锁和停写处理。

普通任务 final 只释放自己所属 URL；全局 ALL 限于管理中心关闭流程：
停止接纳新请求 → 各任务完整收尾并释放使用 → 停止/等待中心下载 → 清理中心所属文件 → 注销背景组。
不能在任一任务 final 里清理全局 ALL，也不能等全局背景管理器先失去执行记录才做传输收尾。

另一个与已确认需求直接相关的边界：10.6 已确定前端先从后端下载应用包，再停后端、安装、重启。
若后端退出 cleanup ALL 把该包也删掉，前端将无法完成安装。
建议前端在停后端前把更新产物明确接管/复制到其拥有的更新目录，
下载中心退出只清理仍归自己管理的临时文件；不能把 ALL 解读成删除已转交的应用升级产物。

### 14.9 评估结论与下一步

保留用户的主职责划分。优先决定单文件接口是否覆盖全部现有预取，以及 URL 共享文件的 owner/释放契约；
再确定状态/错误、请求参数、批量排队、配置新鲜度与退出产物接管。
上述都是当前可达调用及既有能力推导出的具体问题，不要求建立通用外部副作用补偿或新目录预约框架。
用户原方案及本节修订建议均处于评估阶段；未选定最终新签名，未实施代码或新增运行测试。

## 15. 用户补充决定与剩余接口边界

本节记录用户对第 14 节的后续修正，优先于第 14 节中的原草案与未确认建议。
用户要求补充这些决定后继续评估问题，没有要求本轮实施生产代码。
用户随后逐条确认或修正，最终行为以 15.7 为准；15.2–15.6 保留当时讨论记录，不作未决事项重复询问。

### 15.1 已明确的决定

1. 预下载检查返回 list，替代 None/单 URL，当前业务含义为一组需要预取的 URL；空列表表示无需求。
   旧专项固定方法名、新专项插件声明，保持同业务语义，具体函数名与同步/异步签名仍待定。
2. L2 首轮无锁收集本轮需求、批量申请；每个托管取锁后、等待下载之前再调用同一检查接口。
   需求不变则等待；有新增 URL 则补申请再等待。当前已不再需要的旧 URL 不提前释放，
   统一在本 L2 最终收尾释放，因此 L2 需要记录本轮成功申请的 URL 集合/对应申请次数。
3. 下载中心申请/清理 URL 使用引用计数。引用清零不立即删文件；本地缓存总文件体积超限时，
   只清理引用计数为零的缓存。不再把普通 L2 收尾等同于立即物理删除。
4. L2 批量申请被拒绝时等待一段时间再申请，直至受理；重试间隔数值及关闭/取消边界尚未给出。
5. 查询/等待返回值需区分状态并补容错；网络波动导致的失败重试，无法解决的失败明确报错，
   后续托管不接收失败预下载的 path，正常业务准备仍由 manager/L3 处理。
6. 下载结果通过任务信息树参数传给 manager/L3，确认不需要自动传到 L4。
7. 前端在停后端前移动应用更新包；缓存清理发现文件已不存在也视为该文件已清理。
   再次获取缓存内容前检查文件，文件已不存在则重新下载并返回对应状态。

具体缓存上限、回收顺序、重试次数/期限和最终公开返回模型尚未定稿，不能填为用户已选定的数值。

### 15.2 引用计数与本 L2 台账（待确认的实施细节）

建议每个 L2 对成功受理的唯一 URL 只持有一份引用，初次列表先去重；锁后复查
只为“当前需求中、本 L2 尚未成功申请”的 URL 增加引用。同一 L2 内多个托管/多次复查不重复计数，
旧 URL 保留到该 L2 final。若选择每次申请都计数，则台账必须是次数而非简单 set，最终逐次释放。
拒绝受理不计数；查询/等待/缺失文件重下不再次增加已有引用。
成功受理与本 L2 入账应在不会被取消打断的状态更新边界内成对完成；
部分 URL 成功后取消/异常，final 仍须释放全部已受理引用。final 重入不得重复减计数。

### 15.3 受理重试、下载重试与不可继续的错误（待细化）

容量暂满按用户决定等待重试；管理中心已关闭、任务已取消或配置已删除/替换时，
继续等待受理不可能完成原业务，应结束对应等待。现有背景组对容量满与 closing 都返回拒绝，
下载中心应区分原因，而非对所有 False 无限重试。
网络重试由下载中心统一执行，多个等待者不各自再次启动下载；
须给出重试间隔及累计次数/期限，持续断网最终产生明确失败，不永久卡住托管锁。
调用方取消不作为网络故障重试，也不自动取消其他使用者仍在等待的共享下载。

“失败后不给 path 继续正常准备”只适用于底层已收敛的普通传输失败。
FluxdownWriterUnconfirmed/FluxdownCancelUnconfirmed 仍可能有 daemon 写入，
按已核实的现有保证必须阻断后续执行和目标文件复用；不能落入普通无 path 分支。
身份信息/文件校验/实际安装安全是否允许继续由消费业务负责，不因下载失败就宣称安全。

### 15.4 缓存回收与前端移包（待细化）

仅 refcount=0 不足以允许删除仍在写入的条目：应同时确认该条目没有在途下载、续传、校验或移交操作，
或者先取消并等待停写再删除。重新申请与选中回收之间应有原子状态边界，
防止刚增加引用就被另一协程删除；无需为此扩大为全应用目录预约框架。

建议按最近使用顺序回收零引用且已收敛的缓存，降到限制以内；在下载完成和引用释放时检查额度。
若全是仍在使用的文件，缓存只能暂时超限，不能删引用非零文件；这是回收目标，不是绝对磁盘上限。
不要额外引入“引用缓存超限便永久拒绝同一 L2 后续请求”的准入条件，否则全部请求未提交完、
业务又未开始释放引用，可能造成自我等待。

前端移动共享缓存原件前应确保自己是唯一使用者，或者先建立独立副本再移动副本；
“后续查询发现丢失会重下”不能保护其他已经取得 Path、正在读取/安装的使用者。
移包与引用释放的先后应明确，不能先释放后让回收器与移动操作竞争。
物理删除遇文件不存在为成功，但访问失败、仍有写入者不能同样报告成功；
缺失文件须同步更新字节统计与成功缓存状态，不能只忽略 unlink 错误仍返回旧 path。

后续获取发现文件缺失时，将原成功缓存转为重新下载状态；同 URL 多个获取者只启动同一次重下。
当前轮等待者等待这一轮结果，旧完成事件/旧成功记录不能让新 wait 立即返回已丢失的路径。
存在且完整的文件才可报告成功；版本/摘要校验继续按专项消费契约进行。

### 15.5 URL 身份、结果映射与查询/等待模型（待细化）

引用计数保护文件生命周期，不证明同 URL 永远对应同一产物。
建议检查接口返回指向确定版本/架构的 URL；可变 latest 地址的版本/摘要有效性由专项明确校验，
临时授权过期按实际需求业务重新获取，不简单把旧授权地址永久当作成功缓存。
原传输层的来源、代理、超时、下载器选择仍须明确归属；不能只因 URL 列表解决多文件就默认为来源策略问题已解决。

建议 manager/L3 参数使用 URL → 成功路径字符串的映射，避免 list 对齐在去重、重排、部分失败后错位。
当前需求已删除的旧 URL 不再传给业务，仅留本 L2 收尾台账。失败 URL 不提供 path，但保留可查询的失败原因。
若业务要求整组文件全成功才使用，或允许部分成功，需在接口里明确；当前用户尚未选定整组原子消费策略。

建议 query 非阻塞返回当前状态/可空 path/可空错误/进度；wait 订阅当前下载轮次直到成功或明确失败，
不能把失败与进行中都表示为 None。未知 URL 要明确表示不存在；取消须区分等待方取消与下载本身取消。
状态值和字段名尚未定稿。背景结果仍由下载中心唯一消费，自有 URL 记录支持反复查询与多个等待者。

### 15.6 退出与跨启动缓存的接续点（仍需明确）

原草案要求退出前清理 ALL，本轮新增零引用保留、超限回收，但没有明确是否取消退出全删。
若仍退出全删，则缓存只在当前进程生命周期复用；若保留到下次启动，需恢复 URL/文件索引、
核对磁盘并重置上一进程的活动计数。不能把两种选择混成“已有持久缓存恢复”。
无论采用哪种缓存期限，退出都应先停止受理、停止各 L2 并释放引用、停止/等待下载，
最后按选定策略处理缓存和注销背景组；应用升级包须已移交前端，不能被退出清理删除。

本轮已记录用户在 15.1 的决定；15.2–15.6 是尚待确认的细节建议及剩余边界。
总体结构可继续细化，无须推翻。当前仍为设计讨论，未修改生产代码或执行实际下载/清理。

### 15.7 用户逐项确认：计数、取消、缓存与退出的最终契约

用户对上一轮七项逐项答复：第 1–3 项按建议执行；第 4 项明确零计数即最后使用者取消，
不允许零引用下载继续运行；第 5 项前端改复制；第 6 项采用 URL 映射并要求独立参数 key；
第 7 项明确 ALL 仅在程序退出调用，中止全部下载、删除全部缓存。
据此确认以下行为，不把历史疑问再次列为新决策门槛：

1. **L2 引用台账。** 每个 L2 以唯一 URL 集合记录成功持有的引用；首次检查去重，
   锁后复查只为本 L2 尚未成功持有的新增 URL 申请。已不需要的旧 URL 不提前释放，
   final 统一各释放一次。拒绝受理不计数，查询/等待/缺失重下不重复计数；
   取消、部分成功和 final 重入均遵守成对持有/释放，不能漏减或重复减。
2. **受理及网络重试。** 暂时容量满则等待后重试，直到受理或原业务被取消/失效；
   管理器关闭不再重试。网络波动由下载中心统一退避重试，并有累计次数/期限，持续失败形成明确终态。
   需求检查自身失败同样明确处理，不返回空列表伪装无需求；调用方取消不是网络故障。
   下载中心唯一消费背景结果，自有记录供反复查询与多个等待者读取。
3. **失败分流。** 已确认停写的普通终态失败报错，不向后续 manager/L3 传失败文件路径，
   仍由其正常准备流程决定如何继续。FluxDown 等未确认停写的错误维持阻断，
   不能进入无 path 后继续下载/安装的分支。
4. **普通清理含取消语义。** 清理某 URL 先释放对应引用；未清零时不影响其他使用者。
   归零表示最后一个使用者取消：若有在途下载，立即请求取消并等待底层真正停写；
   计数归零后不继续执行该下载，也不自动网络重试。只有确认停止才报告清理完成。
   已成功下载的完整文件归零后先留作缓存，超总文件体积限制时只回收零引用缓存。
   缓存容量使用 `Config.setting.download.cache_mb`，单位 MB，范围 256～9999，默认 1024；
   回收时直接读取当前配置并换算字节，不在下载中心初始化时保存容量副本。
   取消产生的部分文件不冒充成功缓存，再次申请时按传输层已有续传/重新下载规则处理。
   15.4 与上一轮回复所说“零引用仍在写入”不构成另一个需要选策略的场景：
   这里已有明确的取消和等待收敛顺序，实施时据此保证状态一致即可。
5. **前端复制应用包。** 前端停后端前把更新包复制到自身拥有的更新目录，
   确认复制完成后再释放下载引用与停止后端；不移动或改写其他使用者共享的缓存原件。
   后端退出全删缓存不会影响前端持有的独立副本。
6. **路径映射与状态。** 给 manager/L3 的运行参数在一个宿主保留的专门 key 下放整个
   URL → 成功路径字符串字典，不能把 URL 直接铺在参数根字典上，也不能覆盖其他自定义参数。
   只包含锁后当前仍需要且下载成功的 URL；历史需求只留 L2 收尾台账，失败项不传 path。
   参数提交后再创建/更新 manager/L3 上下文，不自动向 L4 合并。
   query 非阻塞给出状态/可空路径/可空错误/进度；wait 等到当前下载轮次成功或明确失败，
   未知 URL、等待方取消和下载取消分别有明确结果，具体模型字段名在接口落地时统一。
   命中缓存前检查文件，缺失则撤销旧成功结果、合并同 URL 的重新下载，返回实际新状态；
   已有引用不因重下重复增加。物理删除发现文件不存在视为完成，并同步条目与体积统计。
7. **ALL 只用于退出。** ALL 不受普通单 URL 零引用保留策略限制；程序退出时停止接纳请求，
   中止全部下载流程并等待停写，删除全部下载缓存、清空记录、注销专属背景组。
   各 L2 final 只释放自己的 URL，不调用 ALL。已在前端的应用更新副本不属于后端下载缓存。
   不建立跨正常退出的缓存复用及持久活动引用恢复方案；15.6 的两种退出策略至此已选定全删。

在以上行为范围内第 7 项核心方案已收敛。参数 key 的具体名字、接口/状态的具体命名、
缓存大小与重试数值尚未写为固定值，属于后续落地细化；不能编造用户已经指定的数值。
本轮完成设计/交接记录更新，未修改生产代码，也未执行下载、复制或清理操作。

## 17. 用户决定：下载器覆写与 RID/哈希文件身份

用户明确要求申请时允许覆写渠道选择，默认 FluxDown 优先；文件基于 rid，
缺失则用哈希，再缺失则用 null 视为同一文件；再次进入先检查，发生修改则重下并切换状态，
本地文件名基于 rid 区分，旧文件先不删。第 16 节两项兼容问题据此确定处理方向。
本轮更新设计与交接文档，尚未修改生产代码或发起下载。

### 17.1 下载器策略

- 下载中心申请入口携带可选下载器覆写参数，缺省采用 FluxDown 优先策略；
  “优先”沿真实传输能力保留可用性判断、回退与停写确认，不等同于强制只能运行 FluxDown。
- 调用方可显式选择内置下载器等已有支持方式。该参数描述下载传输方式，
  不与插件包发布通道或稳定/测试版本混为一谈；具体参数命名可复用已有 downloader。
- 需要特定方式的业务通过该参数声明，例如沿现有 MirrorChyan 行为时显式选择 builtin，
  不要求下载中心从 CDN URL 猜测业务来源。
- 本轮变更只影响传输选项，不替业务选择发布版本、安装方案或更新来源；
  不在同一产物已有受管下载执行时因另一个请求的偏好就隐式启动第二份并行写入。

### 17.2 需求描述与有效文件身份

原先纯 URL 不足以携带本轮用户指定的信息，预检查仍返回 list，元素应携带下载需求描述：
URL、可空 rid、可空文件 hash、可选下载器覆写。空列表仍表示无需求。
旧固定方法与新插件插槽返回同语义结构；具体模型名及字段类型随接口定义统一，
不能要求下载中心隐式从尚未下载的文件中取得请求时就需要的 hash。

有效内容身份按以下优先级计算：

1. rid 存在：使用 rid。
2. rid 不存在而文件 hash 存在：使用文件 hash。
3. 两者均不存在：使用 null，按同一 URL 下同一个文件处理。

rid 在此按调用方提供的文件内容身份记录，不擅自等同于某个来源框架已有的项目级 mirrorchyan_rid。
hash 指调用方已知的文件内容哈希，不用 URL 字符串哈希冒充内容新鲜度。
实现可区分 rid/hash/null 的身份类别，避免不同类别的相同字面值误判为相同身份。
RID 优先时不因为另外一个可选 hash 改变就擅自改变用户指定的身份规则。

null 是真实的缺省占位：同 URL 且有效身份一直为 null 时，视作同一文件；
不额外假定后台会探测远端内容变化或添加隐式 TTL。不同 URL 不因身份都是 null 被合并。

### 17.3 再次申请、锁后复查与状态切换

再次申请/锁后复查不再只比较 URL 集合，还比较有效内容身份：

- 同 URL、同有效身份且成功文件存在：复用对应下载/缓存；仍在执行时合并等待。
- 同 URL 的有效身份变化：按新身份启动新一轮下载，公开状态切换为实际新执行状态，
  成功前不返回旧身份的 path 冒充新结果。
- 同身份但成功文件已经不存在：按 15.7 重新下载并更新状态，不继续暴露旧成功路径。

L2 仍按每唯一 URL 持有一份引用；但“已持有该 URL”不能导致跳过有效身份复核。
对本 L2 已持有 URL 的需求更新/重新验证，不重复增加引用，final 仍只释放一次；
真正新增的 URL 才按既定准入/重试规则申请引用。
当前托管只等待锁后最新需求对应的产物，历史需求与旧产物留到既定收尾/缓存规则处理。

同 URL 不同身份可同时被不同任务使用，查询/等待必须关联本次需求的有效身份/执行轮次，
不能让旧轮次完成事件、错误或 path 覆盖新轮次状态，也不能让新申请把旧使用者等待的结果改成别的产物。
URL 仍作为顶层查找键，内部保留对应文件身份及执行记录；具体通过参数或申请记录绑定随接口落地。

### 17.4 本地命名与旧文件保留

缓存路径必须体现 URL 归属与有效内容身份，RID 存在时以 RID 区分文件，
缺失时以文件 hash 区分，再缺失使用 null 对应的身份命名。
不同 URL 的路径空间分开，不能因它们 RID 相同或都为 null 而碰撞；
原始 rid/hash 字面值的安全编码属于路径生成实现，不直接作为任意路径片段使用。

新身份下载使用独立本地文件，不覆盖旧身份文件。已发布且可能仍被使用的旧文件先不删，
保持此前返回给 manager/L3 的路径有效；未完成下载不作为成功文件发布。
“先不删”不等于永久保留：仍归第 15.7 的引用/缓存体积规则管理，
不能回收仍被使用的旧产物；退出 ALL 仍中止全部下载并删除全部下载缓存。
前端继续复制更新包至自己的目录，不移动共享缓存原件。

第 7 项新增的来源策略与可变 URL 缓存问题已有明确用户决定，后续按第 15.7 与本节一起落实。
具体方法签名、状态字段名、参数 key 名称、缓存容量和重试数值尚未固定，不新增审批门槛。

## 20. 最后一项：插件 HTTP 网关业务异常触发重复调用

本项对应完整清单第 10 项，来源实现缺陷已列为迁入时直接修正，
不是来源与当前宿主必须二选一的架构冲突。本轮核实固定来源 8196f7a8 的 app/api/plugin.py:328–355，
应用 API 契约、函数设计和异常处理规范说明实际问题，未改生产代码。

### 20.1 触发原因

来源网关同时支持无参 handler 与接收 Request 的 handler，先 inspect.signature 判断调用形式。
但它将签名检查、handler(...) 以及 await result 全放在同一个 try 内，
except (TypeError, ValueError) 随后再次执行 handler(request)。

因此被捕获的不只是签名检查错误，也包括业务执行和异步等待期间抛出的 TypeError/ValueError。
例如接收 request 的方法先调用外部操作，再因业务值问题抛 ValueError，
网关会执行同一方法第二次；第二次再次失败后外层才记录并返回错误。
一次 HTTP 请求可能已产生两次业务副作用，最终响应失败也不能说明业务没有执行。
无参方法抛同类业务异常时，还可能被第二次错误传参产生的异常覆盖，丢失原始失败原因。

### 20.2 迁入时的直接修正

- 在进入业务方法之前确定调用约定，可在路由收集/挂载时解析并保存无参/Request 注入方式，
  必要参数绑定检查也在执行前完成。保留需要支持的同步/异步方法。
- 签名读取/参数绑定的错误只在对应窄范围内处理；不能包住 handler 的调用或 await。
- 分派按已确定的参数调用 handler，并且只 await 这一次得到的结果。
  业务 TypeError/ValueError 与其他业务异常一样进入统一错误处理，不重新尝试另一种传参形式。
- 无法确定的调用约定应按公开契约明确处理，不通过执行一次有副作用的方法来探测它怎么调用。
- 仍遵守第 8 节的停止受理与在途 HTTP 跟踪，执行结束/失败/取消后释放该次调用引用。

这消除的是网关异常兜底造成的主动二次调用，不扩大为跨请求幂等、事务补偿、
网络端到端仅执行一次保证，也不恢复第 0 项已关闭的通用外部副作用回退框架。

遥测沿用原任务观察者，本轮不改变用户流程或增加上报。


## 25. MAA 唯一插件实现（2026-11-12）

MAA 全量迁入 `plugins/maa_adapter`，删除旧任务目录与宿主 MAA 模型/注册。模型保持原持久类型名，输入载荷转换 `UserData` 为插件 `users`；计划、账号与托管身份保留。专属前端和词条由插件维护，宿主构建收集入口，现阶段仍随桌面前端交付。

ScriptTypeDecl 声明真实配置类型、执行模式与已有任务插槽；公共配置 CRUD 按已登记真实类型操作。账号创建直接使用 users 集合已收窄的用户类型，不另建配置处理器。计划创建与筛选使用 plan_type 对应的实际类型名，引用由字段 ref 声明负责；配置恢复由插件自己的服务和 API 提供，不向插件管理器登记池表。类型化 HTTP 路由通过调用门装卸，插件声明原有 MCP 端点的暴露意图，核心不持有 MAA 专项工具列表。配置契约生成器区分仅大小写不同的组名，避免 Windows 文件冲突。

配置处理器、恢复池工厂、额外计划创建标识/消费方/字段路径均不属于来源 `8196f7a8` 的原始 `ScriptTypeDecl` 设计，已从通用声明移除，不以另一组回调或插件基类钩子替代。`activity_game` 仍衔接首页活动展示与活动提醒。脚本配置类声明统一命名为 `script_type`，计划配置类声明统一命名为 `plan_type`，宿主运行时及 SDK 使用同一套名称。

移除 `config_handler` 及其 SDK 包装，不将旧配置 CRUD 的回调表改造成另一套插件基类钩子。宿主只使用已声明的配置类型和基类方法，插件内部负责配置业务：MAA 保存准备覆写既有 `ConfigEntry.update()`，网络等待在提交保护范围之外，提交前同步复核绑定和服务器；原生来源互斥由 `MaaUserConfig` 的字段信号约束，直接配置提交也生效；目录由已有 `UserEntry.info.config_path` 的只读属性提供。执行和资源操作仍归插件 L3/L4，本轮不改变调度基类。`ScriptConfigHandler` 实际定义留在 `app/models/script_contracts.py`，仅供旧专项兼容注册使用，插件模块和 SDK 不再暴露该契约。

游戏管理尚未迁移，旧模拟器模块仍需反查托管以展示受影响对象和保护运行中的引用。此过渡期只通过 `ScriptEntry.get_emulator_binding()` 明确声明的只读接口获取绑定，MAA 在自身配置类实现；宿主不读取 MAA 字段名、不接收配置处理器，也不调用未声明的专项方法。该兼容入口随游戏设备迁移移除，不扩展到通用插件声明或调度协议。

框架更换引起的一次性迁移归主程序配置升级所有，不由专项插件声明或启用流程执行。数据版本 `v2.1→v2.2` 在 `app/core/config/manager.py` 编排，具体插件化迁移放在同目录 `plugin_upgrade.py`：按旧托管、计划类型索引识别已完成插件化的专项（当前仅 MAA，含旧测试插件类型名及早期分目录格式）；在领域集合激活前复用插件管理器安装缺失插件并启用，备份和转换旧类型标签；激活后完成已有托管的更新接管和渠道迁移，保留 UID、顺序与引用；全部保存成功后才推进数据版本。安装、加载或保存失败不推进该检查点，重启按原版本及已有字段标记继续。正常 `v2.2` 启动不再执行这段迁移，不反复安装或改写用户后续选择。删除 `ScriptTypeDecl.initialize_config` 及插件内对应迁移函数；新建托管使用的 `ScriptConfigHandler.initialize` 保持原职能。

插件脚本引用联动在类型登记时绑定类级信号，不在实例激活回调内修改生命周期。L2 只为当前插件执行建立进程作用域，正常运行仍在原持锁协程逐级 await；停止先确认更新及保存，再取消，ModeWorker/UserExpander 收尾沿已有进程确认边界执行。TaskBase 本身不增加业务担保。

## 26. MAA 关卡数据归属与源码结构（2026-11-13）

关卡候选由 MAA 插件注册的 `/api/plugin/maa_adapter/stages/options` 提供，
各区服活动与关卡视图由 `/stages/overview` 提供。账号及计划表的主关卡、三个备选关卡
统一声明 `select(endpoint=...)`；字段仍接受自定义关卡字符串，不用远端候选约束持久值。
现有前端直接调用生成的插件客户端，本轮不改为动态 UI。

插件启用时创建自己的关卡服务，通过本插件背景任务组首次检查官方资源；
正文、ETag、成功检查时间保存在 `MaaPluginConfig.stage_cache`，由配置框架持久化。
后续消费复用同一服务，按原有效期、条件请求和失败冷却策略刷新。
缓存失败保留旧内容，停止与重载由插件任务组回收刷新流程，卸载删除插件配置及缓存。
宿主全局设置中的关卡字段、关卡号接口、关卡及材料常量全部移除。
首页宿主概览只提供通用托管统计，MAA 关卡视图由前端独立查询插件接口。

插件命名空间内的具体类型化 HTTP 路由排在通用插件网关之前，防止已注册端点被通配路径遮挡。
原有绝对路径插件路由保持既有优先级；路由仍随调用门及插件生命周期装卸。
MCP 读取关卡的权限由插件端点声明，不再保留宿主专属白名单项。

源码按 `config/tasks/native/updates/cultivate/stages/logs/api` 归组。
配置和查看分别为 `config_session.py`、`view_session.py`，只共享底层 GUI 会话实现，查看不继承配置入口。
任务编排保留在 manager 和 auto_proxy，纯配置转换、养成任务构造、日志解析及恢复操作移到对应领域。
MAA 报告内容生成归插件，通知投递仍直接使用宿主 Notify，不添加业务包装层。
旧模块路径与专项 SDK 通知桥接移除；类名、配置 UID、既有专项 HTTP 路径及任务生命周期语义保持。
