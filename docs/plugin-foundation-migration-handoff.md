## 4. 已解决的第一项冲突：配置事务与外部副作用

### 4.1 最终决定

本阶段配置基类不提供以下两项通用担保，暂不解决，使用者自行尝试规避：

1. **提交后触发保证**：不保证通知、进程操作等外部副作用只在相关配置事务成功后发生。
2. **外部副作用完整回退保证**：不保证配置回退时，任意已经执行的业务副作用都会自动恢复。

例如，通知发出后配置回退，属于配置事务与外部副作用一致性缺口，
可描述为缺少提交后触发保证、幽灵通知或未提交副作用泄漏。
用户曾口误为“仅一次”，已经纠正；本项不要求执行一次、汇集或去重。

已有配置数据、关联字段修改、订阅增删及异常回退契约继续保留。
插件生命周期的既有资源释放与失败清理责任也继续保留。

### 4.2 来源核实与职责分工

```text
注册表接口只接受 enable/disable/reload/uninstall Trigger
→ 配置模型转交 Plugin 操作
→ 插件管理器预检、依赖编排、执行用户/系统钩子
→ 成功后提交 enabled/state 等结果
→ 失败由 _fail_branch / system_rollback / on_fail_cleanup 清理并记录故障
```

用户不会经注册表更新接口直接把 enabled 或运行状态改成成功。
插件管理器成功完成用户钩子和系统登记后才提交启用结果，
因此主要启停链路不依赖“整个配置事务统一撤销全部外部资源”。

配置基类在本轮承担字段、事务及触发传递；插件框架承担操作和约定范围内的失败恢复。
配置提交完成、插件操作完成、文件保存成功分别判断。

### 4.3 不要恢复的旧建议

- 不新增事务完成信号或逐观察者提交后队列。
- 不新增 `connect(..., rollback=...)`、自由 `on_rollback` 登记或通用外部补偿日志。
- 不实现包装器多版本缓存、异步回退阶段或“仅一次”机制来解决本项。
- 不据此修改 L1/L2、TaskBase 或任务 WS 推送。

此前这些方案均已撤回，不能因阅读旧讨论而重新当作需求。
“回退方法处理自身错误，框架捕获意外异常并记录”仅是当时候选方案的约束；
本轮不实施通用登记机制，既有插件清理仍按自身生命周期契约处理异常。

### 4.4 来源额外能力不能混淆

固定来源已经新增了提交后配置观察，以及事务成功后才向 `TriggerDispatcher` 受理命令、失败丢弃命令。
这是真实源码事实，不能说来源完全只有即时信号转发。
但它们不等于任意插件副作用都有完整一致性保证，本阶段也不自动将其列为必迁前置能力。

来源 `BasePlugin.config_events` 依赖 `app.config.committed`；当前 dev 没有对应模块。

## 5. 已落地的调度契约：后续模块必须承接

### 5.1 创建入口与要求树

内部入口为 `TaskManager.start(mode, tasks, *, trigger=TaskTriggerReason.MANUAL)`，返回运行 UUID。
保留 `/api/dispatch/start`；HTTP 手动创建只接收 mode/tasks，触发原因由后端指定。
`TaskCreateIn` 留在 API 边界，内部调用不强制构造它。

- 公开模式仅 `TaskMode.AUTO_PROXY / SCRIPT_CONFIG / SCRIPT_VIEW`。
- `ManualReview` 已移除；`Update/CycleRun` 也不作为公开创建模式。
- 触发原因只有 manual/startup/timed/cycle 单值，独立判定，无组合值。
- 要求节点为 `uid`、独立 JSON 字典 `params`、`children`；索引从 0 连续，JSON 表现为字符串。
- 顶层必须且只能有索引 0 一个入口，不在一次创建中合并多个队列或混合来源。
- 自动代理为“队列 → 队列项/直接托管 → 用户”。真实队列下 uid 是队列项 UUID，L1 解析为托管 UID。
- 队列 `uid="-"` 表示直接托管，下级必须显式指定托管；真实队列空 children 为全队列，托管空 children 为全用户。
- 非空选择必须是原序列的子序列，不能逆序、增加出现次数或选入不存在对象；重复托管按队列项保留独立执行。
- 配置/查看会话只有“托管 → 用户/default”，恰好一个托管和一个目标；default 是共享配置，不是真实账号。
- `instance_idx` 放托管 params；不恢复 `view_only`、独立 queue_item_id 等零散 start 参数。
- 参数按节点隔离复制，向对应层传递，不隐式合并父级参数，也不把队列身份偷塞进托管参数。

### 5.2 唯一运行树

```text
TaskManager 保存多个独立任务根的映射
TaskItem → TaskScriptItem → TaskUserItem → LogRecord
```

所有运行节点自行生成 UUID；原业务配置 UID 只是属性。
进度引用运行 UUID，配置查询使用业务 UID；同托管重复执行的状态、日志和结果独立。
不增加 TaskQueueItem、空队列节点、TaskQueueSource 或总任务树根。
运行树使用当前 Config 基类、信号、集合、虚拟结果，仅驻留内存，不登记为持久化根。

不向公共任务树加入锁状态、MaaFW 专项计数或通知素材。
`locked` 等已移除；维护/推送素材在 LegacyUserState 或专项内，专项计数由专项持有。
结果由模型动态计算，不另建可写结果副本。

### 5.3 L1–L4 与锁

- **L1**：校验并完整建树，展开空选择，填写基本身份，失败不发布部分树。
  不按禁用/天数提前删除用户；成功受理时记录对应触发时间，并保存队列前后脚本、结束动作等快照。
- **L2 ScriptExpander**：按固定托管清单派发，判断队列项星期限制，不锁队列、不重新展开原队列。
  插件路径先确认托管存在，等待其非级联 X 锁，持有凭证至 L3 收尾结束，再解锁。
- **L3 UserExpander**：托管检查/准备，对每个真实用户先确认存在，再等待用户级联 X 锁；
  取得后复核对象和准入，把已锁对象交 L4，等待完整收尾后释放。
- **L4 ModeWorker**：消费已锁用户及参数，执行对应模式和恢复，不重复取得或释放上层票据。

等待时保持等待状态并输出等待对象/占用者日志，下一级真正运行时才改运行状态。
等待每轮重新解析配置，不对已经删除或替换的旧对象永久等待。
当前用户及托管本体冲突修改被拒绝，其他未占用用户可修改、删除。
未来用户执行读取最新热态字段，结束不整份写回旧快照。
共享 default 没有真实用户锁，由托管保护；各层 final_task 兜底释放自己的凭证。

### 5.4 生命周期与旧专项分叉

`TaskBase` 仅保留来源生命周期：`main_task/final_task/on_crash/start/stop/spawn`。
新执行树通过 `await self.spawn(child)` 在同一 Task 中执行子层，保持配置锁上下文。
提交必须由产生暂存的协程完成，不能指望另起 final_task 协程代交原协程暂存。

L2 在 `ScriptExpander` 处分叉：插件走新 L3/L4；旧 task 直接调用原 manager，
其用户展开、锁、历史和通知由旧 manager 承接，上层不大规模重写旧专项。
旧接口以 `[兼容旧专项]` 或 `[兼容旧调用方]` 标明，新插件不新增对其依赖。

**明确禁止为 dev 新停止设计改动 L1/L2 或来源 TaskBase。**
PR #1871 的更新停写确认、MAA 保存确认及所属进程强制清理，临时放在旧专项执行桥的差分内。
`app/task/legacy.py` 持有相关执行边界，使用 `TaskProcessScope`；嵌套旧专项共享范围。
后续插件迁移重新确定它的去向，不把这套兼容机制提升为所有插件或 TaskBase 的标准。

## 9. 当前公共后台与电源能力

`app/core/background_tasks.py` 已替换 runtime_tasks，是应用级背景任务挂载点。
`BackgroundTaskManager` 已是单例，不能再当类构造。

- 申请/注销任务组，组内持有引用；并发和保留记录分别限额，不自动排队。
- spawn 使用协程工厂；关闭或满容量拒绝时不创建协程。
- query 不消费结果；try_take/wait_take 一次性提取并清理。
- 支持执行超时、未提取结果过期，以及显式取消；不能说只能靠超时中止。
- 组关闭和全局关闭等待其清理，独立背景工作不挂 TaskBase 执行树。
- 应用级后台任务清除调用方的 TaskProcessScope 上下文，避免停止旧专项时被误伤。

电源相关协调属于 `app/core/power.py`，原 System 普通功能已转 utils 等真实所有者。
PowerSignal 使用枚举；delay 是唯一倒计时，默认 60 秒；队列最小 1 分钟，填写多少就是多少。
Power 订阅任务结束，在结束动作意图设置后判断是否开始倒计时。
只用 power_task 表示活动倒计时，新任务在 L1 发现它时直接拒绝受理，不加额外避让/补跑机制。
睡眠/休眠不自动退出后端；关机/重启等按现有动作后请求退出的顺序，时序优化已明确延期。
