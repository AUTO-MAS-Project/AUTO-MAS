## 2. 工作包一：配置骨架、插件基类与 SDK

决策依据：设计记录第 1、7、18、19 节。

1. 同步迁入 BasePlugin、扩展/游戏/模拟器/脚本适配器基类、声明、控制协议，以及 SDK 导入和
   类型登记所需的真实配置骨架。不以占位类或空成功实现补齐依赖，也不借此提前迁完具体游戏或专项业务。
2. 对齐当前 `AUTO_PROXY / SCRIPT_CONFIG / SCRIPT_VIEW`、L3/L4、任务上下文和配置锁契约，
   修正来源旧模式及 SDK 导出。保留既有要求树、唯一运行树、运行 UUID、节点参数隔离和同 Task 提交规则。
3. 不迁入已排除的通用提交后观察、Trigger 提交后受理担保或外部副作用补偿框架。
   SDK 的 committed/config_events 依赖据此调整，不用事务内信号冒充提交后事件，不保留虚假成功接口。
4. SDK 服务出口接真实宿主能力；应用更新编排前移后，不继续导出一套完整后端 Updater。
   预下载需求插槽及其真实请求/结果契约与下载管理同步接入。
5. SDK 发行版本跟随宿主，接入现有 CHANGELOG → `scripts/changelog.py` → 版本生成及 CI 链路，
   Python 发行使用既有 PEP 440 转换。协议版本独立表示兼容契约；SDK、宿主合成发行元数据和依赖声明配套一致。
   不另建版本真相来源，不在普通迁移中手改主程序发布版本。
6. 内置 SDK 随源码/资源分发，用户插件和共享第三方包位于用户插件空间，配置和数据位于各自用户目录。
   开发环境和 Runtime 的源码/工作目录分离均按这一布局接线。

完成条件：SDK 公开导入、真实类型声明和当前执行契约成立，发行元数据与统一版本来源一致；
不以 core 插件可导入代替所有外部插件兼容性验证。

## 3. 工作包二：统一下载管理

决策依据：设计记录 10.6、15.7、第 17 节。

### 3.1 执行与公开能力

- 下载中心是全局下载业务所有者，初始化时申请专属 core.BackgroundTaskManager 任务组，
  复用现有 FluxDown/内置传输能力，承担底层线程、进程或 daemon 的停写确认。
- 公开能力包含申请、查询、等待、列表及按 URL 清理/释放；申请受理返回布尔结果。
  查询非阻塞，等待返回对应需求的明确结果，不能用 path/None 混淆未知、运行、失败和取消。
- 下载中心唯一消费背景结果，自行保留业务状态供重复查询、重连和多个等待者读取。
  背景结果被提取或过期不代表可以删除业务文件。
- 默认 FluxDown 优先，保留实际可用性、回退和停写规则；调用方可显式覆写已有下载器选择。
  同一产物正在受管下载时，不因另一个调用方的下载器偏好重复并行写入。
- 下载接口只承担传输管理，不隐式选择应用版本、安装方案、解压或重启。

### 3.2 文件身份、结果与缓存

- 需求携带 URL、可空 rid、可空内容 hash 和可选下载器覆写。内容身份按 rid → hash → null 选择。
  rid 不擅自解释为项目级 MirrorChyan RID；URL 哈希不能冒充文件内容哈希。
- 同 URL 且身份为 null 时视作同一文件，不额外加入隐式远端变化探测或 TTL。
- URL 为顶层查找键，内部保留文件身份和执行记录。再次申请和锁后复查均比较有效身份；
  变化时启动新下载并切换实际状态，查询/等待关联对应身份与执行轮次，不能串用新旧结果。
- 文件路径区分 URL 空间及 rid/hash/null 身份，新下载不覆盖旧产物；旧文件按既定引用与缓存规则管理。
  未完成文件不发布为成功文件，共享缓存原件由业务只读使用，需要改写或移动时使用自己的副本。
- 命中成功结果前检查文件；已不存在则撤销旧成功结果、合并重新下载并返回实际状态，已有引用不重复计数。
  清理时文件已不存在视为完成，同步维护缓存条目及体积统计。

### 3.3 引用、失败与退出

- 申请与清理成对计数；同一 L2 对同一 URL 只持有一份引用，拒绝受理不计数，复查和重下不重复计数。
  一个使用者释放不影响其他使用者。等待方取消不自动取消共享下载，所属业务收尾继续释放自己的引用。
- 计数归零表示最后一个使用者取消：在途下载立即请求取消并等待真正停写，不继续执行或自动网络重试。
  已完成文件先缓存；总文件体积超限时只回收零引用缓存，仍被使用的旧产物不能回收。
- 暂时容量不足由 L2 等待后重新申请，直到受理或业务取消/失效；管理器关闭后结束重试。
  网络波动统一有界退避重试，持续失败形成明确终态；调用方取消不按网络故障重试。
- 普通失败在确认停写后明确报错，不传失败文件 path，由 manager/L3 正常准备流程决定后续处理。
  未确认停写持续阻断，不能通过不传 path 后继续安装或另开下载来绕过。
- ALL 仅应用退出时调用：封闭受理、中止全部下载、等待停写、删除全部下载缓存及记录、注销背景组。
  L2 final 仅释放本轮引用。正常退出不保留跨启动下载缓存；前端已复制的更新包不属于后端缓存。

完成条件：申请、共享、身份变化、缺失重下、取消、失败、缓存回收与退出的状态和文件所有权一致。
公开方法及状态字段的具体命名、并发数、缓存容量、重试间隔/次数/期限随实现细化，本文不写入未经确认的数值。

## 4. 工作包三：插件运行时、Operations 与宿主接线

决策依据：设计记录第 6–8、10、11、19、20 节。

### 4.1 发现、加载与安装

- 迁入来源有效的发现、元数据、加载清理、监视、市场、服务与 HTTP 注册能力。
  按发行元数据及 `PLUGIN` 导出发现，不恢复已经注释的旧管理器；保留不可禁用的 core 插件和加载阶段不创建实例的边界。
- 分清运行时 `requires` 硬服务依赖、`wants` 可降级依赖与发行包 Requires-Dist。
  硬依赖按来源级联编排；可选依赖不被解释为始终保证提供者存活。
- 插件包安装/升级保留后端宿主所有权，沿来源 uv 和共享安装目录方案，共同校验宿主及保留插件依赖。
  不兼容变更明确拒绝，不能只验证插件自身可安装。
- uv 沿既定查找链和 Runtime 安装归属接线；迁入真实镜像配置及 pyproject-metadata、watchdog 等生产依赖与锁文件。
- discover、loader、watcher、装卸包、SDK 和配置根统一使用现有 source/resource/plugins/config/data 路径能力。
  适配工具真实入口；插件通知委托给 core.Notify，复用现有渠道、渲染和唯一报告所有者。

### 4.2 命令与受管调用

- 配置基类保持 dev 实现：普通 Trigger 直接分派，update 返回 None，不注入全局 TriggerDispatcher。
  插件相关配置通过 PluginCommandEntry 接入插件层 Operations；取消策略由插件层 trigger_field 声明。
- Operations 位于 app/core/plugin/operations.py，持有目标、owner、操作身份与后台句柄，
  管理受理、同配置同 Trigger 的去重/冲突、重复查询、有限历史、可取消策略及 owner 暂停/恢复。
  同配置的不同 Trigger 不作整体互斥。
- 实际执行交 core.BackgroundTaskManager，取消独立顶层 `_TriggerTask`。
  Operations 唯一消费后台结果，前端查询读取操作记录；启动前取消和异常均进入准确终态。
  取消、owner 暂停和退出等待覆盖执行及终态通知尝试，通知失败不改变业务结果。
  不为此增加空的 TaskBase 包装或背景组专属收尾框架；具体业务清理由处理函数负责。
- 前端通过独立命令入口取得 operationId，配置保存不再返回操作 ID。注册表/市场输出保留 UID 与 UI 元数据，
  插件菜单、安装和配置动作依据 hints 的存在性及 editable 显示或禁用，不重复推断业务权限。
- 满容量返回 busy，不建立 Operations 排队机制；不可取消命令不叠加绕过其策略的统一执行超时。
  暂停单个 owner 不以注销整个共享操作任务组替代。
- HTTP 和声明式服务在暴露的方法调用边界停止新受理，跟踪实际在途执行并等待结束。
  插件实例获得所属背景组入口，提交协程工厂；释放实例前封禁、取消并等待登记工作。
- HTTP 在业务执行前确定签名和参数绑定；同步/异步 handler 只调用一次，业务 TypeError/ValueError
  进入统一错误处理，不再触发第二次试调用。结束、失败和取消均释放调用引用。

### 4.3 配置与生命周期

- 配置根从构造起就有清理所有者，覆盖插件构造、预检、启用和失败出口；统一注册项与配置根 UID 的定位契约。
  确认保存后才注销，保存失败保留根的所有权和后续保存机会，操作状态如实反映故障。
- 禁用、重载、卸载统一停止受理并等待，修正 uninstall 绕过 owner 暂停；保留合法锁检查及依赖顺序。
- 宿主管理公开调用、登记执行和宿主配置/类型资源；插件负责连接、文件、设备、进程、自建监听器、
  未登记后台工作及外部状态的实际清理。受管协程结束不自动等于外部写入已经停止。
- 重载通过 reload_type 保留游戏/设备及托管配置身份、持久化字段、顺序和有效引用。
  用新类重建并重新绑定控制器、订阅和刷新工作，不删除设备再发现、不虚发删除事件、不把旧运行状态当当前状态。
- 普通禁用适配器沿来源 remove_type，级联删除所属领域配置；插件自身配置根保存释放。
  卸载删除全部所属配置，包括已经禁用后遗留的自身配置文件；共享根只删所属成员。
  配置删除不扩成删除脚本本体、模拟器实例或其安装目录。
- 退出调用 on_teardown，保留用户启用意图。消费者先收敛再释放提供者；服务密封后收尾使用已持有的资源，
  不隐式放开新的业务查询。通知、配置保存和背景执行能力保留至实际收尾结束。

完成条件：发现、装卸、命令、公开调用及登记资源形成真实闭环；失败不虚报成功，资源释放不遗漏配置保存或在途使用。

## 5. 工作包四：完整插件前端与国际化

决策依据：设计记录第 9 节及用户确认的完整来源页面范围。

1. 完整迁入来源实际实现的 Plugins、PluginMarket、PluginSettingsPage，以及配套标签、声明式字段/表单、
   API composable 和路由。通用插件页路由沿来源已有设置页行为，不补做任意动态页面加载器。
2. 对接真实操作查询、安装、启停、重载、卸载和配置保存结果，区分受理与完成；
   后端 schema 改动通过项目生成器同步前端 API，不手改生成代码。
3. 直接迁入来源 core 与插件共同供给资源方案，前后端接通 core、plugins 命名空间；
   bootstrap 继续归前端，界面语言继续由 Electron/前端持有，插件名称/说明跟随同一语言。
4. 后端提供原始各语言词表，保留现有 Vue I18n 回退；来源语言文件名在读取边界映射。
   基础阶段保留中、英、日三种宿主语言，不因插件附带其他资源自动扩充语言菜单。
5. 禁用保留可读插件资源；卸载或来源移除后从完整快照清除。真实资源变更接既有 revision、
   I18n.updated 和重连读取，目标及回退语言同 revision 整批应用，不发布混合快照。
6. 沿现有前端规范和匿名遥测边界接入页面与操作，实际终态由唯一所有者观察，不将请求受理当完成，避免重复采集。

完成条件：来源已实现页面及操作可用，语言偏好、回退、禁用展示、卸载清词条与重连保持一致。

## 6. 工作包五：L2 预下载与旧专项/插件双源适配

决策依据：设计记录 12.4、15.7、第 17、18 节。

1. 旧专项通过固定方法、新专项通过统一插件声明提供同语义检查：传入脚本配置对象，
   返回下载需求 list，空列表表示无需预下载。需求使用 URL、rid/hash 和下载器覆写契约。
2. 初次检查无需获取配置锁，保持只读；需要异步查询时先读取必要字段，避免混读。
   不安装、不写配置、不启动设备，不通过试构造需要持锁的插件执行器探测能力，不持配置事务等待网络。
3. L2 收集本轮固定托管清单的需求，按 URL 去重后提前提交；容量拒绝则等待重试，
   正确记录部分受理、取消和失效。新批量策略替换旧单候选/首次成功后 60 秒策略；
   不借此扩展配置/查看会话的职责，是否需要下载由实际业务声明及既有更新设置决定。
4. 每次运行前先确认配置存在与身份有效，再获取托管锁并重新检查需求；比较 URL 与内容身份，
   新增的补申请，变更的重下，当前已不需要的 URL 不提前释放。仅等待锁后当前需求。
5. L2 台账记录全部成功持有 URL，每 URL 一份引用，final 在 manager/L3 完整使用和收尾后统一各释放一次。
   旧 manager 保留自身锁所有权，兼容入口明确等待/复核位置，避免上层锁与旧递归锁叠加死锁。
6. 将锁后仍需要且成功的 URL → 路径字符串映射放到运行参数的专门保留 key 下，保留其他自定义参数。
   在产生暂存的协程提交，再创建/更新 manager/L3 上下文；不自动向 L4 合并。
7. 需求检查失败明确报错，不用空列表伪装无需求。普通下载失败确认停写后不传 path，
   未确认停写阻断；多个等待者读取下载业务记录，不竞争背景结果。
8. 版本/来源选择、架构/摘要、安装复核及业务元信息仍由各专项更新业务负责。
   将旧需求发现、文件传输和文件消费分开适配，保留多文件/多引擎需求；Whimbox 非文件依赖构建留在业务准备层。
   MaaFW 原隐式 discard 缺失随清理契约适配修正，不继续依赖不完整的旧隐式方法组合。
9. 预下载展示继续从现有任务树预下载状态提供，将统一下载实际状态/进度接入；
   不新增文件运行节点或第二棵任务树。沿现有传输历史与下载方式接线，避免重复记录。

完成条件：新旧混合分派、初次批量申请、锁后差异补充、失败分流、路径消费及成对释放闭环；
已迁移插件解析器不再全局关闭尚未迁移旧专项的预下载。

## 7. 工作包六：应用更新业务前移与启动退出集成

决策依据：设计记录 10.6、15.7、19.4。

- 前端统一负责应用/core 与 Runtime 的版本检查、发布信息、更新源/目标选择、流程策略、产物校验、
  解压/替换/安装、后端启停、重连和最终版本确认。Renderer 负责交互，文件/进程/Runtime 沿 Electron 主进程及 IPC 执行。
- 后端保留统一下载接口与独立升级预检接口。预检结合明确目标、目标依赖和当前插件集合，
  返回可升级、不兼容或检查未完成及原因；只检查，不修改环境，目标/插件集合变化后重新检查。
- 前端取得并校验产物，确认预检仍有效，将更新包复制到前端所属目录并确认完成后，
  再释放下载引用及停止后端；后端退出 ALL 不影响独立副本。

## 9. 后续路线与仍延期的决定

### 9.1 游戏管理阶段已确认边界

### 9.2 专项阶段已确认边界

旧分支保留明确兼容标记，新插件不新增对旧兼容接口的依赖；全部迁完后再移除剩余旧兼容路径。
脚本执行和结果复用上游公开入口，MAS 负责账号、调度、通知、统计和跨脚本编排等自身领域。

维护任务标准、手动更新等兼容入口及隐藏 Update 转换、维护日志消费者、操作身份/查询与取消、
停写未确认结果、通用计划日期调度接入，以及同安装目录等延期问题，仍按交接记录等待对应阶段讨论。
