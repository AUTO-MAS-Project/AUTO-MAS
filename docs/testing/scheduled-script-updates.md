# 顺序队列更新编排

## 三层职责

1. **调度中心**（`app/core/task_manager/manager.py`）：决定本次运行的脚本、排序及循环到期项，执行时只向公共入口发送 `watch`、`take`、`finish`、`close` 指令。
2. **公用更新入口**（`app/core/script_update.py`、`app/core/script_update_queue.py`）：决定下一实际可运行目标、等待 60 秒、异步预下载、持有候选、比对配置基线、移交及取消清理。后台只下载，不安装。
3. **各脚本代理更新逻辑**：只有启用托管更新才检查版本及下载；沿用各自的安装锁、文件完整性/基线校验、回滚、失败恢复。更新包只在本脚本启动前应用，绝不在前项运行期间安装。

用户点击开始运行后，第一项由专项原有的启动前统一更新入口完成版本检查及安装，再进入其账号任务。**当前脚本本轮首个成功任务节点**记录单调时间，继续运行满 60 秒时由第二层开始预下载下一项。脚本级首次成功时间跨账号保留，因此同一脚本的切号不重新计时、不取消正在进行的下载，紧邻的同一脚本也不重复发起预下载。

上一脚本任务及收尾结束后，必须等待已经发起的下载收敛，才进入下一脚本原有安装流程；包尚未下载完不能启动下一脚本。启动前重新核验候选身份及摘要；配置/路径变化则丢弃候选并重新检查。真正的重试导致原首次成功信号失效、脚本失败或用户停止时，撤销预取并等待下载写入权清理；后台更新失败不阻断当前脚本任务。

顺序队列跳过没有选中账号、未安排当日、已删除或锁定的项，只预取实际下一脚本。循环队列只预取调度中心明确标记本轮已到期的下一项；不会扫描到其它未来排期。尚无可靠任务节点成功结果的脚本依旧只走启动前更新。配置身份仅在内存比较，不进入下载日志、文件名和遥测。

| 更新对象 | 预下载内容 | 应用边界 |
| --- | --- | --- |
| MAA GitHub 本体及资源 | 独立缓存内的官方 OTA 或完整包及资源 staging | 复核原版本、包摘要后复制并登记，原生更新器安装；资源启动前才分发 |
| MAA Mirror 本体及资源 | 已有共享完整包及资源 staging | 启动前才登记和分发，预取不分发任何实例 |
| MaaEnd | 官方完整 ZIP 及 SHA256 校验 | 复核安装版本/架构，原有可恢复目录切换 |
| HSR M7A／SRA | 每引擎独立缓存包 | 复核安装版本和包摘要，原有进程门及安装/回滚 |
| MaaFW／M9A／MSS | 完整包进入核心共享下载缓存 | 基线未变时复用候选，变化后重新发现；保留预检、载荷登记及视图切换 |
| 奇想盒 | 官方后端 wheel 及隔离构建的全部依赖 wheel | 复核安装版本及所有包摘要，原有离线安装和恢复标记 |

奇想盒目前没有运行中可用的首节点完成结果，作为前项时不会触发后台预取；作为后项可提前准备更新。其它未提供可靠节点完成结果的适配器同样保持启动前更新，不推断首节点结果。

## 正在修改的 PR 的接入位置

以下三个 PR 保持独立，不导入、复制或合并其尚在修改的实现。共同接缝是管理器的 `prefetch_script_update()` 与 `discard_prefetched_update()`，默认实现不执行下载。合入后按下表接入；安装继续放在原启动前入口，不能在预取钩子调用整个 `prepare()`。

| PR | 预取钩子 | 安装消费 |
| --- | --- | --- |

| #1822 SRC | 调用其 `prepare_update` 保存 Git 对象候选 | 启动前调用 `apply_update`；依赖与 app.asar 仍交原生安装器 |
| #1823 BAAH | 调用其 `prepare_update` 保存官方 ZIP 候选 | 启动前调用 `apply_update`，保留安装身份复核 |

候选取消、配置变化和未消费时由第二层调用 `discard_prefetched_update()` 回收；尚未确认停止的下载器必须保留自己的独立下载目标。公共队列不提前占用安装、不调用游戏任务，也不宣称这三个 PR 已接入。

## 取消与下载身份

用户停止、前项失败后的撤销和重复停止都必须等待实际文件操作与下载进程收尾；收尾期间新收到的停止请求仍须传播，不能在清理结束后继续启动下一脚本。普通下载失败只有在确认写入者停止后才能回退；无法确认的情况中止队列并保留文件和任务映射。

FluxDown 每次 `add` 使用独立的随机输出路径，在发送命令前原子保存该路径和待确认标记。创建响应丢失时只按这条请求路径恢复任务身份，不用任务列表差集推断新旧任务；服务启动时的空快照无法证明没有历史任务。旧版没有请求路径的待确认记录继续保留，不猜测归属。不同输出文件的映射读改写也共用跨进程锁。

覆盖旧目标前先发出 `pause` 请求，但成功响应只表示 daemon 已受理取消，下载线程仍可能在收尾写盘；paused/failed 快照不能充当停写回执。当前 CLI 没有等待暂停完成或返回执行代次的能力，因此只接受 HTTP 任务已完成（completed，`resume` 不会重新下载）或 daemon 明确报告任务不存在这两类证据。初始状态查询失败和 resume 失败后的恢复同样保留原映射，不能因 paused/failed 快照另建下载任务。

这一限制依据 FluxDown 固定提交 `294a72bc8fe300a769cee6420b84d1592fd038cb` 的 [暂停、完成态恢复和删除实现](https://github.com/zerx-lab/FluxDown/blob/294a72bc8fe300a769cee6420b84d1592fd038cb/native/engine/src/download_manager.rs) 及 [daemon 命令回执](https://github.com/zerx-lab/FluxDown/blob/294a72bc8fe300a769cee6420b84d1592fd038cb/native/daemon/src/actor.rs)。代价是服务端下载取消或失败后，即使已经显示暂停，也可能报告“停写未确认”；在取得上述证据前，切换下载器、替换目标和队列移交都会阻断。原任务映射保留，同一目标再次选择 FluxDown 时仍可尝试恢复原任务。

取消时暂停无法确认，无论是否已经取得任务 ID，均尝试结束 MAS 自有、独占的私有服务。强杀不等于持久暂停，服务重启可能自动恢复任务，因此仍保留映射和文件并报告未确认状态，不按普通取消交接后项。

确认下载完成后才把独占文件原子归位，先完成映射清理，再写可取消的下载历史。若进程在归位与清映射之间退出，后续确认旧任务停止并移除后重新下载，不盲用已有目标文件。一次性预取目录只在确认停写后整目录回收；共享缓存保持各自的锁和续传规则。

内置 httpx 的整文件、续传和范围下载同样等待写入、摘要读取和文件关闭完成后传播取消。FluxDown `--local` 在创建和回收阶段持有进程归属；Python 构建进程的终止和等待也受取消保护。重复取消不打断回收，退出时排空管道，避免已结束进程仍卡在输出背压上。

## 验证

`tests/core/test_script_update_queue.py` 验证 60 秒保护窗口、没有成功信号时不预取、短任务撤销计时器、正常完成等待下载、切号保留计时、重试/失败/停止等待清理，以及预取失败不影响当前脚本。专项更新回归继续守护各自的安装和恢复边界。

公共下载回归位于 `tests/services/test_update_fluxdown_proxy.py`、`tests/services/test_update_download_cancellation.py`，覆盖启动空快照、迟到历史任务、请求响应丢失、CLI 缺失、跨进程映射写入、pause 已受理但 paused/failed 快照仍不能确认停写、重复取消、文件线程收尾和真实子进程管道回收。MAA 另验证候选复制结果、原生待更新状态、候选单次消费和取消额度；HSR 使用模块最终业务结果触发首成功信号；MaaFW 验证异步/合作停止等锁；奇想盒验证预取构建与清理的取消边界。

真实 Windows 发行包更新、真实账号任务、登录网络竞争与同组多实例需要作者本机验证；自动测试不替代这些证据。预取不新增遥测事件，脚本及队列终态继续由原观察者记录。
